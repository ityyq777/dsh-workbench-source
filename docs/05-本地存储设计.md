# 05 · 本地存储设计（SQLite）

## 为什么直连 SQLite 而不是宿主 storageDomain

宿主 `storageDomain` 先例（dsh-prompt）是 **zod KV → 单个 JSON 文件**：
读全量、写全量、进程内事件。工作台的负载不同：

- 要按条件查询（今日任务、标签过滤、打卡连续性统计）；
- 同步需要**行级增量**与变更游标；
- addon 各自建表，数据量随时间增长。

JSON 域全部不匹配。db-tool 已证明插件可携带 sqlite 能力
（引用 node:sqlite/better-sqlite3，vendor 目录分发预编译件），照此路线走。

| 驱动 | 优点 | 缺点 | 决策 |
| --- | --- | --- | --- |
| better-sqlite3 | 同步 API、生态成熟、性能极好 | native 模块需 prebuild 三平台 | ✓ 主选（prebuild + node-gyp 兜底） |
| node:sqlite | 零依赖 | Node ≥22.5 且 API 较新、跨 DSH engines(node>=20) 有风险 | △ 运行时探测到则优先 |
| sql.js/wasm | 纯 JS 分发无忧 | 内存常驻、落盘要手动导出，性能差 | ✗ |

## 文件布局

```
~/.dsh/workbench/
├── workbench.db            # WAL 模式；单进程权威（对齐宿主"单进程为准"已知限制）
├── addons/<id>@<ver>/      # addon 安装目录
├── blobs/                  # 附件内容寻址（sha256），DB 只存引用
└── sync-state.json         # 设备密钥、同步游标、登录 token 引用
```

## Schema 骨架

```sql
-- 元数据与迁移
PRAGMA user_version;                      -- 壳持有整库版本；addon 迁移注册在 core 的有序列表里
CREATE TABLE meta(k TEXT PRIMARY KEY, v TEXT);            -- device_id、install_epoch...

-- 每个实体表统一列约定（同步的前提）：
--   id TEXT PRIMARY KEY            —— UUIDv7（时间有序，索引友好）
--   ...业务列
--   rev INTEGER NOT NULL           -- 单调递增版本号（每次写 +1）
--   updated_at INTEGER NOT NULL    -- 毫秒 epoch（LWW 依据）
--   deleted_at INTEGER             -- 软删除墓碑（同步需要删除语义）

CREATE TABLE tasks(
  id TEXT PRIMARY KEY, title TEXT NOT NULL, note TEXT DEFAULT '',
  status TEXT NOT NULL DEFAULT 'open',      -- open|done|archived
  priority INTEGER NOT NULL DEFAULT 2, due_at INTEGER,
  rev INTEGER NOT NULL, updated_at INTEGER NOT NULL, deleted_at INTEGER
);
CREATE INDEX idx_tasks_open ON tasks(due_at) WHERE deleted_at IS NULL AND status='open';
CREATE TABLE task_tags(task_id TEXT NOT NULL, tag TEXT NOT NULL,
  PRIMARY KEY(task_id, tag));

-- 通用变更日志：所有参与同步的表的写入都追加一行（同事务内）
CREATE TABLE sync_change_log(
  seq INTEGER PRIMARY KEY AUTOINCREMENT,     -- 本地推送序（sync cursor 用它）
  table_name TEXT NOT NULL, row_id TEXT NOT NULL,
  op TEXT NOT NULL,                          -- put|delete
  payload TEXT,                              -- 变更后整行 JSON（delete 为 null）
  origin TEXT NOT NULL,                      -- ui|agent|sync|import （回环抑制标记）
  updated_at INTEGER NOT NULL
);
CREATE TABLE sync_state(device_id TEXT PRIMARY KEY, last_pulled_seq INTEGER, ...);
```

## 写路径纪律（core/repository 层强制）

1. addon 只能通过 `api.db` 写自己 manifest 声明过的表；
2. 每次写在一个事务里完成：业务表 UPDATE + rev 自增 + change_log INSERT + 发 bus 事件；
3. `origin='sync'` 的应用远端变更**不再**写 change_log（防回环——由 payload 哈希对账代替）；
4. 崩溃安全靠 WAL + 每写即 journalling；change log 未推送部分就是天然的待同步队列，
   无需第二份 outbox。

## 迁移策略

- 壳启动跑基线迁移（user_version 递增 SQL）；addon 安装/升级时跑各自迁移，
  记录在 `meta` 的 `addon_migrations` 列表；
- 规则：加列带默认值、禁删列（改名用视图过渡）、迁移前自动备份
  `workbench.db.bak.<ts>`（保留最近 5 份）——对齐 person-dsh 处理器"写入前考虑备份"的惯例；
- schema 版本同时上报云端做兼容检查（老客户端收到未知字段必须忽略：payload 演进采用加字段不减字段）。

## 容量与清理

- change_log 保留 90 天且仅保留未推送尾部（推送成功按 seq 截断，每周 VACUUM-lite incremental）；
- 软删除行 180 天后物理回收（同步语义窗口足够长即可）。
