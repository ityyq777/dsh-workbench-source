# 24 · 云端重构评估（以客户端契约为基准）

> 状态：评审结论。结论先行：**同步核心不需要重写，需要「补测试 + 收敛未用面 + 加协议护栏」**；
> 真要拆，等契约测试落地之后再拆，否则拆分等于重写。
> 评估对象：`cloud/`（子模块 `dsh-workbench-cloud`，commit `1e38913`）。
> 基准：`packages/shell/src/sync/sync.ts`（786 行）与 `packages/shell/src/index.ts` 的云端调用。

## 1. 方法与规模

- 基准是**客户端已实际发出的请求**，不是设计文档：客户端发什么，云端就必须答什么；
  云端有而客户端从不调用的面，属于「没有契约的能力」。
- 规模：`cloud/src/main/java` 27 个文件 1511 行（`SyncService` 411 行、`AuthService` 203 行、
  `FileService` 159 行、`FilesController` 144 行、`SyncController` 65 行）；
  schema 一份 `V1__cloud.sql`（12 张表）。
- 测试：`cloud/src/test` 只有 `util` 下两个类（Json / CanonicalJson），**同步与认证零测试**；
  客户端 `packages/shell/src/sync/sync.ts` 786 行也零单测、`scripts/` 下无同步相关脚本。

## 2. 契约对齐矩阵

| 客户端调用点 | 云端端点 | 状态 |
| --- | --- | --- |
| `index.ts:1327` `/v1/auth/signup` `/v1/auth/login` | `AuthController:20,27` | 对齐 |
| `index.ts:995` `/v1/auth/refresh` | `AuthController:34` | 对齐 |
| `index.ts:1321` `/v1/me` | `MeController:20` | 对齐 |

| 无客户端调用 | `/v1/files/check`、`/v1/files/quota`、`PUT/GET/HEAD /v1/files/blobs/{sha256}` | **未用面**（`FilesController` 144 行） |
| 无客户端调用 | `DELETE /v1/devices/{id}` | **未用面** |

协议握手是一致的：`SyncService.open` 要求 `protocol == 2`（否则 `426 protocol_required`），
客户端 `SyncOpenResult` 的 `session_id / server_time / expires_at / tables` 与
`SyncService.open` 返回完全对应；`tables` 的 `mode` 只有 `row` / `tree` 两种，
与 `packages/addons/*/lib/sync.js` 声明的 `mode` 一致。

## 3. 是否需要重构

| 判断项 | 结论 |
| --- | --- |
| 同步协议要不要换 | **不换**。LWW + 树表整表覆盖（`tree`）+ 行级（`row`）已覆盖三个插件的需求，客户端契约与之严丝合缝 |
| `SyncService` 要不要拆 | **暂不拆**。411 行确实承担了 open/push/pull/snapshot/full/close 与冲突解析，但没有契约测试，拆分时任何行为漂移都无从发现 |
| 文件/Blob 子系统要不要保留 | **保留但冻结**。`BlobStore`/`LocalBlobStore`/`S3BlobStore`/`BlobGc`/`BlobRefIndex` 共约 330 行，配了 GC 与配额，客户端却一次也不调；要么近期接上文件同步，要么在配置里关掉，避免被当成既有能力 |
| 要不要裁掉无人使用的端点 | **是**（`/v1/devices/{id}`）或**补齐客户端调用**（设备管理页目前没有） |

## 4. 问题清单（按优先级）

### P1 · 会误导后续开发的

1. **零集成测试**。同步是全系统最难的并发面（会话锁、游标、LWW、树覆盖），却没有任何
   测试；客户端 786 行同样没有。任何一次「顺手重构」都在盲改。
2. **表名没有白名单**。`SyncService.java:25` 只有 `TABLE_RE = ^[a-z][a-z0-9_]{1,63}$`，
   `push` 收到合法格式的表名就落 `row_states` / `change_log`。今天三插件的表固定，
   明天任何插件新增表都会被旧云端静默接受——既是灵活性也是**隐性契约**：
   没有 schema 协商，客户端与云端对「有哪些表」没有共识。
3. **文件面是半成品**：客户端 `grep "files/blobs\|/v1/files"` 零命中，但云端已启用
   `wb.files.gc-interval-ms`（默认 6 小时）和 S3 后端；这种「有实现、无契约、还在跑定时任务」
   的状态最容易被后来的 agent 当成可用能力接进去。

### P2 · 真机上会咬人的

4. **单设备同步锁没有客户端退避**。`SyncService.open` 在另一设备持有会话时抛
   `409 sync_locked`（带 `retry_after_ms`），客户端 `index.ts:1056` 把 `sync_locked` 归到 409，
   但 `sync.ts:690,720` 只对 `version_conflict` 重试——用户会直接看到同步失败，
   而不是「稍后自动重试」。
5. **`change_log` 无保留策略**。`V1__cloud.sql` 只建了 `idx_cl_user` 与 `idx_cl_user_table_seq`，
   没有任何清理任务；`row_states` 靠 LWW 覆盖不会膨胀，`change_log` 会。
6. **推送体积只按条限制**。`MAX_PUSH_ITEMS=500`、单条 payload `MAX_PAYLOAD_BYTES=1_000_000`
   （`SyncService.java:167`），但整包没有总字节上限：最坏情况一次请求 500×1MB。
7. **认证面缺防护**。口令用 scrypt（`AuthService.hashPassword`，参数拼进
   `pass_hash` 前缀，可平滑升级，做法正确）；但**没有登录限速/失败锁定**，
   refresh token 轮换写了 `replaced_by` 却**没有复用检测后的全量吊销**。

### P3 · 结构性的、可以晚点做

8. `SyncService` 可按「协议层（会话/校验/错误码）／存储层（change_log、row_states、模式）」拆，
   但优先级低于前七项。
9. `CanonicalJson` 是 LWW 比较的基础，建议单独补一份「载荷规范化」契约文档，
   否则客户端哪天改变字段序列化顺序就会出现「看起来没改却判定冲突」。

## 5. 建议的分期

| 期 | 内容 | 验收 |
| --- | --- | --- |
| 一 | 契约测试：Testcontainers 起 PG，跑 open→push→pull→snapshot/full→close 全链路，含 409 会话锁、`version_conflict` 重试、tree 覆盖与 tombstone | `cloud/` 有可跑的集成测试；CI 里能失败 |
| 二 | 协议护栏：表名白名单（从客户端 `sync.js` 声明的 tables 生成）、推送总字节上限、`change_log` 保留 30 天 | 公告牌：未知表名返回 `unknown_table`；超限返回 413 |
| 三 | 未用面收敛：文件面要么接客户端（上传/下载/配额），要么 `wb.files.enabled=false` 并在文档标注「未接入」；`/v1/devices/{id}` 二选一 | 文档与端点一一对应，`grep` 无「有实现无调用」 |
| 四（可选） | 拆分 `SyncService`、补载荷规范化契约 | 测试仍全绿 |

## 6. 结论

当前 `cloud/` 的**同步核心与客户端契约是对齐且可用的**，重构（重写）没有收益，
风险却很高——因为它几乎没有测试。真实的债务是三条：
「没有契约测试」「有实现没人用的文件面」「协议缺护栏」。
按第 5 节一、二、三期做完，云端就从「能跑」变成「敢改」；拆分留到第四期。
