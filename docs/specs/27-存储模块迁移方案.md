# 物品管理（storage）原生插件迁移

## 定位与边界

新增 `dsh-workbench-storage` 1.0.0（最低宿主 0.5.6，SDK 0.1.1），域 id 为 `wb-addon-storage`。这是物品管理（库存文本台账）：记录名称、品牌、单位、库存文本与标签。库存保留文本语义，不推导数量、出入库账或财务余额。

本模块不实现 [17-文件存储设计](./17-文件存储设计.md) 的附件平台：没有上传、下载、字节备份、对象存储或文件同步。附件平台的 `file` / `file_link` / `file_blob` / `file_transfer` 是另一项宿主建设工作。

## 本次实现、验证与迁移边界

本次迁移的是物品管理功能代码，未连接或读取旧生产数据，未实现旧数据库自动迁移，也未进行真实云端同步联调。新建记录使用新 UUID；本地 action、同步声明和变更日志测试通过，不等于旧数据或云端链路迁移已完成。

本域导入只支持新备份 schemaVersion: 1。旧系统数字 id 与 type=2 的标签映射不能原样导入：需要另行转换为新字符串 id、item_type="storage"、新记录关联和时间戳字段，并校验引用完整性；本次没有提供该旧库转换工具。

已执行的集成验证使用隔离临时 SQLite：native 四域注册、data/config 行为、backup 全量及指定 storage 导出、记录恢复和标签映射幂等；action schema 审计通过。真实生产数据迁移与真实云端同步仍需单独验收。

## 原生插件结构

- 源码位于 `packages/addons/storage`；服务端由 `lib/index.js` 的 `apply(ctx)` 注册 DomainDef，依赖 `workbench` 服务。
- 包依赖源码宿主 `dsh-workbench`，`cordis.patch.yml` 声明宿主和 storage 行；发布时统一改写为 `dsh-workbench-host`。
- 客户端入口 `client/client.src.cjs` 经 esbuild 生成 `lib/client.js`，通过 ModuleLoader 与 `__WB_HOST__.registerAddon` 注册统计、物品、配置、数据四个视图。
- 业务 action 通过宿主 invoke 执行，复用统一的 schema 自举、能力清单、审计、事件和本地数据库。

## 数据、标签与同步

业务表为 `storage`。新记录使用字符串 id，变更时钟沿用宿主约定；删除采用 tombstone，写操作记录 `sync_change_log`，同步只声明本域的 storage 表，使用行级 LWW。

标签采用 `tag_mapping.item_type = "storage"`。依据 [25-标签域解耦审计与改造](./25-标签域解耦审计与改造.md) 的归属原则，tag/tag_mapping 属于 tags 插件，只有 tags 声明其同步绑定；storage 不重复声明同步表。无 tags 安装时仍须能运行无标签的物品台账。标签统计识别 storage 为“物品”，不得归入未知类型。

配置存储在 `meta` 的 `config.storage.*` 键；不进入业务备份、不参加云同步。数据页只允许查询 storage 业务表，不提供任意 SQL 或宿主表读取。

## 备份与恢复

通过 DomainDef 的 exportData/importData 接入宿主备份，无需在宿主内增加业务分支。宿主导出的 zip 应出现 `modules/wb-addon-storage.json`，清单记录版本；模块选择支持只导出 storage。导入沿用 newest / skip / overwrite 策略。备份保留已删除状态，恢复必须写变更日志，使其他设备能够看到恢复结果。

storage 声明 `backupAfter: ["wb-addon-tags"]`。宿主 0.5.6 在导入前按域声明做稳定依赖排序，每轮选择原清单中最早的可执行模块；不依赖插件安装顺序，也不信任备份清单碰巧已有正确顺序。清单中不存在的依赖不阻塞调度，循环依赖在任何模块写入前拒绝；依赖模块失败仍按原有机制汇总，各域负责引用完整性校验。

`scripts/test-backup.mjs` 先安装 storage，并将其置于待恢复清单最前；清空 storage、tag_mapping、tag 后，统一导入恢复物品、标签及唯一有效映射。另覆盖依赖循环零写入拒绝，以及清单缺少可选依赖的兼容行为。tags 1.6.6 的备份不再重复导入导出 site/storage 映射，由各业务域负责；storage schemaVersion 1 可附带 tagReferences（id/name），用于恢复时将旧标签 id 解析到同名标签。storage 单模块备份仍不能替代标签数据备份：映射恢复需要目标库已有可解析的对应标签。

## 构建、安装与发布集成

1. `scripts/build-addon-clients.mjs` 和 `scripts/audit-actions.mjs` 的插件清单加入 storage。版本检查覆盖包版本、wb.addon.version、服务端、客户端源码和生成物。
2. `scripts/stage-release.mjs` 生成第五个包 `dist/release/packages/storage` 以及独立市场 YAML；重写 dependencies、client.inject 和 patch 中的宿主名。
3. `scripts/publish-npm.mjs` 发布顺序为 host → tasks → tags → sites → storage；GitHub 发布镜像版本清单也包含 storage。构建与生成发布树不等于已经发布到 npm 或市场。
4. 本地先 `pnpm build && node scripts/dist-shell.mjs`，再安装完整 `packages/addons/storage` 包到临时 profile，重启后核对 capabilities 中的版本、actionCount 和页面。不要只复制一部分 lib 文件，也不要重启正在使用的主实例。
5. workspace 的 addons 通配符、宿主通用域注册/备份/同步绑定和行数审计已有通用能力，不需要为 storage 额外硬编码。

## 验收入口

`pnpm test:storage` 覆盖业务动作、标签、备份与本地同步日志等本域契约。统一入口 `test:native`、`test:clients`、`test:backup`、`test:data`、`test:config` 纳入 storage；`test:e2e` 包含 storage 测试。

验收包括：无标签独立加载、四视图注册、schema 与实现一致、创建/查询/编辑/软删除闭环、分页排序过滤、只读数据查询边界、配置重置、标签统计识别、全量/选择备份以及恢复。发布前运行 `pnpm build`、`node scripts/audit-actions.mjs`、`node scripts/audit-lines.mjs` 和相关测试，再在临时 profile 验证完整安装。
