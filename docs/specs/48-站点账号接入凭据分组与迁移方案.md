# 48 · 站点账号接入凭据分组与 D7 迁移方案

> 状态：设计稿（待评审，**不动代码**）· 2026-11-13
> 前置：[46 连接器与凭据保险箱方案](46-连接器与凭据保险箱方案.md) §7.9/§7.10、[47 0.2.0 复盘](47-凭据保险箱0.2.0复盘.md)、[22 站点模块迁移二期](22-站点模块迁移二期.md) §3
> 目标：把站点账号的三个敏感字段迁进 `wb-addon-vault`，站点改为「按组授权」，最终只保留一套保险箱口令。

## 1. 要解决的问题

现状是两套保险箱：

| | sites 自带（1.10.0） | vault 0.2.0 |
| --- | --- | --- |
| 表 | `meta` 存 `sites.vault.salt` / `sites.vault.verifier`，密文在 `site_account.password/phone_number/identity_card` | `vault_header` / `vault_secret` / `vault_group` / `vault_binding` |
| 密钥 | 口令 → scrypt(N=32768) → key，仅内存；HMAC 校验口令 | 口令 → scrypt(N=65536) → KEK → 包 DEK；`wrapped_dek` 落库 |
| 密文 | `v1:iv:tag:ct`，**无 AAD** | `v1:iv:tag:ct`，AAD=`vault:<id>:<name>:<kind>` |
| 口令下限 | 8 位 | 12 位 |
| 同步 | `site_account` 行级同步密文 | 5 张表同步，device/usage 留本机 |
| 明文出口 | `sites.accounts.get`（ui+解锁）/ `reveal`（仅 ui） | `secretReveal`（仅 ui）/ `lease`（仅 plugin） |

结果：用户要记两个口令；同一段明文可能同时出现在两个域；sites 无法利用「一个对象关联一组凭据」的能力。

## 2. 目标与非目标

**目标**

1. 站点账号的敏感字段只以 vault 密文存在，sites 行不再存密文；
2. 站点通过 `vault_binding(subject_type='site', subject_id=site.id)` 关联一个或多个凭据组，不再逐条绑定；
3. 站点侧仍保持「agent 永远拿不到明文」，明文只在 UI + 解锁时返回；
4. 迁移可重入、可验证、保留一个版本的回滚窗口。

**非目标**

- 不移除 sites 的 `sites.*` action 面（只改内部实现）；
- 不改 vault 的加密格式（AAD 不含 group，见 47 号复盘风险）；
- 不做站点之外的对象迁移（连接器已经在用 vault，邮件同理）。

## 3. 方案对比

| 方案 | 做法 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- | --- |
| A. 只加引用，不迁密文 | sites 继续内联加密，另外用 `vault.bind` 关联已有 vault 组 | 改动最小，1 天 | 两套保险箱原样保留；同一账号的密码在 sites、token 在 vault，用户要开两次锁；没解决根因 | 不采用 |
| **B. 完全迁移（推荐）** | 敏感字段 → `vault_secret`；sites 行只留 `account/account_key/remark`；`site_account` 三列清空并停写；`sites.vault.*` 改为委托 vault 的兼容层 | 一套口令、一套密文、一套备份口径；站点按组授权成立 | 需要迁移工具、旧端门禁、回滚窗口；sites 变硬依赖 vault | 采用 |
| C. 双写过渡 | 写 sites 与 vault 两处，读优先 vault | 回滚容易 | 两套真值，任何一侧失败都会分叉；锁态不同步会写出半套 | 不采用 |

## 4. 目标数据模型

### 4.1 分组粒度

- **默认：每个站点一个组**，组名 `站点：<site_name>`（重名加 `#n`），`vault_group.id` 由 vault 生成。
- 组内每条凭据 = 一个账号的一个字段：
  - `name` = `site.<siteId>.<accountKey>.<field>`（≤80 字，超长截断并加短哈希），
  - `kind` = `password`（密码）/ `other`（手机号、身份证，用 `meta.field` 区分），
  - `meta` = `{siteId, accountId, accountKey, field, account}`，`account` 是该账号登录名（非敏感，便于识别）。
- `vault_binding`：`(subject_type='site', subject_id=site.id, group_id=<该站组>)`，一个站点默认一条绑定。
- 需要更细授权时，用户可另建组（如「支付凭据」）并额外绑定到同一站点——多绑定天然支持，不需要改代码。

> 为什么不按账号建组：用户的原话是「site 按组关联多个凭据，不用逐条绑定」；站点级授权粒度最自然。若按账号建组，站点要绑定 N 条，等于逐条绑定换个说法。

### 4.2 sites 侧保留什么

| site_account 列 | 迁移后 |
| --- | --- |
| `account`（登录名） | 保留明文（非敏感） |
| `account_key` | 保留 |
| `password` / `phone_number` / `identity_card` | **清空为 `''`**，停止写入 |
| `remark` / 外联关系 | 保留 |

新增本机表（sites 域，不同步）：

```sql
CREATE TABLE IF NOT EXISTS site_vault_migration (
  account_id  TEXT PRIMARY KEY,
  site_id     TEXT NOT NULL,
  group_id    TEXT NOT NULL,
  state       TEXT NOT NULL,           -- pending / partial / done
  secret_ids  TEXT NOT NULL DEFAULT '[]',
  error       TEXT NOT NULL DEFAULT '',
  updated_at  INTEGER NOT NULL
);
```

用途：断点续跑与审计。真正的授权关系仍在 `vault_binding`，这张表只是迁移进度，不参与同步。

## 5. 迁移流程（UI 编排，可重入）

**硬约束**：vault 的 `setup/unlock/changePassphrase/secretCreate/secretUpdate` 都是 **仅 ui origin**；sites 插件以 `plugin` 身份调用 vault 时只能 `bind/unbind/subjectSecrets/lease`。跨插件也没有共享事务（各自 db 连接、各自事务）。所以迁移必须由 UI 逐条编排，且每一步幂等。

```
前置：sites 已升级到 1.11.0；vault ≥0.2.0 已安装；用户已备份
① UI: vault.status → 未初始化则 setup（口令 ≥12，提示密文上云）
② UI: sites.vault.status → 未解锁则 unlock（输入旧 sites 口令）
③ UI: sites.accounts.list 全量 → 逐账号：
   a. sites.accounts.reveal(id)            # 已有 action，仅 ui，返回三字段明文
   b. vault.bindingsOf(site)               # 无绑定则先 groupCreate + bind
   c. vault.secretList(groupId) → 按 name 决定 secretCreate 还是 secretUpdate
   d. 写入 site_vault_migration(state='done', secret_ids)
   e. sites.accounts.migrateFinalize(id)   # 新 action：清三列 + 校验数量
④ 全部 done → sites.meta['vault.migrated']=1；sites 读路径切 vault
⑤ 验证：随机抽 3 条 secretReveal 与迁移前明文比对（内存比对，不落日志）
⑥ 保留 sites.vault.salt/verifier 与 site_account 旧密文 1 个版本（回滚窗口）
```

- 中断处理：`state='partial'` 的账号重跑时按 `name` 查 `secretList`，存在则 update、不存在则 create；`migrateFinalize` 只在该账号所有字段都成功后才执行。
- 明文只在 UI 进程内存里存在一次请求的生命周期内；不写日志、不进 `logChange`、不进 SSE。
- 迁移期间 sites 与 vault 两个密码都可能被打开：UI 必须显示「迁移中：先不要关闭窗口」。

## 6. 迁移后的读写路径

| 场景 | 实现 |
| --- | --- |
| 账号列表 | `sites.accounts.list` → 调 `vault.bindingsOf` + `vault.subjectSecrets`（plugin origin，已允许）拼 `hasPassword/hasPhone/hasIdentity`；不再解 sites 密文 |
| 查看明文 | `sites.accounts.get`（ui+unlocked）→ 内部改为 `vault` 的 reveal 路径。**需要新增 plugin 可用的读接口**，见 §6.1 |
| 新增/修改账号 | 写 `site_account` 非敏感列；敏感字段由 UI 在同一次操作里调 vault 写入（`secretCreate/Update`，仅 ui） |
| 删除账号 | `sites.accounts.delete` 软删 + `vault.unbind`/`vault.secretDelete`（UI 编排，两步） |
| agent | 一律掩码；`sites.accounts.get` 在 agent origin 下保持 `masked:true`，不触达 vault 明文 |

### 6.1 关键取舍：要不要给 vault 加「plugin 写」能力

迁移后 sites 的**写入**要么由 UI 二次调用 vault（前端编排，简单，但 `sites.accounts.create` 自身不再原子），要么给 vault 增加一个受 binding 约束的 plugin 写接口：

```
vault.pluginSecretUpsert(subjectType, subjectId, name, kind, secret, meta)
  仅 plugin；先校验 subject 已绑定 group 且 group 存在；只允许写该组
```

| | UI 编排 | pluginSecretUpsert |
| --- | --- | --- |
| 原子性 | 两步，中途失败留半套（需补偿） | 仍跨两个 action，但写入点集中 |
| 权限面 | 不扩大（secretCreate 本来就 ui） | **扩大**：任何已绑定插件可写自己组的凭据 |
| 迁移 | 必须 UI 编排 | 可全在 sites 内完成（仍需 UI 触发） |
| 风险 | 前端遗漏调用 → 静默丢字段 | 插件可覆盖同组凭据；需要审计与 origin 白名单 |

建议：**先 UI 编排**（P1–P3），`pluginSecretUpsert` 作为 P4 可选项单独评审；不在这轮引入新的 plugin 写权限。

## 7. 同步、备份与旧端

### 7.1 同步

- `site_account` 继续 row 同步，但三列恒为空 → 云端不再有站点密文；
- vault 的五张表同步密文（0.2.0 已实现）；
- **旧端防护**：sites 的 `siteSync` 给 `site_account` 加 `normalizeIncoming`：本机 `vault.migrated=1` 时，把远端行里的 `password/phone_number/identity_card` 一律置 `''`，避免旧客户端（1.10.x）同步回来的密文复活；
- `vault_subject_type` / `vault_binding` 需要在站点删除时清理：`sites.delete` 增加 `vault.unbind`（UI 编排或 P4 的 plugin 接口）。

### 7.2 备份（必须先定）

现状事实：`packages/addons/sites/lib/infra/backup.js:101-115` 的导出只有 `sites / nodes / nodeMappings / tagMappings`，**根本没有 `site_account`**（与 22 号文档 §8 的「备份包含这两张表」不一致）。也就是说：

- 迁移前：账号本来就不在备份里，靠同步；
- 迁移后：密文只在 vault，而 vault 备份**不导密文** → 凭据不在任何备份产物中。

三选（建议 ③ 先行）：

1. 明示「备份不含凭据，换机靠同步」——最省事，但用户可能真的丢；
2. 增加 `vault.exportEncrypted`（ui-only），导出 header + 密文 + group/binding 的 JSON，带「可离线爆破」警告；
3. 迁移期保留 `site_account_legacy` 快照表（旧密文 + 旧 salt/verifier），一个版本后删除，同时把 sites 备份补上该表。

### 7.3 旧端与版本门禁

- sites 升 1.11.0，`schema_version` +1；`vault.migrated=1` 后拒绝 `sites.vault.setup/rekey`（避免旧口令体系复活）。
- 1.10.x 客户端仍会读写 `site_account.password`：迁移完成后它们显示「未填写」，若用户在新旧端同时编辑，旧端写入的密文会被 §7.1 的 `normalizeIncoming` 清掉（但旧端本地仍可见，属于已知不一致）。发布说明必须写「迁移后不要回退版本」。

## 8. 回滚方案

- 回滚窗口内保留：`sites.vault.salt/verifier`、`site_account` 旧密文（已被清空，所以实际需要在 `site_account_legacy` 里留一份，见 §7.2 选项 3）。
- 新增 `sites.accounts.migrateRollback`（ui）：逐条 `vault.secretReveal`（ui）→ 用 sites 旧密钥重新 `encryptField` → 写回 `site_account` 三列 → 清 `site_vault_migration` 与 `vault.migrated`。
- 回滚要求 sites 保险箱仍能解锁；若用户已忘记 sites 口令，回滚不可行（迁移前必须先确认旧口令可解锁）。

## 9. Action 变更清单

| action | 域 | origin | 说明 |
| --- | --- | --- | --- |
| `sites.accounts.migrateFinalize` | sites | ui | 清空该账号三列 + 校验 vault 侧凭据齐全；幂等 |
| `sites.accounts.migrateRollback` | sites | ui | 反向迁移（窗口期内可用） |
| `sites.vault.status/setup/unlock/lock/rekey` | sites | ui | 改为兼容层：读写转发到 vault（`sites.vault.*` 保留，避免客户端大改） |
| `sites.accounts.get/reveal` | sites | ui | 迁移后改为从 vault 读取；agent 仍掩码 |
| `sites.accounts.list` | sites | ui/agent | 增加 `hasPhone/hasIdentity`；`hasPassword` 改由 vault 计算 |
| `vault.secretCreate/Update/Delete` | vault | ui | 不变（迁移由 UI 调用） |
| `vault.bind/unbind/bindingsOf/subjectSecrets` | vault | plugin | 不变；sites 以 plugin 身份调用 |

## 10. 分期与验收

| 阶段 | 内容 | 验收 | 估时 |
| --- | --- | --- | --- |
| P0 | 本文评审通过，更新 46 号文档 D7 为「迁移执行中」 | 用户确认 §7.2、§6.1 | — |
| P1 | sites 读路径切 vault（list/get/reveal）+ `sites.vault.*` 兼容层 | 未迁移库不受影响；迁移库 agent 仍掩码 | 2d |
| P2 | 迁移工具（UI 编排 + `site_vault_migration` + finalize） | 断点续跑、全量比对、失败可重试 | 3d |
| P3 | 写路径切换 + `normalizeIncoming` 旧端防护 + 站点删除清理 binding | 新旧端同时在线不复活密文 | 2d |
| P4 | 回滚工具 + 备份策略落地 | 迁移→回滚→再迁移，明文一致 | 2d |
| P5 | 真机双设备验证 | B 设备仅凭 vault 口令解锁并读到同一批凭据 | 1d |

测试矩阵（追加到 `scripts/test-sites.mjs` 与 `pnpm test:vault`）：

1. 迁移 fixture：2 站点 / 3 账号 / 三字段齐全，迁移后 `site_account` 三列为空、`vault_secret` 数量 = 字段数；
2. 幂等：第 2 个账号写入时注入失败 → `state='partial'` → 重跑补齐，不产生重复 secret；
3. 授权：站点 A 的 binding 不能 lease 站点 B 的 secret；
4. 旧端：模拟远端带回密文的 `site_account` 行 → `normalizeIncoming` 清空；
5. agent：迁移后 `sites.accounts.get` 仍 `masked:true`，`vault.lease` 需带 subject 且绑定匹配；
6. 回滚：回滚后旧 sites 口令可解出原值，`vault_secret` 仍保留（不删）；
7. 跨设备：设备 B 同步后用同一 vault 口令解锁并读到密文。

## 11. 风险

| 风险 | 对策 |
| --- | --- |
| 迁移中途关窗/崩溃 | 每账号 state 落库，按 name 幂等重跑 |
| 忘记 sites 旧口令 | 迁移前置检查：必须解锁成功才允许开始 |
| 新旧端并发写 | `normalizeIncoming` + 发布说明「迁移后不要回退版本」 |
| 凭据不再进备份 | §7.2 先落 `site_account_legacy` 快照，后续再加加密导出 |
| binding 悬空 | 删除站点/账号时同步 `vault.unbind` + 周期性 `bindingPurge` |
| 口令不统一（sites 8 位 vs vault 12 位） | 迁移时强制设置合规 vault 口令，旧口令只用于解密一次 |
