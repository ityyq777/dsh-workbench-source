# 20 · 配置表与配置页设计（任务 / 标签 / 站点）

> 状态：设计草案（2026-11-08），待评审后实施。
> 目标版本：tasks `2.7.0`、tags `1.5.0`、sites `1.6.0`；宿主不变（仍 `0.5.2`）。
> 关联：[03-UI设计](./03-UI设计.md)、[04-子插件体系](./04-子插件体系.md)、
> [05-本地存储设计](./05-本地存储设计.md)、[15-数据备份](./15-数据备份.md)、
> [16-数据同步方案](./16-数据同步方案.md)、[18-统计报表设计](./18-统计报表设计.md)。

## 0. 一句话结论

每个业务插件新增一张 `<域>_config` 表（`id` + `value`），只存**用户改过的覆盖项**；
服务端用一份带类型的白名单 schema 做校验与默认值兜底；客户端新增第三个「配置」视图，
按分组把这些值渲染成开关/下拉/多选/数字；列表页、统计页、新建表单在挂载时读取配置。
配置随备份与同步走（行级 LWW），但不承担权限或安全语义。

## 1. 问题与目标

### 1.1 现状盘点

三个插件的可调参数目前散落在三处：客户端常量、服务端常量、统计代码里的写死阈值。
改一个分页数要改代码、重新构建客户端 bundle；用户没有任何入口。

用户无法隐藏不关心的部分（例如不用标签的人不需要「标签 × 状态」堆叠图）。

### 1.2 目标

1. **每个插件一张配置表**，`id` 是配置项、`value` 是配置值；值用 JSON 文本承载，
   可以是一个标量，也可以是一个数组或对象，不为每种类型加列。
2. **每个插件多一个「配置」视图**，与「统计」「记录」并列；页面由服务端下发的
   schema 驱动，不在客户端硬编码表单。
3. **只存覆盖项**：默认值留在代码里。升级新增配置项时不需要迁移，用户没改过就自动
   使用新默认值；「恢复默认」= 删掉那一行。
4. **可审计、可自动化**：配置读写走三个 action，agent 也能读能改，变更进
   `sync_change_log`。
5. **不打断现有链路**：备份、同步、卸载、老库升级都要有明确行为，不能因为多一张表
   把导入导出弄坏。

### 1.3 非目标

- 不做通用表单引擎 / 任意字段扩展（`id` 必须命中白名单）。
- 不做远程配置中心：配置只在本机 SQLite，靠既有同步多端一致。
- 不做按用户/按设备的偏好分层：一个工作台数据库一份配置（见 §15 开放问题 1）。
- 不把主题、语言、字号这类宿主级偏好搬进业务插件。
- 不开放分页上限（200）、必填校验、URL 合法性这类**数据完整性**约束。
- 不为了配置化而改 action 的入参契约；agent 显式传参永远优先于配置默认值。

## 2. 设计决策

| # | 决策 | 理由 | 代价 |
| --- | --- | --- | --- |
| D1 | 每个域各一张 `<域>_config` 表，不建宿主公共配置表 | 与现有「域自带表 + 域自带备份 + 域自带同步」一致；卸载插件不残留别人的数据 | 三个包各复制一份 `lib/config.js` 骨架（与 `charts.cjs` 同策略） |
| D2 | 只存覆盖项（overrides-only），不落默认值 | 默认值随版本演进；升级不需要数据迁移；「恢复默认」语义天然 | 读配置要合并默认值；手工看库看不出全貌（用 `configGet` 看） |
| D3 | `value` 存 JSON 文本，不拆多列 | 一个 `sections: ["kpi","trend",...]` 数组、一个 `{}` 对象都不用加列；SQLite 侧无需 JSON1 也能读 | 排序/比较只能在应用层做；需要大小上限 |
| D4 | 服务端白名单 schema 是唯一事实源，写入时校验 | agent 也会写，客户端校验不能当数；UI 文案也从 schema 来 | schema 要写两语文案，比纯客户端常量啰嗦 |
| D5 | 配置项分 `surface = ui / api` 两个生效面 | 用户偏好不该悄悄改变 agent 调 action 的结果：只有确实改变数据/校验的项才进服务端读取路径 | 每个配置项要想清楚归属，不能一股脑塞给服务端 |
| D6 | 「恢复默认」= 软删行（`deleted_at` 非空），不写回默认值 | 同步能表达「这里改回默认了」；默认值以后调整还能跟随 | 表里会留墓碑行（几十行量级，无所谓） |
| D7 | 配置表参与备份与同步（row 级 LWW） | 换设备/恢复备份后不用重设 | 备份 `schemaVersion` 升到 2，要兼容 v1 导入 |
| D8 | 配置视图排在「统计」「记录」之后 | 不改变既有默认落地页（统计）和肌肉记忆；[18 §17](./18-统计报表设计.md) 的页签约定扩为三段 | 首页卡片多一个 tab，无功能影响 |
| D9 | 写入即时生效、即时落库，不做「脏草稿 + 保存」 | 三个视图切换即卸载（宿主只渲染 `activeView.component`），草稿很容易在切页时丢；即时保存的交互成本更低 | 没有批量撤销；靠逐项「恢复默认」兜底 |
| D10 | 不缓存配置 | 配置量 < 30 行，读一次是全表扫描；缓存只会引入失效问题（agent 写入不经过 UI） | 每次 action 多一次查询（微秒级） |

## 3. 数据模型

### 3.1 表结构

表名：`task_config` / `tag_config` / `site_config`（与域前缀一致）。

```sql
CREATE TABLE IF NOT EXISTS task_config (
  id         TEXT PRIMARY KEY,   -- 配置项 id，如 list.pageSize
  value      TEXT NOT NULL,      -- JSON 文本：12 / "30d" / ["kpi","trend"] / {...}
  rev        INTEGER NOT NULL DEFAULT 1,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  deleted_at INTEGER             -- 非空 = 已恢复默认（墓碑，供同步传播）
);
```

- 不加索引：行数 < 30，主键查询 + 全表扫描都够。
- 列顺序与 `task_dep` 一致，`rowToObject` 之类的通用工具可直接复用。
- DDL 由 `lib/config.js` 的 `CONFIG_DDL` 导出，在 `setup` 里紧跟 `ensureSchema` 执行：
  `ensureSchema(db)` → `ensureConfigSchema(db)` → `registerTaskActions(api)` →
  `registerConfigActions(api)`。
- `loadConfig` 先 `tableExists(db, "task_config")`，缺表时返回全默认值并记一条 warning，
  保证老库、单测里只调 `ensureSchema` 的场景不会炸。

### 3.2 列语义

| 列 | 语义 | 备注 |
| --- | --- | --- |
| `id` | 配置项标识 | 白名单键，见 §3.3；同时是主键与行级同步的 `uniqueKeys` |
| `value` | 规范化后的 JSON 文本 | `JSON.stringify(normalized)`；不做 pretty print |
| `rev` | 行版本 | 每次写入 +1；与其它业务表一致 |
| `created_at` | 首次设置时间 | 恢复默认再设置不会重置它（更新时保留） |
| `updated_at` | 最后写入时间（ms） | 冲突 LWW 的比较字段 |
| `deleted_at` | 恢复默认时间 | `configGet` 视同不存在；再次设置时清空 |

### 3.3 键名规范

- 形式 `<group>.<name>`，全小写开头的驼峰，例如 `list.pageSize`、`stats.weekStartsOn`。
- `group` 只用于配置页分组与批量重置，固定为 `list` / `form` / `stats` / `behavior`
  （标签另有 `create`）。
- 键名一旦发布**不再改名**（改名等于丢用户设置）。废弃走 `deprecated: true`：
  保留在 schema 里、`configGet` 仍返回（带标记）、`configSet` 拒绝、UI 不渲染。
- 正则兜底：`^[a-z][a-zA-Z0-9]*\.[a-zA-Z][a-zA-Z0-9]*$`；真正的准入仍靠白名单。

### 3.4 值编码

| schema `type` | 存储 | 规范化 |
| --- | --- | --- |
| `bool` | `true` / `false` | 只接受布尔 |
| `int` | 整数 | `Math.round` 后夹在 `[min,max]`；越界直接报错，不静默夹取 |
| `number` | 数字 | 校验有限数、`step` 对齐（0.5 的倍数） |
| `enum` | 字符串或数字 | 必须是 `options[].value` 之一，保持原类型 |
| `multi` | 数组 | 去重、剔除未选项、按 `options` 顺序重排；空数组合法 |
| `string` | 字符串 | 去首尾空白；`maxLength`；`ref` 只做 UI 提示，服务端不校验引用存在性 |
| `json` | 任意 JSON | 仅用于确实无法枚举的结构；`JSON.stringify` 后 ≤ 8KB |

硬限制：单值序列化后 **≤ 8192 字节**；`multi` ≤ 32 项；字符串 ≤ 512 字符
（`create.maxNameLength` 这类另有 `maxLength`）。超限报错而不是截断。

### 3.5 生命周期

```
默认（无行）
  └─ configSet(id, v) ──► 有行，deleted_at=NULL，rev+1
        └─ configSet(id, null) / configReset ──► 墓碑行，deleted_at=now，rev+1
              └─ 再次 configSet ──► 复活同一行，rev+1，created_at 不变
```

- `configSet` 写入与当前**有效值**相同的值时视为 no-op：不写行、不 bump `rev`、
  不写变更日志（避免同步噪音）。
- 所有写操作在一个 `tx()` 事务里完成；批量 patch 里任何一项校验失败 → 整批回滚。

### 3.6 与同步

`lib/sync.js` 各加一行：

```js
{ name: "task_config", mode: "row" }
```

- 行级 LWW，冲突粒度 = 整条配置项；两个设备同时改不同项互不影响，改同一项后写者胜。
- 写入走 `logChange(db, "task_config", id, "upsert", row, origin, ts)`；
  `origin === "sync"` 时不写日志（现有 `logChange` 已保证）。
- 墓碑行参与同步，所以「A 设备恢复默认」能传到 B 设备；B 设备若同时设置了新值，
  按 `updated_at` 决出胜负。
- 老版本客户端/对端不认识 `*_config` 表：同步协议按表名声明，未声明的表不会被推送，
  升级后自动开始同步，无需协商。

### 3.7 与备份

`lib/backup.js`：

- `SCHEMA_VERSION` 由 `1` 升到 `2`。
- 导出增加一段：`config: [{ id, value, rev, updatedAt, deletedAt }]`（只导出有效行，
  墓碑不导出——导出语义是「当前配置」）。
- 导入接受 `schemaVersion ∈ {1, 2}`：v1 数据没有 `config` 字段，跳过配置导入并提示
  「旧备份不含配置，已保留当前配置」；v2 按同一 `policy`（`skip|overwrite|newest`）
  逐行写入，配置行也走 LWW。
- 导入前先 `ensureConfigSchema`，避免在空库上导入时缺表。

### 3.8 规模与性能

- 单域配置项上限按 40 个设计（当前草案 21 / 15 / 20），全表 < 10KB。
- `configGet` 一次全表读 + 合并默认值，O(n)，无可感知开销。
- 统计页每次 `statsReport` 会多一次配置读取（同一个 `db` 句柄），可忽略。

## 4. 服务端契约

### 4.1 配置项描述符

`lib/config.js` 里每个插件维护一份 `CONFIG_SPEC`：

```js
export const CONFIG_SPEC = {
  version: 1,
  groups: [
    { id: "list", label: { zh: "列表与分页", en: "List & paging" } },
    { id: "form", label: { zh: "新建与完成", en: "Create & complete" } },
    { id: "stats", label: { zh: "统计页", en: "Stats" } },
    { id: "behavior", label: { zh: "自动化", en: "Automation" } },
  ],
  items: [
    {
      id: "list.pageSize",
      group: "list",
      type: "enum",
      surface: "ui",
      apply: "mount",
      default: 12,
      options: [6, 12, 24, 48].map((n) => ({ value: n, label: { zh: n + " 条", en: String(n) } })),
      label: { zh: "每页条数", en: "Page size" },
      help: { zh: "只影响分页页签（已关闭/已开启/已完成/总览）。", en: "Applies to paged tabs only." },
    },
    // ...
  ],
};
```

字段说明：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✓ | 全局唯一键，见 §3.3 |
| `group` | ✓ | 必须是 `groups[].id` |
| `type` | ✓ | `bool/int/number/enum/multi/string/json` |
| `surface` | ✓ | `ui`：只被客户端读取；`api`：服务端读取并影响结果/校验 |
| `apply` | ✓ | `mount`（切换到该视图时读取）/ `live`（订阅事件即时重渲染）/ `api`（每次调用读取） |
| `default` | ✓ | 与 `type` 匹配；`multi` 为数组 |
| `label` / `help` | ✓ | `{zh, en}`；配置页直接展示，缺 en 时回退 zh |
| `options` | enum/multi | `[{value, label:{zh,en}}]`；value 允许数字或字符串 |
| `min` / `max` / `step` | int/number | 闭区间；`step` 缺省 1 |
| `maxLength` | string | 缺省 512 |
| `ref` | string | `table` / `node` / `tag`，仅用于配置页渲染选择器 |
| `deprecated` | 可选 | 为 true 时不渲染、不可写，读仍返回 |
| `since` | 可选 | 引入版本，便于文档/迁移判断 |

### 4.2 action 定义

三个 action 都注册在各自域下（`tasks.configGet` / `tags.configGet` / `sites.configGet`）。

#### `configGet`

```json
{ "type": "object", "properties": {}, "additionalProperties": false }
```

返回（顺序即配置页渲染顺序）：

```json
{
  "version": 1,
  "groups": [{ "id": "list", "label": { "zh": "列表与分页", "en": "List & paging" } }],
  "items": [
    {
      "id": "list.pageSize",
      "group": "list",
      "type": "enum",
      "surface": "ui",
      "apply": "mount",
      "value": 12,
      "isDefault": true,
      "default": 12,
      "options": [{ "value": 6, "label": { "zh": "6 条", "en": "6" } }],
      "label": { "zh": "每页条数", "en": "Page size" },
      "help": { "zh": "…", "en": "…" }
    }
  ],
  "warnings": []
}
```

- `value` 永远是**有效值**（有行取行，无行取默认）。
- `isDefault` 用于 UI 显示「恢复默认」按钮；等价于「无有效行」。
- `warnings` 收集：表缺失、JSON 解析失败、值校验失败（回退默认）等；不阻塞返回。

#### `configSet`

```json
{
  "type": "object",
  "properties": {
    "patch": {
      "type": "object",
      "additionalProperties": true,
      "description": "id → 新值；null 表示恢复该项默认（软删）"
    }
  },
  "required": ["patch"]
}
```

- 返回与 `configGet` 同构（应用后的完整快照），客户端可直接替换本地状态。
- 校验顺序：patch 是否为对象 → 每个 id 是否存在/是否 deprecated → 类型 → 范围/枚举 →
  大小 → 规范化。第一处失败即抛错，整批不落库。
- 值未变化时不写行（§3.5），但仍返回快照。
- `origin` 由宿主注入（`ui` / `agent`），进变更日志。

#### `configReset`

```json
{
  "type": "object",
  "properties": {
    "ids":   { "type": "array", "items": { "type": "string" } },
    "group": { "type": "string" },
    "all":   { "type": "boolean" }
  }
}
```

- `ids` / `group` / `all: true` 三选一，都不给报错。
- 语义都是软删（墓碑）；已经是默认的项跳过，不产生空写入。
- 返回应用后的完整快照。

### 4.3 错误文案

宿主把 `execute` 抛出的 `Error.message` 原样放进 HTTP 500 的 `error` 字段，
所以文案要能直接给用户看，并带上出错的配置项 id。

| 条件 | 文案 |
| --- | --- |
| patch 不是对象 | `config.patch 必须是对象` |
| 未知配置项 | `未知配置项：list.pageSizeX` |
| 已废弃 | `配置项已废弃：xxx` |
| 类型不符 | `list.pageSize 必须是整数` |
| 枚举越界 | `list.pageSize 只能是 6、12、24、48` |
| 数值越界 | `stats.top 必须在 1–20 之间` |
| 多选含未知项 | `stats.sections 含未知区块：foo` |
| 超长/超大 | `stats.sections 超出单值 8KB 上限` |
| reset 参数缺失 | `configReset 需要 ids、group 或 all 之一` |
| group 不存在 | `未知配置分组：xxx` |

### 4.4 生效面（surface）

这是本设计里唯一需要逐项判断的地方。规则：

- **`ui`（默认）**：只影响本机界面。客户端读取，服务端从不读。agent 调
  `tasks.list` 时不会因为用户把每页设成 48 而改变返回条数。
- **`api`**：改变服务端返回结果或校验规则，服务端每次调用读取。例如
  `stats.weekStartsOn`（周起始影响趋势分桶）、`tags.stats.staleDays`（沉睡清单）、
  `tags.create.maxNameLength`（校验）、`sites.form.maxLinks`（校验）。
- 判断口诀：**「换个 agent 来调用，这个默认值还合理吗？」** 合理 → `ui`；
  不合理（结果会变、会误判）→ `api`。统计类因为「用户看的是同一张报表」，
  所以 `weekStartsOn`、`staleDays` 归 `api`，而 `sections`、`top` 归 `ui`。

`api` 项的读取点：

| 配置项 | 读取位置 |
| --- | --- |
| `stats.weekStartsOn` | 各 `lib/stats.js` 的 `resolveRange`，把 `weekStartsOn` 放进返回的 `range`，`bucketKeys` / `bucketOf` 用它 |
| `stats.staleDays` | `tags/lib/stats.js` 的 `staleBefore` 计算；`sites/lib/stats.js` 的新鲜度分桶与 `stale` 清单 |
| `stats.duplicateLimit` | `sites/lib/stats.js` 的重复 URL 分组截断 |
| `tags.create.maxNameLength` | `tags/lib/tags.js` 的 `MAX_NAME` 校验（`create` / `update` / `rename`） |
| `sites.form.maxLinks` | `sites/lib/sites.js` 的链接数量校验（当前无上限，新增） |
| `tasks.behavior.autoCreateTags` | `tasks/lib/tagging.js` 的 `ensureTagsByNames` 调用点（新建任务时的自动建标签） |

### 4.5 事件

写配置成功后 `api.emit("<domain>-config-changed", { ids, origin })`：

- `tasks-config-changed` / `tags-config-changed` / `sites-config-changed`。
- 配置页自己不用订阅（它持有返回快照）；统计页、列表页订阅后重取数据，
  用于 `apply: "live"` 的项（例如 `stats.sections` 在统计页仍打开时不应变，但
  如果宿主将来保留挂载，也不会读到旧值）。
- 事件不携带完整配置，避免把大 JSON 塞进事件总线。

新增 `lib/config.js`（每个包一份，结构与 `client/charts.cjs` 的复制策略一致）：

### 4.7 读取约定

- 一次 action 只读一次配置：`const cfg = loadConfig(db);` 然后把需要的值取出来往下传，
  不在循环里反复查库。
- `api` 项在服务端读取时**只在入口读一次**，不要读「已保存但未生效」的中间态
  （不存在这种状态，因为写入即提交）。
- `statsReport` 的签名不动：`statsReport(db, args)` 内部自己 `loadConfig`，
  避免改测试与其它调用点。

### 5.3 控件映射

| type | 控件 | 说明 |
| --- | --- | --- |
| `bool` | 开关（checkbox 样式化） | 立即写入 |
| `enum` | `<select>` | 选项文案取 `options[].label[lang]` |
| `int` / `number` | `<input type=number>` + 失焦/回车提交 | 本地先夹到 `min/max`，提交仍由服务端校验 |
| `multi` | 复选组（≤ 8 项）或「多选下拉 + 已选标签」（> 8 项） | 顺序按 `options`，不提供拖拽排序（v1） |
| `string` + `ref` | `<select>`，候选来自现有 action | `table` → `taskNodes.tree` 的 type=1 节点；`node` → `sites` 的 `siteNodes.tree`；`tag` → `tags.list` |
| `string` 无 ref | `<input type=text>` | 失焦提交 |
| `json` | `<textarea>` + 提交时 `JSON.parse` | 解析失败就地报错，不发请求 |

`multi` 的空数组表示「全不展示」，要允许；「全部展示」= 勾满。两者语义不同，
UI 用「全选 / 清空」两个快捷按钮表达。

### 5.4 状态机

```
loading ──configGet 成功──► ready
   │                          │
   └──失败──► degraded（用代码内默认值渲染，顶部黄条提示，控件禁用）
                              │
         控件变更 ──► saving（控件禁用 + 行尾 loading）
                              ├─ 成功 ──► ready（用返回快照替换，弹 1.5s「已保存」）
                              └─ 失败 ──► ready + 该控件回滚 + toast(error)
```

- 连续快速切换同一个多选时，用 `AbortController` 之外的方式串行化：保存中禁用控件，
  不做队列（配置写入是毫秒级，串行足够）。
- `degraded` 只在 `configGet` 完全失败时出现（老宿主没有该 action / 表损坏）。
  此时页面仍要能打开，避免把整个插件弄挂。

### 5.5 `useConfig` hook

`client/config.cjs` 导出：

```js
function useConfig(api, opts) {
  // opts: { ids?: string[], live?: boolean }
  // → { ready, degraded, items, groups, get(id, fallback), set(id, value), reset(id), resetAll, error }
}
```

- 传 `ids` 时只取需要的子集（列表页只要 `list.*`，统计页只要 `stats.*`），
  减少首屏解析；不传则全量（配置页）。
- `get(id, fallback)` 在未 ready 时返回客户端常量 `FALLBACK`，保证列表页不必等配置
  就能先渲染骨架。
- `live: true` 时订阅 `<domain>-config-changed`，收到后重新 `configGet`。
- hook 内部对同一 action 做 30s 的 `Map` 缓存？**不做**——切视图就重新读，量极小，
  避免跨视图失效问题。

- 站点 `resolveSort` 已对白名单外列回落 `update_time`；配置页只提供三项，
  与后端白名单保持一致。
- `stats.staleDays` 影响 `freshnessBins` 的档位标签：分桶按 `7 / 30 / staleDays`
  生成，标签用 `0–7 / 8–30 / 31–N / >N` 这种语言无关写法，顺带修掉现在中文写死、
  英文界面仍显示中文标签的问题。
- 重复 URL 的「归一化规则」（去尾斜杠、协议、`www`）属于算法而不是偏好，
  不开放；`form.duplicateUrlPolicy` 仅决定发现重复后的行为，P2。

## 9. 明确不做成配置的项

| 候选项 | 为什么不做 |
| --- | --- |
| tab 编号语义（5/6/7/8）与状态值（0/1/2/3） | 会破坏 action 契约、同步对端与历史数据；属于数据模型，不是偏好 |
| 分页上限 200、单次批量上限、请求体大小 | 防滥用/防卡死的硬限制 |
| 字段必填性（站点必须有目录、任务必须有标题） | 数据完整性约束 |
| URL 归一化、去重算法 | 算法口径应全局一致，否则两台设备算出的「重复」不同 |
| 主题色、明暗、语言、字号 | 宿主级设置，业务插件不应各存一份 |
| 同步开关、冲突策略、备份策略 | 属 [16](./16-数据同步方案.md)/[15](./15-数据备份.md) 的全局设置，且影响数据安全 |
| 任意新增标签/字段/表单 | 会滑向动态表单引擎，超出插件边界 |
| 账号、token、云端地址 | 敏感信息，禁止进业务表 |
| 统计口径（完成率分母是否含已关闭） | 先固定，避免「两个人的报表对不上」；见 §15 |

## 10. 兼容、迁移与降级

### 10.1 老库升级

- `setup` 里 `ensureConfigSchema` 用 `CREATE TABLE IF NOT EXISTS`，空库/老库都幂等。
- 不写默认值行，所以升级后配置表是空的；`configGet` 返回全默认，用户无感。
- 卸载插件：表随库保留（与现有业务表一致），重装后配置自动回来。

### 10.2 客户端与服务端版本错配

| 组合 | 行为 |
| --- | --- |
| 新客户端 + 老服务端（无 `config` action） | `configGet` 404/500 → 配置页进入 `degraded`：用客户端 `FALLBACK` 常量渲染，控件禁用，顶部提示「当前宿主版本不支持配置」；列表/统计页继续用 `FALLBACK` |
| 老客户端 + 新服务端 | 老客户端不注册配置视图，也不会调 action；服务端多出的 action 与表不影响它 |
| 新客户端 + 新服务端但 `configGet` 缺某项 | `get(id, fallback)` 回退 `FALLBACK`；不报错 |

客户端 `FALLBACK` 只保留 P0 项的最小集合（`pageSize`、`defaultTab`、`stats` 的
`range/top`），不复制整份 schema，避免两份真值长期漂移。

### 10.3 备份

- v1 备份导入 v2 客户端：保留当前配置，提示一句。
- v2 备份导入 v1 客户端：老代码只认 `schemaVersion === 1`，会报「版本不兼容」并
  拒绝整包导入——这是**已知且可接受**的行为（老版本本来就不该读新备份）；
  文档 [15](./15-数据备份.md) 补一条说明。
- 导出的 `config` 只含有效行，墓碑不导出。

### 10.4 手工改库/脏数据

- `value` 不是合法 JSON → 该项回退默认，`warnings` 里记 `id`，其余项正常。
- `value` 能解析但校验不过（例如 `pageSize: 999`）→ 回退默认 + warning，不抛错。
  只有 `configSet` 会抛错；读取路径永远宽松。
- `id` 不在 schema 里（降级/手写）→ 忽略，但保留行不删（可能来自更高版本），
  `configGet` 的 `warnings` 里提示「存在未知配置项 N 个」。

### 10.5 同步

- 配置表加进 `sync.tables` 后，首次同步会把本机配置推给对端；对端若已有同 id 行，
  按 `updated_at` LWW。
- 墓碑行会传播「恢复默认」；接收端只更新本机行，不重放 UI。

## 14. 风险与回滚

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 配置项膨胀成第二套数据模型 | 维护成本失控 | 白名单 + 本文档评审 + `deprecated` 机制；每加一项必须写 surface/apply |
| `ui` 项被误做成 `api` | agent 行为被用户偏好悄悄改变，难复现 | §4.4 口诀 + code review 检查读取点 |
| 客户端/服务端版本错配 | 配置页报错或空白 | 三分支降级 + `FALLBACK` |
| 备份 v2 让老客户端无法导入 | 用户降级后恢复失败 | 文档明示；必要时提供「导出为 v1」后续项（本次不做） |
| 同步把本机偏好带到其他设备 | 用户困惑「我没改过」 | 明确「配置属于工作台而非设备」；开放问题 1 再评估 |
| 手工改库写坏 JSON | 统计页异常 | 读取路径宽松回退 + warnings，永不因配置抛错 |

回滚：删掉视图注册与三个 action 即可退回两页签；三张表留在库里无副作用；
备份 `SCHEMA_VERSION` 回退到 1 会丢掉配置段（不建议）。

## 15. 开放问题

1. **配置的归属粒度**：当前按「工作台数据库」存一份，多端同步后一致。
   如果未来同一库多用户使用，需要 per-user 命名空间（`id` 加前缀或加 `owner` 列）。
   建议 v1 不做，保持简单。
2. **统计口径要不要开放**（完成率是否含已关闭、逾期是否含已关闭）：
   开放会让两个人看同一份数据得出不同结论。建议先固定，等有明确诉求再做，
   且做成 `api` 项并在报表页标注口径。
3. **是否允许 agent 写 `ui` 项**：技术上可以（同一个 action）。建议允许，但在
   action description 里写明「ui 项只影响本机界面」，避免 agent 把它当业务参数。
4. **列表默认排序是否下放服务端**：下放后 agent 调 `tasks.list` 也会受用户偏好影响，
   与 D5 冲突。建议保持客户端传参（`auto` 时服务端用自己的分页默认）。
5. **配置项废弃策略**：建议保留 id、标 `deprecated`、读仍返回、UI 不渲染、
   `configSet` 拒绝；一年后再考虑清行。
