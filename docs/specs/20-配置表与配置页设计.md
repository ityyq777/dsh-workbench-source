# 20 · 配置表与配置页设计（任务 / 标签 / 站点）

> 关联：[03-UI设计](./03-UI设计.md)、[04-子插件体系](./04-子插件体系.md)、
> [05-本地存储设计](./05-本地存储设计.md)、[15-数据备份](./15-数据备份.md)、

## 0. 一句话结论

每个业务插件把自己的配置写成 `meta` 表里的键值对：`config.<domain>.<id>` → JSON 文本，只存
**用户改过的覆盖项**，删除键即恢复默认。服务端用一份带类型的白名单 schema 做校验与默认值兜底；
客户端新增第三个「配置」视图，按分组把值渲染成开关/下拉/多选/数字；列表页、统计页、新建表单
在挂载时读取配置并据此初始化。

配置是**本机偏好**：不参与云端同步，也不进入备份包。这样既不新增表，也不扩大同步与备份的
协议面；代价是换机或清库后需要重新设置（可接受，见 §3.6、§10.5）。

## 1. 问题与目标

### 1.1 现状盘点

三个插件的可调参数目前散落在三处：客户端常量、服务端常量、统计代码里的写死阈值。
改一个分页数要改代码、重新构建客户端 bundle；用户没有任何入口。

用户无法隐藏不关心的部分（例如不关心排行的人不需要「任务表排行」「任务组排行」）。

### 1.2 目标

1. **每个插件一组配置键**：复用平台 `meta` 表，`id` 是配置项、`value` 是配置值；
   值用 JSON 文本承载，可以是一个标量，也可以是一个数组或对象，不为每种类型加列。
2. **每个插件多一个「配置」视图**，与「统计」「记录」并列；页面由服务端下发的
   schema 驱动，不在客户端硬编码表单。
3. **只存覆盖项**：默认值留在代码里。升级新增配置项时不需要迁移，用户没改过就自动
   使用新默认值；「恢复默认」= 删掉那个键。
4. **可审计、可自动化**：配置读写走四个 action，agent 也能读能改；写配置不写
   `sync_change_log`，因为配置不参与同步。
5. **不打断现有链路**：备份、同步、卸载、老库升级都要有明确行为，不能因为配置读写
   把现有导入导出弄坏。

### 1.3 非目标

- 不做通用表单引擎 / 任意字段扩展（`id` 必须命中白名单）。
- 不做远程配置中心：配置只在本机 SQLite 的 `meta` 表，不参与云端同步。
- 不做按用户/按设备的偏好分层：一个工作台数据库一份配置（见 §15 开放问题 1）。
- 不把主题、语言、字号这类宿主级偏好搬进业务插件。
- 不开放分页上限（200）、必填校验、URL 合法性这类**数据完整性**约束。
- 不为了配置化而改 action 的入参契约；agent 显式传参永远优先于配置默认值。

## 2. 设计决策

| # | 决策 | 理由 | 代价 |
| --- | --- | --- | --- |
| D1 | 复用宿主 `meta` 表，键前缀 `config.<域>.`，不新建表 | 免去建表、迁移、域表声明、备份与同步声明；`meta` 本来就是平台键值表 | 键空间与其它 meta 使用者共享，必须统一前缀；三个包各复制一份 `lib/config.js` 骨架（与 `charts.cjs` 同策略） |
| D2 | 只存覆盖项（overrides-only），不落默认值 | 默认值随版本演进；升级不需要数据迁移；「恢复默认」语义天然 | 读配置要合并默认值；手工看库看不出全貌（用 `configGet` 看） |
| D3 | `value` 存 JSON 文本，不拆多列 | 一个 `sections: ["kpi","trend",...]` 数组、一个 `{}` 对象都不用加列；SQLite 侧无需 JSON1 也能读 | 排序/比较只能在应用层做；需要大小上限 |
| D4 | 服务端白名单 schema 是唯一事实源，写入时校验 | agent 也会写，客户端校验不能当数；UI 文案也从 schema 来 | schema 要写两语文案，比纯客户端常量啰嗦 |
| D5 | 配置项分 `surface = ui / api` 两个生效面 | 用户偏好不该悄悄改变 agent 调 action 的结果：只有确实改变数据/校验的项才进服务端读取路径 | 每个配置项要想清楚归属，不能一股脑塞给服务端 |
| D6 | 「恢复默认」= 删除键，不写回默认值 | 只存覆盖项，删键即回到代码默认；默认值以后调整还能跟随 | 没有「何时恢复默认」的历史 |
| D7 | 配置不参与同步、不进入备份 | 评审结论（m00336）：配置是本机偏好，跨端同步会互相覆盖；备份 `schemaVersion` 保持 1 | 换设备/恢复备份后需要重新设置 |
| D8 | 配置视图排在「统计」「记录」之后 | 不改变既有默认落地页（统计）和肌肉记忆；[18 §17](./18-统计报表设计.md) 的页签约定扩为三段 | 首页卡片多一个 tab，无功能影响 |
| D9 | 写入即时生效、即时落库，不做「脏草稿 + 保存」 | 三个视图切换即卸载（宿主只渲染 `activeView.component`），草稿很容易在切页时丢；即时保存的交互成本更低 | 没有批量撤销；靠逐项「恢复默认」兜底 |
| D10 | 不缓存配置 | 配置量 < 30 行，读一次是全表扫描；缓存只会引入失效问题（agent 写入不经过 UI） | 每次 action 多一次查询（微秒级） |

## 3. 数据模型

### 3.1 存储位置

不新增业务表，复用宿主平台表 `meta`：

```sql
CREATE TABLE IF NOT EXISTS meta (
  k TEXT PRIMARY KEY,   -- config.<domain>.<id>，如 config.tasks.list.pageSize
  v TEXT NOT NULL       -- JSON：12 / "30d" / ["trend","status"] / false
);
```

- 三个插件的 `lib/config.js` 都在注册配置 action 时执行同一段 `ensureMeta(db)`：
  `CREATE TABLE IF NOT EXISTS meta ...`。宿主与标签插件此前都不保证这张表存在，
  各自兜底最稳；DDL 幂等，重复执行无副作用。
- 只写覆盖项：`config.<domain>.<id>` 存在即覆盖，不存在即用 schema 默认值。
- 读取用 `k LIKE 'config.<domain>.%'` 一次取回本域全部键，再与默认值合并。
- 恢复默认 = 删除键，不写墓碑；因此没有 `rev / updated_at / deleted_at` 列。

### 3.2 键值语义

| 位置 | 语义 | 备注 |
| --- | --- | --- |
| `k` 的 domain 段 | `tasks` / `tags` / `sites` | 域 id 去掉 `wb-addon-` 前缀 |
| `k` 的 id 段 | 白名单配置项 id | 见 §3.3；未知 id 读取时忽略并记 warning |
| `v` | `JSON.stringify` 规范化后的值 | 数字、布尔、字符串、数组都走 JSON，不做 pretty print |
| 删除键 | 恢复默认 | 配置页的「恢复默认」直接 `DELETE FROM meta WHERE k=?` |

没有行版本与时间戳：配置不参与同步，也就不需要 LWW 的比较字段。

### 3.3 键名规范

- 形式 `<group>.<name>`，全小写开头的驼峰，例如 `list.pageSize`、`stats.weekStartsOn`。
- `group` 只用于配置页分组与批量重置，固定为 `ui` / `list` / `form` / `stats`
  （各域按自己的目录取舍）。
- 键名一旦发布**不再改名**（改名等于丢用户设置）。废弃走 `deprecated: true`：
  保留在 schema 里、`configGet` 仍返回（带标记）、`configSet` 拒绝、UI 不渲染。
- 正则兜底：`^[a-z][a-zA-Z0-9]*\.[a-zA-Z][a-zA-Z0-9]*$`；真正的准入仍靠白名单。

### 3.4 值编码

| schema `type` | 存储 | 规范化 |
| --- | --- | --- |
| `bool` | `true` / `false` | 只接受布尔 |
| `int` | 整数 | `Math.round` 后夹在 `[min,max]`；越界直接报错，不静默夹取 |
| `enum` | 字符串或数字 | 必须是 `options[].value` 之一，保持原类型 |
| `multi` | 数组 | 去重、剔除未选项、按 `options` 顺序重排；空数组合法 |
| `string` | 字符串 | 去首尾空白；`maxLength`；`ref` 只做 UI 提示，服务端不校验引用存在性 |

实现目前只用到 `bool / int / enum / multi / string`；`number`、`json` 作为后续扩展预留。
硬限制：单值序列化后 **≤ 8192 字节**；`multi` ≤ 32 项；字符串 ≤ 512 字符
（`form.maxNameLength` 这类另有 `maxLength`）。超限报错而不是截断。

### 3.5 生命周期

```
默认（无键）
  └─ configSet(id, v) ──► 写入 meta 键，值 JSON
        └─ configSet(id, null) / configReset ──► 删除该键
              └─ 再次 configSet ──► 重新写入
```

- `configSet` 写入与当前**有效值**相同的值时视为 no-op：不写键。
- 所有写操作在一个 `tx()` 事务里完成；批量 values 里任何一项校验失败 → 整批回滚。
- 没有行版本、时间戳、墓碑：恢复默认就是 `DELETE`，配置不参与同步，不需要 LWW。

### 3.6 与同步

**不参与云端同步。** 依据（m00336）：配置是每台机器自己的偏好，跨端同步会把 A 设备的
分页/页签/统计偏好强加给 B 设备，收益低而冲突解释成本高。

- 三份 `lib/sync.js` 都不声明配置表或配置键；同步器看不到这些 `meta` 行。
- 配置写入是 `INSERT OR REPLACE INTO meta`、删除是 `DELETE FROM meta`，都不写
  `sync_change_log`（测试 `scripts/test-config.mjs` 会断言日志为 0），因此也不会被增量同步捎带出去。
- 多设备各自维护自己的配置；换机后回到默认值，需要重新设置。

### 3.7 与备份

**不进入备份包。** `lib/backup.js` 的 `SCHEMA_VERSION` 保持 `1`，导出结构不变
（仍是 `{ schemaVersion, tasks, taskNodes, taskDeps }` 等），配置键不在导出范围内。

- 备份语义是「业务数据」，配置属于环境偏好；把它塞进备份会让「换机恢复」意外改变
  新机器的界面行为。
- 恢复备份不会覆盖本机配置；本机配置也不会被备份文件带回来。
- 同一份数据库文件内卸载/重装插件不会丢配置（键还在 `meta` 里）。

### 3.8 规模与性能

- 单域配置项 10–15 个（实际：tasks 15 / tags 10 / sites 13），全表 < 10KB。
- `configGet` 一次 `LIKE 'config.<domain>.%'` 查询 + 合并默认值，O(n)，无可感知开销。
- 统计页每次 `statsReport` 会多一次配置读取（同一 `db` 句柄），可忽略。

## 4. 服务端契约

### 4.1 配置项描述符

`lib/config.js` 里每个插件维护 `DOMAIN`、`GROUPS`、`ITEMS`：

```js
export const DOMAIN = "tasks";

const GROUPS = [
  { id: "ui", zh: "界面", en: "Interface" },
  { id: "list", zh: "列表", en: "List" },
  { id: "form", zh: "新建", en: "Create" },
  { id: "stats", zh: "统计", en: "Statistics" },
];

const ITEMS = [
  {
    id: "list.pageSize", group: "list", type: "enum", surface: "ui", apply: "mount",
    default: 12,
    zh: "每页条数", en: "Page size",
    hintZh: "记录页每页显示多少条", hintEn: "Rows per page in Records",
    values: [6, 12, 24, 48].map((n) => ({ value: n, zh: n + " 条", en: String(n) })),
  },
  // ...
];
```

字段说明（与实现一一对应）：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `id` | ✓ | 白名单键，见 §3.3 |
| `group` | ✓ | 必须是 `GROUPS[].id` |
| `type` | ✓ | `bool` / `int` / `enum` / `multi` / `string` |
| `surface` | ✓ | `ui`：只被客户端读取；`api`：服务端读取并影响结果/校验 |
| `apply` | ✓ | `mount`（切换到该视图时读取）/ `api`（每次调用读取） |
| `default` | ✓ | 与 `type` 匹配；`multi` 为数组 |
| `zh` / `en` | ✓ | 配置页名称，直接展示 |
| `hintZh` / `hintEn` | 可选 | 行内说明 |
| `values` | enum/multi | `[{value, zh, en}]`，服务端会转成 `options[{value,label:{zh,en}}]` 下发 |
| `min` / `max` | int | 闭区间；越界直接报错，不静默夹取 |

实现里没有 `deprecated` / `since` / `ref` / `step`：当前取值都是标量或固定枚举，
不需要这些机制；将来要加再补，不影响现有键名。

### 4.2 action 定义

四个 action 都注册在各自域下：`configGet` / `configSet` / `configReset` / `configOptions`。

#### `configGet`

```json
{ "type": "object", "properties": {}, "additionalProperties": false }
```

返回（`items` 顺序即配置页渲染顺序）：

```json
{
  "domain": "tasks",
  "schemaVersion": 1,
  "table": "meta",
  "groups": [{ "id": "list", "zh": "列表", "en": "List" }],
  "items": [
    {
      "id": "list.pageSize",
      "group": "list",
      "surface": "ui",
      "apply": "mount",
      "type": "enum",
      "default": 12,
      "zh": "每页条数",
      "en": "Page size",
      "hintZh": "…",
      "hintEn": "…",
      "options": [{ "value": 6, "label": { "zh": "6 条", "en": "6" } }]
    }
  ],
  "values": { "list.pageSize": 12 },
  "overrides": {},
  "warnings": []
}
```

- `values` 是**有效值**（有键取键，无键取默认）；`overrides` 只含用户改过的项。
- `items` 不带值；客户端用 `values[id]` 取，节省重复字段。
- `warnings` 收集：表缺失、JSON 解析失败、值校验失败（回退默认）等；不阻塞返回。

#### `configSet`

```json
{
  "type": "object",
  "properties": {
    "values": {
      "type": "object",
      "additionalProperties": true,
      "description": "id → 新值；null 表示恢复该项默认（删键）"
    }
  },
  "required": ["values"]
}
```

- 返回 `{ changed, values, state, updatedAt, origin }`；`state` 就是 `configGet` 的快照，
  客户端可直接替换本地状态。
- 校验顺序：values 是否为对象 → 每个 id 是否存在/是否 deprecated → 类型 → 范围/枚举 →
  大小 → 规范化。第一处失败即抛错，整批不落库。
- 值未变化时不写键（§3.5），但仍返回快照。
- `origin` 由宿主注入（`ui` / `agent`）；不写变更日志。

#### `configReset`

```json
{
  "type": "object",
  "properties": {
    "ids": { "type": "array", "items": { "type": "string" } }
  }
}
```

- `ids` 可选；省略表示重置全部。
- 语义是删除键；已经是默认的项跳过，不产生空写入。
- 返回 `{ reset, state, updatedAt, origin }`。

#### `configOptions`

```json
{ "type": "object", "properties": {} }
```

- 返回 `{ domain, schemaVersion, groups, items }`：只含目录与默认值，不含当前值。
- 给 agent 查「有哪些配置 id、取值是什么」用，避免先拉一遍全量快照。

### 4.3 错误文案

宿主把 `execute` 抛出的 `Error.message` 原样放进 HTTP 500 的 `error` 字段，
所以文案要能直接给用户看，并带上出错的配置项 id。

| 条件 | 文案 |
| --- | --- |
| values 不是对象 | `values 必须是对象` |
| 未知配置项 | `未知配置项：list.pageSizeX` |
| 已废弃 | `配置项已废弃：xxx` |
| 类型不符 | `list.pageSize 必须是整数` |
| 枚举越界 | `list.pageSize 只能是 6、12、24、48` |
| 数值越界 | `stats.top 必须在 1–20 之间` |
| 多选含未知项 | `stats.sections 含未知区块：foo` |
| 超长/超大 | `stats.sections 超出单值 8KB 上限` |


### 4.4 生效面（surface）

这是本设计里唯一需要逐项判断的地方。规则：

- **`ui`（默认）**：只影响本机界面。客户端读取，服务端从不读。agent 调
  `tasks.list` 时不会因为用户把每页设成 48 而改变返回条数。
- **`api`**：改变服务端返回结果或校验规则，服务端每次调用读取。例如
  `stats.weekStartsOn`（周起始影响趋势分桶）、`tags.stats.staleDays`（沉睡清单）、
  `form.maxNameLength`（校验）、`form.maxLinks`（校验）。
- 判断口诀：**「换个 agent 来调用，这个默认值还合理吗？」** 合理 → `ui`；
  不合理（结果会变、会误判）→ `api`。统计类因为「用户看的是同一张报表」，
  所以 `weekStartsOn`、`staleDays` 归 `api`，而 `sections`、`top` 归 `ui`。

`api` 项的读取点：

| 配置项 | 读取位置 |
| --- | --- |
| `stats.weekStartsOn` | 各 `lib/stats.js` 的 `resolveRange`，把 `weekStartsOn` 放进返回的 `range`，`bucketKeys` / `bucketOf` 用它 |
| `stats.staleDays` | `tags/lib/stats.js` 的 `staleBefore` 计算；`sites/lib/stats.js` 的新鲜度分桶与 `stale` 清单 |
| `stats.duplicateLimit` | `sites/lib/stats.js` 的重复 URL 分组截断 |
| `form.maxNameLength` | `tags/lib/tags.js` 的 `maxName(db)` 校验（`create` / `update` / `rename`） |
| `form.maxLinks` | `sites/lib/sites.js` 的 `checkLinkLimit`（`createSite` / `updateSite`） |
| `form.autoCreateTags` | `tasks/lib/tasks.js` 的 `requireKnownTagNames`（`create` / `update` / `bulkUpdate`） |

### 4.5 事件

**不广播事件。** 宿主只渲染 `activeView.component`，切页签即卸载旧视图；写配置后无需
通知别的视图，切回时它们会重新 `configGet`。少一条事件总线就少一类「配置变更后谁该
刷新」的隐式依赖。将来若宿主支持保留挂载，再补 `<domain>-config-changed`。

### 4.6 代码结构

新增 `lib/config.js`（每个包一份，结构与 `client/config.cjs` 的复制策略一致）：

### 4.7 读取约定

- 一次 action 只读一次配置：`const cfg = configValues(db);` 然后把需要的值取出来往下传，
  不在循环里反复查库。
- `api` 项在服务端读取时**只在入口读一次**，不要读「已保存但未生效」的中间态
  （不存在这种状态，因为写入即提交）。
- `statsReport` 的签名不动：`statsReport(db, args)` 内部自己 `configValues`，
  避免改测试与其它调用点。

### 5.3 控件映射

| type | 控件 | 说明 |
| --- | --- | --- |
| `bool` | 开关（checkbox 样式化） | 点击即写入 |
| `enum` | `<select>` | 选项文案取 `options[].label[lang]` |
| `int` | `<input type=number>` + 失焦/回车提交 | 输入框本地保留草稿，提交仍由服务端校验范围 |
| `multi` | 复选组 | 顺序按 `options`；空数组表示「全不展示」 |
| `string` | `<input type=text>` | 失焦/回车提交 |

当前实现的 `string` 只用于名称长度这类数值型文本，没有 `ref` 选择器；
`number` / `json` 控件未使用（见 §4.1）。

### 5.4 状态机

```
loading ──configGet 成功──► ready
   │                          │
   └──失败──► degraded（用代码内默认值渲染，顶部黄条提示，控件禁用）
                              │
         控件变更 ──► saving（控件禁用 + 行尾 loading）
                              ├─ 成功 ──► ready（用返回快照替换，弹 1.5s「已保存」）
                              └─ 失败 ──► ready + 该控件回滚 + toast(error)
```

- 连续快速切换同一个多选时，用 `AbortController` 之外的方式串行化：保存中禁用控件，
  不做队列（配置写入是毫秒级，串行足够）。
- `degraded` 只在 `configGet` 完全失败时出现（老宿主没有该 action / 表损坏）。
  此时页面仍要能打开，避免把整个插件弄挂。

### 5.5 `useConfig` hook

`client/config.cjs` 导出：

```js
function useConfig(api, fallback) {
  // → { ready, values, items, groups, overrides, error, state }
}
```

- `fallback` 是客户端常量（`CFG_FALLBACK`），`configGet` 失败或未返回时用它，保证
  列表/统计页永远能渲染。
- 挂载时读一次 `<domain>.configGet`；`ready` 为假时列表页渲染居中的「载入中…」，
  避免用默认值先请求一遍再按配置重取。
- 配置页 `ConfigView` 不复用这个 hook 的返回值，而是自己持有快照（保存成功后整体替换）。
- 不做缓存、不订阅事件：切视图就重新读，配置量极小。

## 9. 明确不做成配置的项

| 候选项 | 为什么不做 |
| --- | --- |
| tab 编号语义（5/6/7/8）与状态值（0/1/2/3） | 会破坏 action 契约、同步对端与历史数据；属于数据模型，不是偏好 |
| 分页上限 200、单次批量上限、请求体大小 | 防滥用/防卡死的硬限制 |
| 字段必填性（站点必须有目录、任务必须有标题） | 数据完整性约束 |
| URL 归一化、去重算法 | 算法口径应全局一致，否则两台设备算出的「重复」不同 |
| 主题色、明暗、语言、字号 | 宿主级设置，业务插件不应各存一份 |
| 同步开关、冲突策略、备份策略 | 属 [16](./16-数据同步方案.md)/[15](./15-数据备份.md) 的全局设置，且影响数据安全 |
| 任意新增标签/字段/表单 | 会滑向动态表单引擎，超出插件边界 |
| 账号、token、云端地址 | 敏感信息，禁止进业务表 |
| 统计口径（完成率分母是否含已关闭） | 先固定，避免「两个人的报表对不上」；见 §15 |

## 10. 兼容、迁移与降级

### 10.1 老库升级

- 不新增业务表；`ensureMeta` 用 `CREATE TABLE IF NOT EXISTS meta`，空库/老库都幂等。
- 不写默认值行，所以升级后没有任何配置键；`configGet` 返回全默认，用户无感。
- 卸载插件：`meta` 行随库保留（与现有业务表一致），重装后配置自动回来。

### 10.2 客户端与服务端版本错配

| 组合 | 行为 |
| --- | --- |
| 新客户端 + 老服务端（无 `config` action） | `configGet` 404/500 → 配置页进入 `degraded`：用客户端 `FALLBACK` 常量渲染，控件禁用，顶部提示「当前宿主版本不支持配置」；列表/统计页继续用 `FALLBACK` |
| 老客户端 + 新服务端 | 老客户端不注册配置视图，也不会调 action；服务端多出的 action 不影响它 |
| 新客户端 + 新服务端但 `configGet` 缺某项 | `get(id, fallback)` 回退 `FALLBACK`；不报错 |

客户端 `CFG_FALLBACK` 只保留界面初值真正需要的那几项，不复制整份 schema，
避免两份真值长期漂移；服务端 `configGet` 成功后以返回值为准。

### 10.3 备份

- 配置不进入备份包，`SCHEMA_VERSION` 保持 1，老备份/新备份互相兼容。
- 恢复备份只写业务数据，不触碰 `meta` 里的配置键。
- 换机流程：先恢复备份拿回业务数据，再在配置页按需重设本机偏好。

### 10.4 手工改库/脏数据

- `value` 不是合法 JSON → 该项回退默认，`warnings` 里记 `id`，其余项正常。
- `value` 能解析但校验不过（例如 `pageSize: 999`）→ 回退默认 + warning，不抛错。
  只有 `configSet` 会抛错；读取路径永远宽松。
- `id` 不在 schema 里（降级/手写）→ 忽略，但保留行不删（可能来自更高版本），
  `configGet` 的 `warnings` 里提示「存在未知配置项 N 个」。

### 10.5 同步

- 配置不参与同步：`sync.js` 不声明，写入不记 `sync_change_log`。
- 云端不会下发配置，所以不同设备可以有不同的分页、排序、统计范围与阈值。
- 若将来要跨端同步，再单独设计同步通道与冲突策略即可，不改现有键名。

## 14. 风险与回滚

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 配置项膨胀成第二套数据模型 | 维护成本失控 | 白名单 + 本文档评审 + `deprecated` 机制；每加一项必须写 surface/apply |
| `ui` 项被误做成 `api` | agent 行为被用户偏好悄悄改变，难复现 | §4.4 口诀 + code review 检查读取点 |
| 客户端/服务端版本错配 | 配置页报错或空白 | 三分支降级 + `FALLBACK` |
| 配置键与将来其它 `meta` 使用者撞名 | 互相覆盖 | 统一 `config.<域>.<id>` 前缀；读取只认白名单 |
| 用户误以为配置会跟设备走 | 换机后要重设 | 配置页底部明示「只保存在本机」 |
| 手工改库写坏 JSON | 统计页异常 | 读取路径宽松回退 + warnings，永不因配置抛错 |

回滚：删掉视图注册与四个 action 即可退回两页签；`meta` 里的配置键留着无副作用；
备份 `SCHEMA_VERSION` 回退到 1 会丢掉配置段（不建议）。

## 15. 开放问题

1. **配置的归属粒度**：当前按「工作台数据库」存一份，多端同步后一致。
   如果未来同一库多用户使用，需要 per-user 命名空间（`id` 加前缀或加 `owner` 列）。
   建议 v1 不做，保持简单。
2. **统计口径要不要开放**（完成率是否含已关闭、逾期是否含已关闭）：
   开放会让两个人看同一份数据得出不同结论。建议先固定，等有明确诉求再做，
   且做成 `api` 项并在报表页标注口径。
3. **是否允许 agent 写 `ui` 项**：技术上可以（同一个 action）。建议允许，但在
   action description 里写明「ui 项只影响本机界面」，避免 agent 把它当业务参数。
4. **列表默认排序是否下放服务端**：下放后 agent 调 `tasks.list` 也会受用户偏好影响，
   与 D5 冲突。建议保持客户端传参（`auto` 时服务端用自己的分页默认）。
5. **配置项废弃策略**：建议保留 id、标 `deprecated`、读仍返回、UI 不渲染、
   `configSet` 拒绝；一年后再考虑清行。
