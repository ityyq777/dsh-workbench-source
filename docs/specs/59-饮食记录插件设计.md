# 59 饮食记录插件设计（diet 0.1.0）

> 状态：设计稿，确认后开发。
> 目标包：`dsh-workbench-diet`，域 `wb-addon-diet`，前端前缀 `wbdiet`，首页栏目 `other`。

## 1. 背景与目标

用户要一个跟饮食相关的工作台插件：记录每天的一日三餐，并让 AI 根据饮食情况给出
「下一顿吃什么」的建议。讨论中确认的两条关键结论：

1. **目标不能写死**。同一个人在不同阶段（减脂期、维持期、增肌期、控糖期）需求不同，
   所以目标做成**阶段（phase）**：可配置、可引导、可随时切换；历史记录按日期归属到
   当时的阶段，阶段结束后能回头看「这个阶段到底吃成什么样、有没有效果」。
2. **AI 建议走双通道**。宿主没有 LLM 服务，插件不能自己调模型——**agent 就是那个模型**：
   插件提供结构化上下文 action 让 agent 推理，再把建议写回；同时内置规则引擎保证
   不接 agent 也有建议卡可看。

本插件解决五件事：

1. 按日期记录早/午/晚/加餐，食物条目带份量与营养；
2. 今日看板：已摄入、剩余预算、缺口（热量/蛋白/蔬菜/水）、三餐时间线；
3. 下一顿建议：带依据、可采纳、可复盘；
4. 阶段化目标与统计：7/30 天趋势、达标率、外卖占比、阶段对比；
5. **提醒与定时建议不自己写定时器**，交给「自动化」插件调度（见 §7）。

**非目标**：不做拍照识别、不做医学营养处方（血糖/尿酸只做忌口规则）、不做多人共享菜单、
不做菜谱库与采购闭环（留接口，见 §12）、**不自建定时/限频/通知体系**（复用自动化与消息插件）。

## 2. 数据模型

### 2.1 表 `diet_phase` 阶段（目标体系核心）

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `id` | TEXT PK | `dph_` + 时间戳 + 随机 |
| `started_at` | TEXT NOT NULL | 开始日期 `YYYY-MM-DD` |
| `ended_at` | TEXT NULL | 结束日期；NULL 表示当前活跃阶段 |
| `goal` | TEXT NOT NULL | `cut` 减脂 / `maintain` 保持 / `gain` 增肌 / `control` 控糖控指标 / `free` 只记录 |
| `target_kcal` | REAL NULL | 每日热量目标；`free` 可为 NULL |
| `target_protein` | REAL NULL | 每日蛋白目标（克） |
| `target_veg` | INTEGER NULL | 每日蔬菜份数目标（默认 3 份） |
| `target_fruit` | INTEGER NULL | 每日水果份数目标（默认 2 份） |
| `target_water` | INTEGER NULL | 每日饮水目标（ml，默认 2000） |
| `body_weight` / `body_height` / `body_age` / `body_sex` / `activity` | REAL/INT/TEXT | 引导时采集的身体数据与活动系数，用于 TDEE |
| `note` | TEXT NOT NULL DEFAULT '' | 阶段备注，如「体检后开始减脂」 |
| `created_at` / `updated_at` | INTEGER | UTC 毫秒 |
| `deleted_at` | INTEGER NULL | 软删除 |
| `rev` | INTEGER | 版本号 |

约束：

- **同一时刻最多一个活跃阶段**（`ended_at IS NULL AND deleted_at IS NULL`），新建/切换前
  自动把原活跃阶段 `ended_at` 置为前一天（或用户指定日期）；
- 阶段日期不可重叠（写入前校验区间冲突）；
- 没有任何阶段时进入「自由记录」：只统计不评判，建议只做均衡性提示。

### 2.2 表 `diet_meal` 一餐

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `id` | TEXT PK | `dme_` + 时间戳 + 随机 |
| `date` | TEXT NOT NULL | `YYYY-MM-DD` |
| `type` | TEXT NOT NULL | `breakfast` / `lunch` / `dinner` / `snack` |
| `eaten_at` | TEXT NULL | `HH:mm`，用于时间线与规律性统计 |
| `place` | TEXT NOT NULL DEFAULT `'home'` | `home` / `canteen` / `takeout` / `restaurant` / `other` |
| `cost` | REAL NULL | 这餐花费（用于饮食支出统计） |
| `satiety` | INTEGER NULL | 饱腹感 1–5（1 很饿、5 很撑） |
| `feeling` | TEXT NOT NULL DEFAULT '' | 餐后感受，如「犯困」「清爽」「胀气」 |
| `note` | TEXT NOT NULL DEFAULT '' | 备注 |
| `created_at` / `updated_at` / `deleted_at` / `rev` | | 同 §2.1 |

**同一天同一餐型允许多笔**（加餐常见、补记常见），不做唯一约束；UI 按「日期 + 餐型」分组展示。

### 2.3 表 `diet_item` 食物条目

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `id` | TEXT PK | `dit_` + 时间戳 + 随机 |
| `meal_id` | TEXT NOT NULL | 所属餐 |
| `food_id` | TEXT NULL | 食物库 id；NULL 表示手动/agent 估算条目 |
| `name` | TEXT NOT NULL | 食物名（冗余保存，食物库改名不影响历史） |
| `amount` | REAL NOT NULL DEFAULT 1 | 份数/克数口径下的数量 |
| `unit` | TEXT NOT NULL DEFAULT `'份'` | `份` / `碗` / `个` / `g` / `ml` |
| `grams` | REAL NULL | 折算克数（有则用于展示与复算） |
| `kcal` / `protein` / `carb` / `fat` / `fiber` | REAL | **该条目的绝对营养值**，写入时算好落库 |
| `veg_servings` / `fruit_servings` | REAL | 蔬菜/水果份数（1 份≈100g） |
| `created_at` / `updated_at` / `deleted_at` | | |

**关键决策**：条目存绝对值而非「per-100g × 份量」，食物库以后改数据不会篡改历史摄入。

### 2.4 表 `diet_food` 食物库

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `id` | TEXT PK | `dfd_` + 时间戳 + 随机 |
| `name` | TEXT NOT NULL | 名称 |
| `aliases` | TEXT NOT NULL DEFAULT '[]' | 别名 JSON 数组（「西红柿」「番茄」） |
| `category` | TEXT NOT NULL | `staple` 主食 / `protein` 蛋白 / `veg` 蔬菜 / `fruit` 水果 / `drink` 饮品 / `snack` 零食 / `dish` 成品菜 |
| `per100_kcal` / `per100_protein` / `per100_carb` / `per100_fat` / `per100_fiber` | REAL | 每 100g 营养 |
| `default_grams` | REAL NOT NULL DEFAULT 100 | 默认一份克数 |
| `tags` | TEXT NOT NULL DEFAULT '[]' | JSON：`high-protein` / `high-gi` / `vegan` / `takeout` / `fried` |
| `favorite` | INTEGER NOT NULL DEFAULT 0 | 收藏 |
| `use_count` | INTEGER NOT NULL DEFAULT 0 | 使用次数，用于「常吃」排序 |
| `last_used_at` | INTEGER NULL | |
| `created_at` / `updated_at` / `deleted_at` | | |

内置种子约 120 条常见食物（覆盖食堂/外卖/家常），首次建库时写入；`name` 唯一（软删不计）。
检索：`name`/`aliases` 模糊匹配 + 分类过滤 + 收藏与使用次数排序。

### 2.5 表 `diet_water` 饮水

`id`、`date`（`YYYY-MM-DD`）、`at`（`HH:mm`）、`amount_ml`、`created_at`、`deleted_at`。
饮水独立成表（一餐不产生多次饮水，一次饮水也不属于某一餐）。

### 2.6 表 `diet_weight` 体重（v1 轻量）

`id`、`date`（同日多笔允许，取当日最后一次）、`weight_kg`、`body_fat`、`note`、时间戳。

### 2.7 表 `diet_advice` 建议

| 列 | 类型 | 含义 |
| --- | --- | --- |
| `id` | TEXT PK | `dad_` + 时间戳 + 随机 |
| `date` | TEXT NOT NULL | 建议针对的日期 |
| `meal_type` | TEXT NOT NULL | 针对哪一餐 |
| `source` | TEXT NOT NULL | `agent` / `rule` |
| `content` | TEXT NOT NULL | 建议正文（可直接展示） |
| `basis` | TEXT NOT NULL DEFAULT '{}' | 依据 JSON：缺口数字、候选、过滤原因 |
| `status` | TEXT NOT NULL DEFAULT `'open'` | `open` / `adopted` / `ignored` |
| `meal_id` | TEXT NULL | 采纳后关联的那一餐 |
| `created_at` | INTEGER | |

建议保留最近 60 天（清理任务在建表时挂一次性删除），用于「建议采纳率」复盘。

### 2.8 表 `diet_day` 每日汇总（派生，写入时重算）

主键 `date`。列：`kcal`、`protein`、`carb`、`fat`、`fiber`、`veg_servings`、`fruit_servings`、
`water_ml`、`meal_count`、`cost`、`updated_at`。

任何餐/条目/饮水变更都重算对应日期的汇总。理由：统计页与今日看板都要按天聚合，
现算一遍全表太贵；派生表也让「缺口」查询变成一次读。

索引：`diet_meal(date)`、`diet_meal(date, type)`、`diet_item(meal_id)`、`diet_water(date)`、
`diet_food(name)`、`diet_advice(date)`。

## 3. 目标体系：阶段 + 引导 + 可切换

### 3.1 引导（首次进入 / 无活跃阶段时）

目标页顶部一张「定个阶段」卡片，逐步问 4 个问题（可跳过）：

1. 现在最想解决什么？（减脂 / 维持 / 增肌 / 控糖 / 先随便记）→ `goal`
2. 身体数据：身高、体重、年龄、性别（用于 TDEE，可跳过）
3. 活动量：久坐 / 轻度 / 中度 / 高强度 → 活动系数 1.2 / 1.375 / 1.55 / 1.725
4. 忌口与过敏：多选标签（辣、生冷、海鲜、乳制品、坚果、内脏、酒精、素食）+ 自由填写

生成阶段草案：TDEE 用 Mifflin-St Jeor 估算，`cut` 取 −18%，`gain` 取 +10%，`maintain`/`control`
取 TDEE；蛋白按 1.6g/kg（cut）、1.8g/kg（gain）估算。用户可逐项改数字后保存。

### 3.2 切换与结束

- 「切换阶段」：选新目标 → 老阶段 `ended_at` = 今天 − 1 天，新阶段 `started_at` = 今天；
- 「结束阶段」：只关不改，进入自由记录；
- 阶段列表可回看历史阶段的目标值（**历史统计始终用当时的阶段目标，不用当前目标**）。

### 3.3 与建议、统计的关系

- 建议：读**当前活跃阶段**的目标与忌口；无阶段则只给均衡性提示；
- 统计：按日期找覆盖阶段，分组对比（如「减脂期 12 周：日均 −280 kcal，蛋白达标 7/12 周」）。

## 4. Action 清单（agent 可见）

命名空间 `diet.`。读操作全部只读；写操作允许 agent（用户口述后直接落库），删除为软删。

| action | 类型 | 说明 |
| --- | --- | --- |
| `diet.status` | 读 | 今日汇总摘要、当前阶段、下一顿类型 |
| `diet.today` | 读 | 今日各餐 + 条目 + 汇总 + 缺口 |
| `diet.mealList` | 读 | 按日期范围/餐型/地点查询（含条目） |
| `diet.mealCreate` | 写 | 建一餐（含 `items[]`；条目可只给名称+份量，按食物库折算；未命中则要求给营养值） |
| `diet.mealUpdate` | 写 | 改餐级字段（时间、地点、花费、饱腹感、备注） |
| `diet.mealDelete` | 写 | 软删一餐（含条目） |
| `diet.itemAdd` / `diet.itemRemove` | 写 | 单条目增删（「再加个苹果」） |
| `diet.foodSearch` | 读 | 食物库检索（别名、分类、收藏） |
| `diet.foodCreate` | 写 | 新增食物（agent 估算的营养入库，下次可复用） |
| `diet.waterAdd` | 写 | 记一次饮水 |
| `diet.adviceContext` | 读 | **建议结构化上下文**：今日摄入、阶段目标与缺口、近 3 天已吃菜品、忌口、常吃候选、下一顿类型与时间窗口 |
| `diet.adviceSave` | 写 | 写回建议（`source`、`content`、`basis`） |
| `diet.adviceList` / `diet.adviceMark` | 读写 | 建议列表 / 采纳或忽略 |
| `diet.remindNextMeal` | 写 | **原子提醒**：算当前餐型与缺口 → 调 `message.send` 落消息中心 → 返回摘要；供自动化的 action 模式定时调用 |
| `diet.remindRecord` | 写 | 检查今天哪一餐还没记，有缺就发一条提醒消息 |
| `diet.dayClose` | 写 | 日终定格：重算当日汇总、发日报消息、`emit("day.closed")` |
| `diet.weekReport` | 读 | 周报（纯计算版，可被自动化调用后自行发消息） |
| `diet.checkTakeout` | 写 | 检查外卖连续顿数，超阈值发消息（供域事件规则调用） |

> 供自动化调用的 action（`remindNextMeal` / `remindRecord` / `dayClose` / `weekReport` /
> `checkTakeout`）**不要声明 `origins: ["ui","agent"]`**：自动化以 `plugin` 来源调用，收窄来源会被直接拒绝；
> 省略 `origins` 默认就包含 `plugin`。
| `diet.phaseList` / `diet.phaseCreate` / `diet.phaseUpdate` / `diet.phaseEnd` | 读写 | 阶段管理 |
| `diet.weightCreate` / `diet.weightList` | 读写 | 体重记录 |
| `diet.statsRange` | 读 | 区间统计：日汇总序列、达标率、外卖占比、花费、阶段对比 |
| `diet.dataTables` / `diet.dataQuery` | 读 | 数据页（UI 专用，`agentEnabled:false`） |
| `diet.actionSchema` | 读 | Action 页 |

### 4.1 自然语言记账流程（核心体验）

```
用户：「中午吃了牛肉面加一个卤蛋，28 块」
agent：diet.foodSearch("牛肉面") → 命中（per100 + 默认 600g）→ 折算
      diet.mealCreate({ date:"今天", type:"lunch", eaten_at:"12:20", place:"takeout",
                        cost:28, items:[{name:"牛肉面", amount:1, unit:"碗"},
                                        {name:"卤蛋", amount:1, unit:"个"}] })
插件：落库 + 重算当日汇总 → 返回「已记录：620 kcal / 蛋白 32g；今日 980/1800 kcal」
agent：把返回摘要转述给用户，必要时顺带一句下一顿建议
```

未命中食物库时，agent 直接给出营养估值并带 `kcal/protein/...` 字段，插件照存并入库为新食物
（`foodCreate` 由 agent 在 `mealCreate` 的 `items[].nutrition` 里隐式触发，避免两次往返）。

## 5. 视图与交互

| 视图 | 内容 |
| --- | --- |
| `today` 今日 | 顶部阶段条（当前目标/剩余热量）→ 营养进度（热量环 + 蛋白/蔬果/水条）→ 下一顿建议卡（可采纳/换一条/忽略）→ 三餐时间线（折叠、就地编辑/删除）→ 快捷记录（常用食物一键加、饮水 +250ml） |
| `records` 记录 | 按日期分组列表；筛选：日期范围、餐型、地点、是否外卖；行内展开条目；「复制这一餐」到指定日期 |
| `stats` 统计 | 7/30 天热量折线与宏量堆叠、蛋白与蔬果达标率、外卖占比、饮食支出、三餐时间规律、记录连续天数、健康分、阶段对比、体重曲线 |
| `foods` 食物库 | 搜索/分类/收藏筛选；列表显示每 100g 营养与使用次数；新增/编辑/删除 |
| `settings` 目标与档案 | 阶段列表与切换、引导向导、身体数据、忌口标签、「接入自动化」入口（跳到自动化规则） |
| `data` 数据 / `actions` Action | 走共享 `data-view.cjs` 与 `action-schema-view.cjs` |

首页卡片底部（`home.card.footer` 自己贡献，不内建他人来源）：`今日 1250/1800 kcal · 蛋白 62/110g`。

健康分（0–100）权重：热量落在目标 ±10% 内 30 分、蛋白达标 25 分、蔬果达标 20 分、
饮水达标 15 分、三餐时间规律 10 分。自由记录阶段不算分，只显示「已记录」。

## 6. 建议引擎（规则兜底）

输入：`diet.adviceContext` 同款数据。流程：

1. **判缺口**：热量剩余、蛋白缺口、蔬菜缺口、饮水缺口，取缺口最大的 1–2 项定候选池；
2. **过滤**：忌口/过敏标签、最近 2 天已吃过的成品菜（避免连续重复）、地点与时段不合适
   （如 23:00 不推正餐）；
3. **打分**：`缺口匹配度 × 0.5 + 常吃权重 × 0.3 + 便捷度 × 0.2`；
4. **成句**：给出具体搭配与估算（「鸡胸肉 150g + 西兰花 200g + 米饭 100g ≈ 520 kcal，蛋白 45g」），
   再补一句为什么（「今天蛋白只吃了 45g，距目标差 65g」）。

建议卡每次展示 1 条主推 + 2 条备选；「换一条」换备选，「采纳」跳转到记录并预填条目，
采纳后 `diet_advice.status = adopted`。agent 写回的建议与规则建议同表，UI 用 `source` 区分。

## 7. 与「自动化」「消息」插件的分工

### 7.1 职责边界

| 谁 | 负责 | 不负责 |
| --- | --- | --- |
| 饮食 `diet` | 数据、缺口计算、建议生成、文案、发消息、发域事件 | 什么时候触发、触发几次、要不要暂停 |
| 自动化 `automation` | 触发（定时/域事件/手动）、条件、限频、运行记录、暂停恢复 | 不理解饮食语义，也不该理解 |
| 消息 `message` | 提醒落点（消息中心 + 全局悬浮入口） | — |
| agent | 需要推理的部分：建议正文、周报点评、自然语言记账 | 不该用来做「每天 12:00 提醒」这种确定性动作 |

原则：**定时是自动化的事，内容是饮食的事，推理才是 agent 的事。**

### 7.2 三种接法

1. **action 模式（固定提醒首选）**：规则 `schedule / dailyAt 12:20` → 调 `diet.remindRecord`
   （不传参数，diet 自己判断今天缺哪一餐）。确定性、不耗 token、运行记录可查。
2. **agent 模式（需要推理的建议/周报）**：规则 prompt 写「调用 `diet.adviceContext` 拿今日缺口，
   给出晚餐建议，用 `diet.adviceSave` 写回并简短回复」。宿主每次投递算一次模型请求，适合一天
   1–2 次，不要做成每半小时。
3. **域事件模式（因果联动）**：diet 发 `meal.recorded`，automation 订阅 `diet / meal.recorded`
   加条件 `data.place == "takeout"`，再调 `diet.checkTakeout`。

### 7.3 diet 发出的域事件

| 事件 | 时机 | 载荷 |
| --- | --- | --- |
| `meal.recorded` | 新建一餐成功后 | `{ mealId, date, type, place, kcal, protein }` |
| `meal.updated` / `meal.deleted` | 修改 / 软删 | `{ mealId, date }` |
| `day.closed` | `diet.dayClose` 执行后 | `{ date, kcal, protein, mealCount }` |
| `phase.changed` | 新建/切换/结束阶段 | `{ from, to, goal }` |
| `advice.adopted` | 建议被采纳 | `{ adviceId, mealId }` |

事件只放摘要数字，不放整餐条目，避免事件总线被大对象拖累。

### 7.4 推荐的默认规则（引导创建，不硬编码）

| 规则 | 触发 | 执行 | 效果 |
| --- | --- | --- | --- |
| 午饭提醒 | 每天 12:20 | action → `diet.remindRecord` | 「今天午饭还没记」 |
| 晚饭建议 | 每天 16:30 | agent → 读 `adviceContext` 出建议 | 一天唯一一次模型请求 |
| 日报 | 每天 21:30 | action → `diet.dayClose` | 今日摄入与缺口摘要 |
| 外卖过多 | 域事件 `meal.recorded` | action → `diet.checkTakeout` | 连续第 3 顿外卖时提醒 |

**接入方式（已核对权限）**：`automation.ruleCreate` 声明了 `origins: ["ui","agent"]`，插件来源
（diet 用 `api.call` 走 `plugin`）**调不动**，所以不设计「饮食页一键建规则」的按钮。两条可行路径：

1. **对话代建（推荐）**：用户说「帮我建个每天 12:20 提醒记午饭的规则」，agent 直接调
   `automation.ruleCreate`（origin=agent，默认启用）+ 在自动化设置里勾选 `diet.remindRecord`；
2. **手动建**：目标页只展示这 4 条规则的参数与操作步骤，用户到自动化「规则」页照填。

目标页保留一个「去自动化配置」的跳转入口，不做假按钮。

### 7.5 约束与坑

- **白名单**：automation 的 `allowedActions` 默认空，必须勾选 `diet.*`；`*.delete`、`vault.*`、
  `automation.*` 是硬底线——饮食的记录删除天然不能被自动化触发，这正好符合预期。
- **来源陷阱（双向）**：自动化以 `plugin` 来源调 diet 的 action，diet 的提醒类 action 若照抄
  日历/联系人的 `origins: ["ui","agent"]`，会被直接拒掉——一律省略 origins（默认含 plugin）；
  反过来 diet 想替用户建自动化规则也走不通（`ruleCreate` 只开放 ui/agent），规则只能由人点或 agent 建。
- **去重**：提醒消息统一带 `dedupeKey: "diet-<类型>-<YYYY-MM-DD>"`，避免重复触发、重启补跑刷屏。
- **参数模板**：automation 的 action args 是静态 JSON，只能 `{{...}}` 取事件载荷；所有
  「今天还差多少」必须由 diet 的 action 现场算，不能写死在 args 里。
- **错峰**：默认时间取 :20 / :30 这类非整点，避开其他自动化规则与宿主的每小时上限。
- **时区**：`dailyAt` 带 tz，默认 `Asia/Shanghai`，跨时区旅行时提醒仍落在本地时间。
