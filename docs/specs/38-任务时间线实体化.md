## 0. 最新产品约束（覆盖原自动建线设想）

**时间线必须由用户独立手动创建。未指定时间线的任务没有时间线归属，不再默认拥有 self-id 时间线。** 新增 taskTimelines.create 与独立“新建时间线”UI；创建任务、source=1、归并、旧 payload 和重启均不得隐式创建实体。source=1 只能选择已存在且有效的线，不存在报 TIMELINE_NOT_FOUND，已删除报 TIMELINE_DELETED。普通 source=0 无归属；若同时传时间线参数，提示改用加入已有线的明确操作，不静默忽略或建线。

旧库分类与来源证据只用于待审阅报告，不能当作用户手动创建。历史组需用户审阅并明确批准恢复清单后才能回填；尚未批准的组保留旧数据但不作为新实体。实体已在其他设备手动创建后的同步，以及明确授权的新版完整备份恢复，是复制/恢复已有实体，不是依据任务 key 推断建线。阶段 2 已按此边界实施，历史回填尚未执行。

目标是一个时间线拥有多个任务、一个任务最多属于一个时间线的 **1:N** 关系。不是把一个任务复制到多条线。任务自身的树归属 table_id、重启链 restart_key 保持独立。合并通过移动 link，独立改名不再批量修改任务。

只读采样使用 sqlite3 -readonly 读取本机任务库：434 行任务（421 存活），411 行 key=self-id，0 行空 key；按全部历史任务分组为 413 个 key，其中 410 个 singleton self-id、3 个多成员组。非 self-id 单组或多成员组候选共 24 行（21 存活）。这些只是结构计数，不证明 410 个都是普通任务，也不证明 3 组均来自显式归并；正式 dryRun 必须重新采样。

## 2. 两表实际 DDL（仅提案，不执行）

时间戳沿用 INTEGER 毫秒；rev 每次真实变化加一。标题 title 是为“改名”额外提出的字段，description 独立存正文，避免把标题塞进描述。

```sql
CREATE TABLE IF NOT EXISTS task_timeline (
  id TEXT NOT NULL PRIMARY KEY,
  title TEXT NOT NULL DEFAULT '',
  description TEXT NOT NULL DEFAULT '',
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  deleted_at INTEGER,
  rev INTEGER NOT NULL DEFAULT 1 CHECK (rev >= 1)
);
CREATE INDEX IF NOT EXISTS idx_task_timeline_updated_at
  ON task_timeline(updated_at);

CREATE TABLE IF NOT EXISTS task_timeline_link (
  id TEXT NOT NULL PRIMARY KEY,
  task_id TEXT NOT NULL,
  timeline_id TEXT NOT NULL,
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  deleted_at INTEGER,
  rev INTEGER NOT NULL DEFAULT 1 CHECK (rev >= 1),
  UNIQUE(task_id)
);
CREATE INDEX IF NOT EXISTS idx_task_timeline_link_timeline_id
  ON task_timeline_link(timeline_id);
CREATE INDEX IF NOT EXISTS idx_task_timeline_link_updated_at
  ON task_timeline_link(updated_at);
```

约束与身份策略：

- id 为 TEXT，实体 id 沿用旧 key 的原字符串。独立手动建线 action 未指定 id 时生成新 id；旧 key 不改 UUID、不 trim 后重命名、不把 "001" 和 "1" 合并。
- link.id 固定等于 task_id（跨设备确定性身份），UNIQUE(task_id) 覆盖墓碑。移出软删同一行，重新加入或换线更新/复活同一行，不能再插一个随机 link.id。历史轨迹由 change log/备份保存。
- 无 link 或 link.deleted_at 非空均表示当前无归属；只有 link、timeline、task 三者存活才算有效成员。状态 3 仍保留归属，只在旧 timeline 查询展示时隐藏。
- 不加物理 FOREIGN KEY/ON DELETE CASCADE：当前同步可能先到 link 后到 task，且 core 采用 DELETE+INSERT 替换行；物理级联会误删。事务内业务校验完整性，同步暂存悬空引用、查询不展示、同步批次后校验/重拉；不凭悬空 link 自动复活已删线。
- 若将来转 M:N，除了去 UNIQUE(task_id)，还要改 link.id 规则与 API；“表形状可复用”不等于只删索引即可安全上线。

## 3. 问题 a–g 的明确答复

### a) 普通 self-id、显式单成员与重启的识别

不为每个普通任务建立实体。迁移先在**全量任务（包括 status=3、墓碑）**上按原 key 分组：

1. 空 key：无归属；保留原值在迁移清单中。
2. 多成员组或存在 task.id != key 的组：仅列入历史分组候选报告，待用户明确批准恢复后才整组沿用同 key（包括 id=key 的锚任务），不能逐行用 key!=id 过滤而漏掉锚任务。可能只是重启形成的组，不能据此自动建线；批准前保留旧数据。
3. 只有一条且 key=id：普通任务与显式单任务线在现表完全同形，**不可可靠识别**。默认不建实体/link，标记 ambiguousSelfId；即使有明确审计原始入参 source=1 或归并记录，也只是候选证据，必须用户审阅并确认恢复清单才纳入。普通 task change-log 全行 payload 未保存 source，不可把它当来源证明，也不能靠标题、rev、日期猜测。
4. 仅墓碑的历史组：经批准恢复后可保留墓碑实体/link，不产生可见线；存活组里的已删除任务以墓碑 link 保存归属历史。混合组存活任务建立活 link。

按最新产品约束，不再对普通 self-id 做 tasks.timeline 查询 fallback，否则用户仍会看到“每任务一条线”。timelineKey 与 timelineId 均只读有效实体，未归属/未批准恢复的旧 self-id 返回空结果，不创建、不展示伪时间线。旧 key 查询一致性验收只适用于用户批准恢复的历史线；未恢复组可在迁移审阅报告查询，不能混入正常时间线列表。参数名与返回外形兼容不代表保留已明确废弃的自动归组语义。

source=1 和归并都先验证目标已存在且存活，只加入明确选择的任务。即使 key 恰好等于普通任务 id，也不能创建线或自动带入锚任务。source=2 必须自动继承原任务已有效的同一实体归属，不能静默另选时间线；若同时传 timelineId/timelineKey，与继承值相同可接受，不同则返回 TIMELINE_INHERITANCE_CONFLICT。原任务无有效归属（包括线已删除）时，不执行重启，UI 提示“请先手动建立并关联时间线，再重启”；可引导手动新建或选择已有线并明确关联原任务，完成后由用户重新提交重启。API 返回结构化 TIMELINE_REQUIRED_FOR_RESTART，含原 taskId、原因及 nextActions，不自动建线、不用 restartKey/self-id 兜底。存在性与归属校验必须发生在关闭原任务、改状态3、写重启任务及任何变更日志之前，失败保留原任务及整条重启链原状；事务内重验以防并发删除/移出。

### b) 旧 key 保留

所有经用户批准恢复的分组、单成员组使用原值作为 task_timeline.id 与 link.timeline_id。时间线改名不改 id。旧聊天 key、客户端参数继续可查；数字旧参数仅做 String(value)，不重新使用旧迁移 Number(value)===0 规则。无法判别的 self-id 记录保留在迁移 manifest 与旧列，删除旧列前需保留审阅档案，但不提供普通任务时间线投影；任意异常原值须归档，不能静默丢弃。

### c) 标题、描述、改名与删除

- 独立手动创建时允许填写 title/description；未填 title 用“未命名时间线”。只有经批准的历史恢复可以取首条存活成员（publish_date,id 升序）标题作为**写入的标题快照**，无存活成员时也用“未命名时间线”。这样任务改标题不会隐式改线。空字符串标题输入可归一为该占位，但不改变 id。
- description 默认空串；UI 显示“暂无描述”，不把占位文字持久化进 description。
- 改名/改描述只写实体并发出 timeline/tasks 展示刷新事件。任务列表 join/batch 读取实体标题，避免 N+1；主文显示标题，悬停及复制操作提供完整 id。缓存按 timeline id 失效，不复制标题到 task。
- 删除线为软删，事务内软删所有活 link，保留任务及重启链，成员变为普通无归属任务；双写阶段 task.timeline_key 回写 NULL。回执包含影响任务数并支持 dryRun。删除不是删除任务。
- 删除任务时同事务软删对应 link 并更新线时间；最后一个成员离开后保留空线供重用，不自动删实体。恢复任务不隐式复活已删线；恢复归属须显式操作。实体墓碑默认不允许同 id 自动重建，须显式恢复，避免旧 payload 复活。
- timelineRefactor 支持互斥的 ids 与 timelineKeys：ids 仅移动指定任务；timelineKeys 在服务端选取全部有效成员（排除 status=3 与软删除，不受列表分页限制），目标 timelineKey 必须包含在选中 keys 内，每个 key 必须有有效成员，且目标须为已存在有效实体，不能懒创建。未来逐条更新既有 link.timeline_id，不新增多重归属。整线模式不搬隐藏历史成员，因此来源实体可能仍有历史 link，不能把页面空了视为可删；自动删除来源线不在此接口范围。不会改外部旧 id 为目标 id，也不承诺旧来源 id 自动跳转。

### d) updated_at 触发

实体在创建、标题/描述实质变化、成员加入/移出/换线、成员删除、线删除/恢复时更新 updated_at 与 rev；换线同时更新旧线和新线，一次事务每条线只递增一次。标题变化视为元信息变化。

任务 title/description/status/priority/date 等自身编辑不更新线；status=3 引起展示数量变化也不是成员变化。幂等加入同一线、重复提交相同标题/描述、重放同一 payload 不更新。UI 如需“最近任务活动”，用单独派生值，不混用实体 updated_at。迁移不伪造当前业务活动：初始 created_at 取该组最小历史 created_at、updated_at 取最大历史 updated_at，标明这是历史近似，rev=1；导入/同步用原始事件时间参与 LWW，不用接收时间覆盖。

### e) timelineId 与别名兼容

canonical 新参数 timelineId；timelineKey 至少保留一个完整发布版本且最长离线客户端升级完成后才讨论移除。input schema 同时声明两者，description 标 deprecated；capabilities 的说明/关系描述同步标注（不杜撰宿主未支持的字段）。两者相同接受，不同返回明确参数冲突；仅旧值也正常接受。同步/旧备份 timeline_key 在入口适配，不作为新 action 的遗漏字段。

返回中保留旧 timelineKey，新添 timelineId/title/description（以最终已发布结构为准）；无实体时 timelineId=null、timelineKey=null，不能输出 self-id。source=1 必须有规范化后的 id，验证已存在有效线后，事务内只创建任务和成员关系；已删除同 id 返回可恢复提示，不自动复活。idempotent dedupe 命中既有任务时不得顺便创建空线或改归属。

### f) 加表、回填、双写、切读、删列顺序

必须按第 5 节逐步执行。先扩展表及适配器，再可重跑回填，然后短双写窗口、影子比对、切读，最后才删列和 idx_task_timeline。删列不是首个迁移步骤；双写是应用事务，不是“失败后补写”。旧列只在双写窗口保留为兼容投影。删列后 wire payload 仍可保留 timeline_key 以服务旧设备，物理 schema 与传输契约分开演进。

### g) 旧客户端/云端 payload

入口兼容转换而不因 timeline_key 列已删报 SQL 错。覆盖 action、批量创建、旧库迁移、备份导入、同步 pull/snapshot/冲突回写/手动冲突解决，不只普通表单。

- 参数 source=1 + 旧 timelineKey 或明确 timeline_key 归组意图：仅关联已存在有效线，未知 id 返回明确业务错误（不再以兼容为由自动建线）；source=0 的普通 self-id 不建线。已有任务的旧 payload 未携带字段表示不修改归属，显式 null 表示移出（需走版本冲突判断）。
- 只有旧全行 payload、key=self-id 且无 provenance：按 a 的保守分类，不能断言显式单成员。key 非 self-id 也不能创建占位实体；目标未到达时暂存待解析引用，补拉已有实体，若根本不存在则记录待审阅/错误，不建立关系。目标存在墓碑则隔离冲突，不静默复活。
- 老客户端编辑任务正文可能回送旧 key；比较当前 shadow/wire 投影，key 未变则不产生 link 更新。跨设备“陈旧 key + 新任务时间戳”无法仅凭行级 LWW识别意图；兼容期冲突保留双方并要求消歧，不把正文编辑当作授权换线。优先采用有独立归属版本的新 payload；旧 payload 真正改 key 时只在新归属自已知旧投影版本后未变化才可转换。
- 删列后先抽取 timeline_key 转换为领域操作，再只将允许的 task 列交给 core；不能原样 Object.keys(payload) INSERT。同步转换事务回滚不得留下已删未插的 task 行。
- 回放同一旧事件不会二次建线、涨 rev 或重复推送。同步原样回写不进 change log；需要向新表补推的兼容转换以稳定事件标识/归属版本去重，防止循环。旧备份需按整包分组后转换，不能逐任务先行判断单成员。

独立 tasks.timelines 的当前工作不要求等待本设计实现。切换方案：将“列表展示模型”和“存储 provider”分开，以同一过滤器分别运行 legacy-key 聚合与 entity-join，在冻结快照对比；未归组 self-id 排除、隐藏状态、跨任务表计数必须沿用其已批准语义。实体化支持单成员/空线会扩展可列集合，需通过明示选项或版本说明，不偷偷改变旧默认。已核本次实现：tasks.timelines 返回 {records,total,current,size}，默认 pageSize=20、最大200；参数 titleKey/pageNumber/pageSize/includeSingletons，默认过滤 taskCount<2。记录字段 timelineKey/title/taskCount/openCount/doneCount/firstPublishDate/lastActivityDate 保持；openCount 仅状态0，doneCount 仅状态2，关闭任务计入 taskCount。lastActivityDate 取发布/完成/关闭日与创建/更新时间本地日最大值，不含计划 targetDate；按 lastActivityDate DESC,timelineKey ASC 排序。这个活动字段不能换成实体 updated_at，需另增 timelineUpdatedAt。titleKey 保持对列表标题的字面子串搜索；实体化后独立标题取代首成员占位属于预期展示升级。阶段 2 合并前再次核对最终 schema，新增字段采用兼容扩展。

## 5. 可审计迁移与分步回滚

### 5.1 迁移计划和 dryRun

阶段 2 实现单一纯分类器，供 dryRun/实际 apply 共用。建议计划参数 dryRun=true（默认）、approvedTimelineKeys、approvedSelfIds、excludedKeys、expectedSnapshotHash、batchSize、migrationVersion。dryRun 使用只读连接，不建表、不写 meta、不写审计/变更日志；只返回或导出审阅报告。正式 apply 在事务内重核 task 数、key、updated_at/rev 的快照摘要；不一致要求重跑计划，不能用陈旧报告覆盖新操作。

报告至少包含 scanned/live/deleted、distinctKeys、ordinaryOrAmbiguousSelf、approvedSelf、legacyGrouped、restartOnlyCandidates、emptyInvalidKeys、wouldCreateTimelines、wouldCreateLiveLinks、wouldCreateTombstoneLinks、existingIdentical、conflicts、skipped、wouldLog、源/目标计数，以及每个候选原 key、成员 id、分类理由。首次采样为结构候选 3 组/24 行，并非自动创建计划；未提供用户批准清单时 wouldCreateTimelines=0，候选/歧义单列，不能把 dryRun 报告当作批准。

apply 只处理用户批准的恢复清单，不能把分类命中当作手动创建授权；其余保留待审阅。以稳定 link.id=task.id 与原 key upsert；只填缺失行，不覆盖已经变更的实体标题、成员位置或墓碑。已存在同值跳过、不涨 rev、不写重复 log；不同值记录 conflict 并中止该批。不能用 INSERT OR IGNORE 把唯一键冲突吞成成功。每批实体/link/迁移日志/进度 checkpoint 同事务，崩溃可重跑；完成标记在全量校验通过后写入。启动只做已批准版本的安全恢复，不自动把 unresolvedSelfIds 判为显式。

迁移 manifest 保留原 task.timeline_key（包括异常空值）、组分类、旧时间戳/rev、创建的实体/link id、每批水位与版本、快照 hash；不存凭据。新表回填生成同步 change log 一次，不能只 INSERT 导致云端永远看不到；旧 task 未发生实变则不改 rev。

## 6. 同步、备份和数据页的联动

### 6.1 同步不是“声明两表”就结束

[repo.ts](/Users/yyq/code/dsh-workbench/packages/core/src/repo.ts#L62) 当前严格行级 LWW、远端等时间不同 payload 以服务端为准，使用远端所有列 DELETE+INSERT；[sync.ts](/Users/yyq/code/dsh-workbench/packages/shell/src/sync.ts#L306) uniquePolicy=lww-tombstone 只软删同唯一键的输家。**该策略不能处理本设计无条件 UNIQUE(task_id)：软删后仍占唯一键。** 因此采用确定 link.id=task_id，让并发归属变为同一行冲突；外部异常随机 link.id 在入口规范化或隔离，不能靠软删输家继续 INSERT。

[SDK DomainSyncTable](/Users/yyq/code/dsh-workbench/packages/sdk/src/index.ts#L91) 目前没有行级转换 hook，阶段 2 需设计领域级 normalize/apply hook 并覆盖 pull、snapshot、conflict-current、delete、人工 conflict-resolve；宿主不硬编码 tasks。该接口工作量是本设计实施前置条件。两新表注册 row 模式、纳入域 tables 与清理/备份清单。

云端 [SyncService.java](/Users/yyq/code/dsh-workbench/cloud/src/main/java/com/dsh/workbench/cloud/service/SyncService.java#L120) 目前按合法表名接受 JSON payload，检查 id/updated_at 一致、按时间戳 LWW，将行放入通用 row_states；未见任务专属列映射。新逻辑表不等于在云端创建两张物理业务表，但必须核对部署版本/能力与 schema 演进，不能假设现网已是此代码。旧云端 JSON 仍可能带 timeline_key，因此客户端必须转换，不能寄希望服务端自动删字段。

父实体/link 分表拉取可能乱序；先落候选、隐藏悬空关系，补拉父/任务，再校验。删除与并发加入冲突时墓碑实体阻止活成员可见，不自动“修复”为复活；保留冲突供用户恢复或移出。成员更新实体 updated_at 的本地事务不能提供跨表网络原子性，最终收敛校验负责补齐；不改变普通任务编辑不触线的规则。测试两设备同时将同一任务移向两条线、断网恢复、墓碑延迟与同时间戳冲突。

双写窗口旧设备仍只写 task key：桥接服务仅在已有有效实体且归属变更无冲突时生成 link 与日志，未知 key 待审阅，不补建线；新设备改归属须投影到旧 task wire。删物理列后，旧任务 payload 的投影 timestamp/rev 要以持久化兼容水位生成稳定版本（任务正文事件与归属事件合成版本），payload.updated_at 必须等于 envelope.updated_at，重复同步输出完全一致。不能只在发送时临时用 Date.now()，也不能沿用较老 task.updated_at 导致新归属被云端拒绝。具体水位存储沿用宿主 meta/sync state，阶段 2 接口评审先定契约；未完成不得进入 M5。

### 6.2 备份

新格式 schemaVersion=2，增加 taskTimelines/taskTimelineLinks，含墓碑及 created_at/updated_at/rev、兼容迁移版本；仍导出 tasks/taskNodes/taskDeps。支持 v1→分类审阅→用户批准恢复清单→v2 导入、v2 明确恢复已有实体；当前精确匹配版本判断必须更新。保留独立 v1 兼容导出选项时从 link 投影 timeline_key，并明确警告标题/描述/空线/显式 self-id 单成员无法完整表达；不可宣称 v1 round-trip 无损。

新格式导入先校验整个包，再在事务中恢复 timeline/task/link，保护 UNIQUE(task_id)；newest/skip/overwrite 三策略一致应用且报告逐表计数。墓碑不能因缺失数组被清空；新版归属优先于同包的旧投影，不双重执行。不存在/冲突父引用报告并保留诊断，不静默丢成员。重复导入不涨 rev/不重复日志。只有 v2 round-trip 才验收完整实体元数据和归属；v1 验收已能表达的关系及歧义报告。

### 6.3 数据页与客户端

两表加入只读数据页白名单，新增 timeline_id、title/description 中文列名，rev/deleted_at 仍按系统列展示。双写期旧列标“旧时间线键（兼容）”；删列后默认表不再列出它，旧排序/筛选请求转换为 join 投影或返回带替代列的明确兼容提示。数据页 count 默认含墓碑还是仅存活须保持其既有约定，并把实体成员数与物理 link 行数分开。

新 UI 增加独立“新建时间线”表单（title/description），任务创建中的时间线为可选的已有线选择器；不输入即无归属，source=1 必须选择有效线。创建线后显示空线详情及“添加已有任务”，不默认带入某个 self-id 任务；选择器需要列出空线与单成员线，不能直接复用默认过滤单成员的聚合列表。新 UI 区分无归属、空线、已删线，不把 self-id 当标题。三处显示改在客户端源文件，构建产物由 build:clients 生成；阶段 1 不构建不改包版本。

### 6.4 点击时间线按钮的空态

用户点击任务的时间线按钮时，查不到关联显示 **“没有关联时间线”**，不自动创建线，不回退查询 task.id/self-id 普通任务。过渡前端已按无 key、空结果及历史 self-id 单成员识别空态；这些启发式只适用于旧字段阶段。实体化后必须以当前任务的活 link、活 timeline 和活 task 判断实际关联，不能仅凭 key===task.id 或成员数为1判无关联，因为用户手动创建的合法单成员线也可能沿用该 id。

无有效关联返回明确的空态；已有有效关联但可见成员列表为空，应保留实体信息并显示“暂无可显示成员”，不能把数组为空直接当作未关联。查询/网络错误继续显示错误与重试入口，不伪装成“没有关联时间线”。在不破坏原 tasks.timeline 数组/分页返回形状的前提下，通过任务的 timelineId 或独立实体详情获取关联事实；不要把临时无数据转换成建线操作。
