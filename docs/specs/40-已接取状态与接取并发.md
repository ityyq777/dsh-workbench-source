# 已接取状态与接取并发（3.5.0）

## 1. 目标与边界

多 agent / 多会话同时处理任务时，需要显式表达「这条任务已被谁接走」，避免重复开工。本期新增状态 `4 = 已接取（CLAIMED）` 与三个 action：`tasks.claim`、`tasks.claimBatch`、`tasks.grab`。

不做：`tasks.release`（归还）、`claimNext`（候选池自动抢）、任务卡片展示 owner 主信息区、抢夺的 UI 入口。

## 2. 数据模型

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `owner` | TEXT 可空 | 接取者标识，缺省 `local`；agent 建议 `agent:<sessionId>`，最长 120 字符 |
| `claimed_at` | INTEGER 可空 | 接取时间（毫秒） |
| `claim_token` | TEXT 可空 | 每次 claim/grab 重新生成的 UUID，用于后续自动化写的 ABA 防护 |

迁移：`ensureTaskColumns` 幂等 `ALTER TABLE task ADD COLUMN`；`task_schema_version` 3 → 4，旧库升级后历史行三列为 NULL。

列不变量（写入层强制，不加 DB 约束）：

1. `status='4'` 时三列必须非空；
2. `status` 为 0/1/2/3 时三列必须为 NULL，进入终态时清空；
3. 软删除保留原值，便于审计。

## 3. 状态机

```
0 已开启 ──claim/grab──▶ 4 已接取 ──完成/关闭──▶ 2 已完成 / 1 已关闭
   ▲                        │
   └────grab（覆盖）────────┘

1/2/3 ──claim──▶ 拒绝（TASK_NOT_CLAIMABLE）
4 → 0：本期不提供（不使用 tasks.update 绕过）
```

- `0 → 4`：保留原优先级 P1..P10，不清零；`4` 视为「开启类」，`priorityForStatus` 放行。
- `4 → 2/1`：走现有更新流程，`priority=0` 并清空三列；带 `claimToken` 时先校验。
- `4 → 0`：拒绝，需要归还能力时显式设计 `tasks.release`。
- 重启：同一 `restart_key` 创建新任务（`source=2`）时，`status IN ('0','4')` 一律按「已开启」转关闭（最终进入重启链），并清空接取字段。
- `tasks.update` / `tasks.bulkUpdate` 直接写 `status=4` 一律拒绝（`CLAIM_REQUIRED`），避免绕过 CAS。

## 4. 并发语义（CAS）

单条接取只用一条条件 UPDATE，读 `run().changes` 判定，不做「先 SELECT 再判断」：

```sql
UPDATE task SET status='4', owner=?, claimed_at=?, claim_token=?, updated_at=?, rev=rev+1
 WHERE id=? AND status='0' AND deleted_at IS NULL
```

- `changes === 1` 成功；`0` 时再读一次行，仅用于区分「不存在 / 已删除 / 已被接取 / 不可接取」的失败原因。
- 批量接取整批 `BEGIN IMMEDIATE`，逐条同一 CAS；单条失败只进 `failed`，不回滚整批；结束只发一次聚合 `tasks-changed`。
- `grab` 的 WHERE 为 `status IN ('0','4')`，成功覆盖 owner 与 token，返回 `previousStatus/previousOwner/previousClaimToken` 供审计。
- `SQLITE_BUSY` 由 `taskTransaction` 映射为 `DATABASE_BUSY`（retryable）。

## 5. 错误码

| code | 场景 | 附加信息 |
| --- | --- | --- |
| `TASK_NOT_FOUND` | 不存在或已软删除 | `id` |
| `TASK_NOT_CLAIMABLE` | 状态不是 0（claim）/ 不在 0 或 4（grab） | `status`、`nextActions` |
| `TASK_CLAIM_LOST` | 带旧 token 写、或 grab 竞争失败 | `status`、`retryable` |
| `CLAIM_REQUIRED` | update/bulkUpdate 直接写 4 | `nextActions` |
| `DATABASE_BUSY` | 并发写锁冲突 | `retryable` |

## 6. Action 契约

| action | 必填 | 返回 |
| --- | --- | --- |
| `tasks.claim` | `id` | `{claimed:true,id,task,previousStatus,owner,claimToken}` |
| `tasks.claimBatch` | `ids` | `{requested,claimed[],failed[{id,reason,status?}],counts{claimed,alreadyClaimed,notClaimable,notFound,deleted,busy}}`；`dryRun:true` 只预览 |
| `tasks.grab` | `id` | `{grabbed:true,task,previousStatus,previousOwner,previousClaimToken,owner,claimToken,reason}` |

`reason` 稳定枚举：`already_claimed / not_claimable / not_found / deleted / busy`。批量中任何失败都不抛错。

## 7. 查询与统计口径

- `tasks.list`：`statuses` 接受 0..4；新增页签 `9 = 已接取`（`CLAIMED`）。
- `tasks.statsReport`：`totals.claimed` 单列，`breakdowns.status` 含 4（「已接取」）；`active` 仍只算 `status='0'`，两口径不相加。
- 逾期 / 今日到期 / 未来 7 天 / 逾期率分母按 `status IN ('0','4')`，文案注明「含已接取」。
- 逾期列表与账龄分布同步覆盖 4。

## 8. 同步与备份

- 同步 `normalizeTimelineTask`：incoming 缺 `owner/claimed_at/claim_token` 时保留本地值；显式 `null` 视为新值。
- 备份导出列白名单与 `taskValues` 增加三列；恢复旧备份默认 NULL；导入后 `status='4'` 但缺 owner/token 时返回 `claimWarnings`（`CLAIM_FIELDS_MISSING`），不静默通过。

## 9. 验收

对应 `scripts/test-task-claim.mjs`：

- schema v4，三列存在；
- 双连接并发抢同一条，恰好一个成功、另一个 `TASK_NOT_CLAIMABLE`；
- 重复接取 / 终态 / 不存在 / 非法 id 的错误码；
- ABA：旧 token 写被拒、当前 token 成功；
- 批量混合（可接取、已接取、不存在、已删除）不抛错、counts 准确、dryRun 零写入、只发一次聚合事件；
- grab 覆盖换 token 并返回 prev 字段，终态拒绝；
- 重启把已接取视作已开启；
- 列表 tab 9 / statuses[4] 与统计口径一致。
