# 47 · 凭据保险箱 0.2.0 复盘（评审稿）

> 状态：待评审 · 评审对象 `ac8e7d3`（vault 0.1.0 → 0.2.0）· 2026-11-13
> 关联：[46 连接器与凭据保险箱方案](46-连接器与凭据保险箱方案.md) §7.9–§7.11、[22 站点模块迁移二期](22-站点模块迁移二期.md) §3
> 本文只复盘**已经落地的 0.2.0**，不改代码；文末列出需要拍板的点。

## 1. 结论摘要

0.2.0 把保险箱从「两表 KV + 不参与同步」改成「七表模型 + 密文上云 + 分组/关联」，同时把口令下限提到 12 位、并发改口令定为 LWW。功能闭环已通，测试 6 个全绿，desktop profile 已装 0.2.0（**进程仍需重启**）。

三个必须知道的代价：

1. **两套保险箱仍然并存**：sites 的账号保险箱原样不动，用户可能要记两个口令（sites 一套、vault 一套）；
2. **密文与元数据上云**：云端可见 salt/kdf/wrapped_dek、凭据名、组名、绑定关系，离线爆破风险取决于口令强度；
3. **回退没有工具**：schema 只做了向前迁移（`vault_meta` → `vault_meta_legacy`），没有任何反向迁移脚本；退回 0.1.0 会看不到已有凭据。

## 2. 变更清单（0.1.0 → 0.2.0）

| 面 | 0.1.0 | 0.2.0 |
| --- | --- | --- |
| 表 | `vault_meta`（KV）+ `vault_secret` | `vault_header` / `vault_device` / `vault_secret` / `vault_group` / `vault_binding` / `vault_subject_type` / `vault_secret_usage` |
| 云同步 | `sync: { tables: [] }` | 5 张表声明：header（键 `id`，lww）、secret（`id`、`name`，lww-tombstone）、group（`id`、`name`，lww-tombstone）、binding（`id` 与 `subject_type+subject_id+group_id`，lww-tombstone）、subject_type（`id`、`type`，lww-tombstone） |

| 并发改口令 | 未定义 | LWW：`passphrase_rev` 递增，另一台解锁时提示「口令已在其他设备修改」 |
| 视图 | status / secrets / config / data / actions | 增 `groups`；secrets 带分组筛选，status 加分组数 |
| 迁移 | — | `ensureSchema` 自动迁移；旧表改名 `vault_meta_legacy` 保留一版；幂等 |

## 3. 关键取舍复盘

| # | 决策 | 备选 | 为什么这么选 | 代价 / 已知缺口 | 回退难度 |
| --- | --- | --- | --- | --- | --- |
| 1 | 独立 `wb-addon-vault` 域（沿用 0.1.0） | 宿主内建服务，sites 委托 | 不动 sites、可独立发版与回滚；形态上是「数据归 vault」而非「平台能力」 | 与 sites 两套保险箱并存，口令不统一 | 中（改宿主需动 shell） |
| 2 | 拆成七张表 | 单表 + KV 元数据 | 同步引擎按表声明、按 `id` 对齐行；device/usage 必须留本机，只能分表 | 迁移代码 + 多表 join；`vault_header` 只能单行 | 中（legacy 表在） |
| 3 | `vault_header` 单行 | 多行版本化 header | salt/wrapped_dek 是全局密钥材料，天然单例；`rev` 递增便于冲突判断 | 每次解锁多一次查询；两设备并发 setup 未做互斥 | 低 |
| 4 | `vault_device` 留本机 | 随密文同步 device 包裹 | device key 是本机文件（0600），同步它等于把「自动解锁」复制到所有设备 | 换机必须重输口令；device key 丢失需重设解锁模式 | 低 |
| 5 | `vault_secret_usage` 留本机 | 保留 `vault_secret.last_used_at` 并同步 | `last_used_at` 每台设备不同，同步会制造无意义冲突与写放大 | 列表/租约多一次 join；数据页看不到 last_used_at | 低 |
| 6 | `vault_subject_type` 用 `id` 主键 | `type` 主键 | 宿主 `applyIncoming` 按 `WHERE id=?` 对齐行（`packages/shell/src/sync/sync-incoming.ts:17-24`），没有 `id` 的表无法同步 | 多一列 + 唯一索引；注册逻辑要先查 `type` 再 UPDATE | 低 |
| 7 | 分组与绑定由 vault 持有 | 业务方自己存 `group_id` / 混合 | 用户明确要求「跟 tag_mapping 一样由保险箱维护」，模块只注册自身标识 | vault 不校验 `subject_id` 是否存在，删除业务对象后 binding 会悬空（提供 `bindingPurge`，需业务主动调） | 中 |
| 8 | 同名冲突 `lww-tombstone` | 报错要求手工合并 | 同步场景无法阻塞；宿主已有 `conflict_shadow` 留底 | 两台设备各建同名凭据时，较旧那条会被软删 | 低 |
| 9 | 无运行时同步开关 | 加 `sync.enabled` | SDK `DomainSyncDef` 只有 `tables`，没有开关能力；加开关要改宿主协议 | 用户不能「先不同步」；不配云只能靠不登录/不启用同步 | 高（改宿主） |
| 10 | 并发改口令 LWW | 加 rev 强制提示 / 要求唯一在线设备 | 用户在 2026-11-13 明确选 A：简单、不阻塞 | 先改的那台口令静默失效，只在下一次解锁提示 | 低 |
| 11 | 口令 ≥12、N=2^16 | 维持 10 位 / 2^15 | 密文上云后可离线爆破，必须抬成本 | 解锁更慢（测试里 unlock/改口令约 300ms 级），老用户口令可能不合规（未强制改） | 低 |
| 12 | AAD 不含 `group_id` | AAD 纳入组 | 改组不触发重加密，批量挪组是 O(1) 行更新 | 本地/云端能改 `group_id` 而不破坏 GCM 校验 → 越权改组的唯一屏障是接口与审计，不是密码学 | 中（v2 密文格式 + 迁移） |
| 13 | `lease` 带 subject 校验 binding | 只按 secret id 租 | 「按组授权」要能落地：站点/连接器只能拿到自己组内的凭据 | 每次租约多一次 binding 查询；未绑定对象直接报错（匿名 RSS 无影响，它本来不用 secret） | 低 |
| 14 | 备份不导密文（沿用 0.1.0） | 备份含密文 | 备份文件会同时含 wrapped_dek，等于把可离线爆破的包给出去 | **迁移 sites 后凭据不在任何备份里**，换机只能靠同步 | 待定（见 §7） |

## 4. 与 46 文档 v2 的一致性

已核对，文档与代码一致的点：七表 DDL、同步声明与 uniqueKeys、`subjectSecrets`、`subjectsOf` 返回 `subjectType/subjectId/title`、setup 口令 ≥12 与 `syncNote`、`secretCreate/Update` 参数名为 `secret`、`subject_type` 用 `id` 主键、`vault_secret_usage` 留本机。

未在文档中写清、只在代码里的行为（建议补文档）：

- `groupDelete` 的 `moveTo` 必须指向**现存且未删**的组，否则报「目标分组不存在」；
- `bind` 对已软删的旧行做复用（同三元组重新置 `deleted_at=null`），否则会撞唯一索引；
- `setup` 不检查 header 是否已存在——**同一账号在两台设备各自 setup，后写的会覆盖 header**，先写设备的口令随即失效；
- `syncStatus` 的 `pending` / `conflicts` 目前固定为 `null`（宿主没有暴露按域的待同步计数）。

## 5. 风险清单

| 风险 | 影响 | 现状 | 建议 |
| --- | --- | --- | --- |
| 两套保险箱、两个口令 | 用户困惑；「我明明设过口令」 | sites 1.10.0 内联，vault 0.2.0 独立 | 由 48 号方案收敛；过渡期在 vault 设置页与 sites 账号页互相提示 |
| `group_id` 不在 AAD 内 | 能改库/能改云端行的人可把凭据挪到别的组，租约随之放行 | 未防护 | 接受（本机攻击者本就等同 root），或在 v2 密文格式把 `group_id` 纳入 AAD，代价是每次挪组重加密 |
| binding 悬空 | `subjectsOf` 出现已删除对象；`subjectSecrets` 仍可被旧 id 调用 | 提供 `bindingPurge` | 业务删除时调 purge；sites 迁移时一并实现 |
| 云端元数据泄露 | 凭据名/组名/绑定关系暴露业务结构（不含明文） | 已上云 | 文档明示；敏感命名由用户自律 |
| 两设备并发 setup | 后写覆盖 header，先写设备口令失效且**无提示** | 未处理 | `setup` 前先 pull/检查 header；存在则拒绝并提示「已初始化，请解锁」 |
| 内存明文无法清零 | 租约窗口内可由同机进程读取 | 短租约 30–300s | 文档已明示，接受 |
| 回退无工具 | 退回 0.1.0 看不到凭据 | legacy 表只保留了旧 header，不含新 secret 的 0.1.0 形态 | 若要支持回退，需写反向导出（解密 → 0.1.0 格式） |
| 并发 LWW 口令 | 旧设备静默用旧口令失败一次 | 有提示文案 | 接受（用户已选 A） |

## 8. 如果重来

- 会把「分组/关联」与「云同步」分成两个 PR：前者不动加密与表结构（只加 `group_id` + 三表），后者才拆 header/device 并动密文归属；混在一个提交里，出问题时难以判断是分组还是同步引起的。
- 会在 0.1.0 就把 `subject_type` 设计成 `id` 主键——这是同步协议决定的，早做省一次迁移。
- 会把「sites 迁移」和「vault 分组」绑定评审：分组能力的第一个真实用户就是 sites，没有迁移，分组只是空转。
