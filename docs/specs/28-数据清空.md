# 28 · 数据清空（宿主本机 + 私人云端）

> 状态：已实现。宿主 `dsh-workbench` 0.10.7、私人云端 `dsh-workbench-private-cloud` 0.2.0。
> 唯一目的：把「数据全没了、从头再来」变成一个有确认、有回执、可重复执行的操作，
> 而不是让用户去删 `workbench.db` 或 `~/.dsh/workbench`。

## 为什么要做

备份页只有导出/导入，导入还刻意只合并不删除（见 [15-数据备份](./15-数据备份.md)）。
用户想彻底重来时只能手删数据库文件，这有三个问题：删文件要求宿主先停、容易留下
`-wal`/`-shm` 兄弟文件、也不清 `cloud-config.json` 一类状态文件。私人云端同理：
清空数据目录会连 PID 文件、日志一起删，服务身份（`instance_id`）也跟着换。

因此两侧各提供一个**只清数据、不动库文件与配置结构**的入口，并要求输入确认词。

## 口径

| 问题 | 结论 |
| --- | --- |
| 宿主清空什么 | 全部业务表 + 各插件配置表 + 同步元数据（游标、影子表、死信）+ 云端连接与凭据文件 |
| 宿主保留什么 | 表结构、库文件、插件安装状态、端口与进程；清完立刻可用，不需要重启 |
| 云端联动 | **只清本机**；清空后云端连接回到默认「共享云端 + 未登录」，不会去删私人云端的数据 |
| 私人云端清空什么 | 与同步相关的 7 张表 + `blobs/`、`tmp/` 目录 + `meta` 里除 `instance_id` 之外的内容 |
| 私人云端保留什么 | 库文件、`instance_id`（服务身份）、访问密钥、端口与日志 |
| 谁能触发 | 宿主：备份页（界面）与 `POST /workbench/api/data/clear`；云端：概览页、CLI、`POST /v1/admin/clear` |

自动断开而不是继续同步，是因为两边同时清时顺序无法保证：如果本机清了、云端还有数据，
下一轮同步会从云端把数据拉回来，看起来像「清空没生效」。断开后同步只会由用户显式重连触发。

## 宿主实现

| 文件 | 作用 |
| --- | --- |
| `packages/shell/src/infra/data-clear.ts` | 清库、清状态文件；导出 `CLEAR_CONFIRM`、`listDataTables`、`clearDatabase`、`clearHostFiles` |
| `packages/shell/src/infra/network.ts` | `POST /data/clear` 路由：校验确认词、拒绝在同步中执行 |
| `packages/shell/src/index.ts` | `clearAllData()`：清库 → 删文件 → 重载云端配置 → 广播事件，作为依赖注入给 `installNetwork` |
| `packages/shell/client/backup-tab.cjs` | 备份页底部的危险区（确认词输入 + 结果回执） |
| `packages/shell/client/locale.cjs` | `clear_*` 中英文案 |
| `packages/shell/client/styles.cjs` | `.wb-danger*` 样式，只用主题 token |

要点：

- 业务域的 `setup()` 只在安装时跑一次，闭包持有同一个 `DatabaseSync`；因此**不能**换库句柄或删库重开，
  只能在同一连接上逐表 `DELETE`。表名从 `sqlite_master` 现查，不维护清单，插件新增表自动覆盖。
- `DELETE` 在 `BEGIN IMMEDIATE` 事务里执行，失败整体回滚；成功后 `DELETE FROM sqlite_sequence`
  （清掉 `AUTOINCREMENT` 计数）、`wal_checkpoint(TRUNCATE)` 与 `VACUUM` 都是尽力而为，失败不影响结果。
- 状态文件删三类：`cloud-config.json`、`cloud-creds.json`、`vault-device.key`。删掉后 `loadCloudConfig()`
  返回默认的共享云端配置，`state.creds = null`，等价于刚装好、未登录。
- 返回 `{tables, rows, names, files, cloud}`：`names` 是被清的表名，便于日志与界面回执；
  `files` 是实际删除的文件名，没有文件时是空数组。

### HTTP 契约

```http
POST /workbench/api/data/clear
content-type: application/json

{"confirm": "清空全部数据"}
```

| 情况 | 状态码 | body |
| --- | --- | --- |
| 成功 | 200 | `{"ok":true,"tables":24,"rows":32,"names":[...],"files":["cloud-config.json"],"cloud":{...}}` |
| 确认词不对 | 400 | `{"ok":false,"code":"confirm_required","error":"请先输入「清空全部数据」确认","confirm":"清空全部数据"}` |
| 正在同步 | 409 | `{"ok":false,"code":"sync_running","error":"正在同步，请稍后再试"}` |
| 执行异常 | 500 | `{"ok":false,"code":"clear_failed","error":"..."}` |

确认词同时出现在服务端的 `CLEAR_CONFIRM` 与客户端的 `clear_phrase` 文案里；
改一处必须改两处，`scripts/test-data-clear.mjs` 会拦住不一致。

## 私人云端实现

| 文件 | 作用 |
| --- | --- |
| `cloud-private/src/admin.js` | `CLEAR_CONFIRM = "清空云端数据"`、`clearAllData(db, dataDir)` |
| `cloud-private/src/server.js` | `POST /v1/admin/clear`，走同一套 Bearer 鉴权与错误格式 |
| `cloud-private/src/dashboard.js` | 概览页「数据清空」卡片，确认词匹配后才启用按钮 |
| `cloud-private/bin/wb-private-cloud.mjs` | `clear [--yes]` 子命令 |

要点：

- 清空的表固定为 `change_log`、`row_states`、`sync_table_state`、`sync_sessions`、`devices`、
  `blob_refs`、`blobs`；`meta` 用 `DELETE FROM meta WHERE k <> 'instance_id'` 保留身份。
- `blobs/` 与 `tmp/` 目录删掉后**重新创建**：上传逻辑会自己 `mkdir -p`，但概览页与测试都假设目录存在。
- 服务运行中时，CLI 不直接写库，而是发 `POST /v1/admin/clear`：两个进程同时写会撞锁，
  也会让运行中的同步会话指向已删除的行。服务没跑时才 `openDb()` 直接清。
- 非交互环境必须显式 `--yes`；交互环境要求原样输入确认词，输错即取消（退出码 1）。

### HTTP 契约

```http
POST /v1/admin/clear
authorization: Bearer <密钥>
content-type: application/json

{"confirm": "清空云端数据"}
```

成功返回 `{"ok":true,"tables":7,"rows":42,"blobs":3,"devices":2,"cleared_at":"2026-11-22T13:40:00.000Z"}`；
确认词不对 400 `confirm_required`（body 里带 `confirm` 提示词），未带密钥 401。
清空不结束进程、不换 `instance_id`，`/v1/health` 与 `/v1/sync/open` 立即可用。

## 测试

```bash
pnpm test:data-clear      # 宿主：临时 WB_HOME，确认词、清空范围、文件删除、句柄可写、幂等
pnpm cloud-private:test   # 云端：test/clear.test.mjs 覆盖确认词、鉴权、清空后统计与文件、重复清空
```

两侧测试都只用 `mkdtemp` 出来的临时目录，**不得**指向 `~/.dsh/workbench` 或 `cloud-private/data`。

## 不在范围

- 不清插件安装、不卸载 addon、不重置端口/密钥；
- 不做「只清某个模块」——那是备份页勾选导出的语义，清空是全局兜底；
- 不自动清对方一侧的数据；宿主与云端都必须各自确认，避免误删另一台设备的数据。
