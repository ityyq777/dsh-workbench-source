# 插件功能清单（Tool 与 Action）

> 适用版本：宿主 `dsh-workbench` 0.8.2（SDK `@wb/sdk` 0.2.2）；任务插件 5.2.33；标签插件 1.7.5；站点插件 1.12.7；储物插件 1.5.9；消息插件 0.1.3；凭据保险箱插件 0.3.11；连接器插件 0.1.5；自动化插件 0.2.4；联系人插件 0.1.4；日历插件 0.1.4；邮件插件 0.5.3；工资插件 0.4.1；弹幕插件 0.2.4。
>
> 本文列出 **DSH agent 能发现与调用的 tool、action**，以及默认不对 agent 开放但界面可用的 action（标 `agentEnabled:false` 可开关、`agentLocked:true` 永远锁死）；客户端按钮、视图内部函数不在范围内。字段级 schema 以运行时 `actions.help` 为准。

> 插件之间“谁依赖谁、缺了会怎样”见 [`插件依赖关系.md`](./插件依赖关系.md)。

## 1. 调用链

```text
DSH Agent
  └─ Workbench（唯一 tool）
       ├─ capabilities.list / capabilities.get   宿主元 action：插件记录什么
       ├─ actions.list / actions.help            宿主元 action：action 的真实字段
       ├─ actions.setAgentAccess                 宿主元 action：逐个开/关 agent 可调用（仅界面）
       └─ <plugin>.<action>                      业务插件注册的 action
            ├─ tasks.* / taskNodes.*
            ├─ tags.*
            └─ sites.* / siteTags.* / siteNodes.*
```

关键点：

- 业务插件不各自注册 DSH tool，只向宿主注册 action；DSH 只看到 `Workbench` 一个工具。
- `Workbench` 的 `action` 是命名空间字符串，`args` 是该 action 的入参。
- action 名稳定；字段可能演进，调用前用 `actions.help` 确认，不要按旧顶层 schema 猜。

## 2. Tool 清单

### 2.1 `Workbench`

| 项 | 内容 |
| --- | --- |
| 名称 | `Workbench` |
| 注册方 | 宿主 `dsh-workbench` |
| 用途 | 个人工作台统一入口：任务、标签、站点、能力发现 |
| 超时 | 60s |
| 入参 | `action`（必填）、`args`（对象，选填） |
| 返回 | `{ text }`，agent 直接读文本 |

调用示例：

```js
Workbench({
  action: "tasks.create",
  args: { title: "整理发布清单", tablePath: ["开发", "发布管理"], priority: 7, difficulty: 2, targetDate: "2026-11-10" }
})
```

注意：

- 参数必须放 `args`。旧版顶层字段仍兼容，但会按 action 的真实 schema 校验；`due_at` / `tags` / `parentId` 等假字段会明确提示“已忽略”。
- 不带命名空间的旧 action 会映射到 `tasks.*`；新调用请写全命名空间。
- 插件安装/卸载不在本工具里做，走 DSH 插件管理。

### 2.2 为什么没有“每个插件一个 tool”

如果 tasks/tags/sites 各注册一个 tool，DSH 会同时看到三个大 schema，参数重叠且难以维护。现在用一个 `Workbench` + 每个插件自己的 action：

- `capabilities.*` 回答“这个插件记录什么、首选哪个 action”；
- `actions.*` 回答“这个 action 的真实字段是什么”；
- 业务 action 只负责执行。

### 2.3 审计日志（`audit.*`，宿主元 action）

宿主在唯一的 action 分发点记录本机行为账本：谁（`agent` / `ui` / `sync`）在何时调了哪个 action、成功与否、耗时、目标与（脱敏后的）参数。只读 action 默认不记，`capabilities.*` / `actions.*` / `audit.*` 自身不记。

| action | 用途 | 关键参数 |
| --- | --- | --- |
| `audit.list` | 查询审计记录（按时间倒序分页） | `action` / `actionPrefix` / `actor` / `domain` / `ok` / `q` / `target` / `since` / `until` / `page` / `pageSize`（≤200，默认 50） |
| `audit.get` | 单条详情 | `id`（必填） |
| `audit.stats` | 近 N 天汇总（总数/失败数/按 action/按入口/按天） | `rangeDays`（默认 30） |
| `audit.prune` | 清理早于保留期的记录 | `retentionDays`（1~3650，缺省读 `meta.audit.retentionDays` 或 90） |

约束：

- 表 `audit_log` 是平台表，不登记进任何业务域，**不参与同步与备份**；
- 参数中的密码、token、cookie、API key、保险箱/密文等键名一律写成 `***`；单字段超 2000 字符截断，参数整体超 12KB 折叠为 `{"truncated":true,...}`；
- 只读 action 需要留痕时设置 `meta.audit.recordReads=1`；
- 默认保留 90 天，启动时清理一次，之后每 200 次写入惰性清理。

客户端首页「管理」区有「审计日志」卡片（`GET /workbench/api/audit`，支持 `stats=1&rangeDays=30`）。宿主 0.6.4 起，筛选变化立即查询，过期响应不能覆盖当前结果；默认全部且不持久化。结果筛选有明确标签、当前筛选反馈和清除入口，查询按钮保留用于重试。近 30 天统计为独立全局口径，界面明确注明不受筛选影响。

### 2.4 跨域搜索（`search.*`，宿主元 action）

宿主把各业务插件注册的搜索 provider 聚合起来，插件不跨域读表。

| action | 用途 | 关键参数 |
| --- | --- | --- |
| `search.query` | 并行搜索已注册 provider，统一打分排序 | `q`（必填，1–100 字）、`domains`（限定域 id）、`limit`（默认 20，最大 50） |
| `search.providers` | 列出已注册 provider，供 UI 筛选 | 无 |

单域超时 500ms 或抛错不影响其他域，结果带 `partial=true` 与 `failed` 域列表；空查询不调用 provider。已注册 provider：`wb-addon-tasks`、`wb-addon-tags`、`wb-addon-sites`、`wb-addon-connector`。客户端首页搜索框与 `Cmd/Ctrl+K` 面板走同一套 action。

## 3. 能力发现顺序

1. `Workbench({ action: "capabilities.list" })` — 所有插件的能力摘要；可传 `kind` 过滤（`task` / `site` / `tag`）。
2. `Workbench({ action: "capabilities.get", args: { domain: "tasks" } })` — 单插件完整清单：字段字典（方向/范围/默认值）、记录时机、不要记录、去重、关系、示例、action 列表。
3. `Workbench({ action: "actions.list", args: { domain: "tasks" } })` — action 参数与必填项。
4. `Workbench({ action: "actions.help", args: { action: "tasks.create" } })` — 完整 JSON Schema 与示例。
5. 调 `primaryAction`。

`domain` 可写完整 id（`wb-addon-tasks`）或短名（`tasks`）。未声明能力的插件仍会在 `capabilities.list` 中出现，`source` 为 `fallback`，此时直接用 `actions.list`。

每个 action 还有一个**本机**的「agent 可调用」开关：`actions.list` / `actions.help` / `capabilities.*` / `<域>.actionSchema` 的条目带 `agentEnabled`（界面 schema 另带 `agentLocked`），界面的 Action 页可逐个开或关。关闭后 agent 在下一次发现里看不到它、硬调得到结构化错误 `ACTION_AGENT_DISABLED`；界面 `origin=ui` 永远不受影响，`plugin` / `sync` 也不看这个开关。开关存宿主库 `meta`（键 `config.wb-shell.actionAgent.<action>`），不写同步日志、不进备份、换机即回到默认值。两类「开关也打不开」的固有锁定单独说明：宿主内置的 `actions.setAgentAccess`（打开它等于打开一切，永久锁死）与插件声明 `agentLocked: true` 的 action（保险箱 21 个敏感与数据类操作，agent 永远调不到）。详见 8.0 节的开关说明。

## 4. 宿主能力与动作发现 action（6 个）

| Action | 说明 | 入参 | 返回重点 |
| --- | --- | --- | --- |
| `capabilities.list` | 列出各业务插件“记录什么、首选哪个 action” | `kind?` | `domains[]`：summary、records、source、actionCount、warnings |
| `capabilities.get` | 查看单个插件完整能力清单、字段字典与 action 列表 | `domain` 或 `id` | `capability`（fields/records/when/notFor/dedupe/relations/examples）+ `actions[]` + warnings |
| `capabilities.setTaskTarget` | 显式设置业务域对应的开发任务表；null 清除配置，不猜测、不自动建表 | `domain`, `tableId` | 返回配置状态与有效目标路径；失效映射明确提示未配置 |
| `actions.list` | 列出 action、参数与必填项 | `domain?`、`detail?` | `domains[]`、`actions[]`；`detail:true` 带 input schema |
| `actions.help` | 单个 action 的完整 schema、参数说明、示例 | `action`（或 `name`） | `input`、`params`、`examples` |
| `actions.setAgentAccess` | 打开/关闭某个 action 的 agent 可调用开关（**仅界面**；开关只存本机 meta，不参与同步与备份） | `action`（必填）、`agentEnabled`（必填布尔）、`domain`（可选，校验 action 归属） | 返回生效值与来源（`meta`/`declared`）；agent 永远不可调用，开关自身也永久锁死 |

> 注意：站点插件还有一个业务 action `sites.capabilities`，返回 `tags`（标签子插件是否可用）、`overviewAction: "siteNodes.overview"` 与 `placementGuidance`（先看目录概览再创建站点的归属引导）；它不是宿主元 action `capabilities.*`。

## 4.1 自描述约定（字段字典）

agent 只能看到 tool 自描述，所以每个插件必须在 `capability.fields` 里声明字段字典：`{ name, type, description }`，`description` 要说清**方向 + 取值范围 + 默认值 + 特殊值含义**。`capabilities.get` 会把字典渲染成「字段字典（方向/范围/默认值以此为准）」，并在缺失时给出 warning。

约定：

- 方向必须写死（例如 `priority` 已开启任务是 `1..10`、关闭/完成为 `0`，**数值越大越紧急**，`>=6` 进紧急页签；不要指望 agent 从 “priority” 猜方向）；
- 枚举必须列全（`status` 0=已开启 / 1=已关闭 / 2=已完成 / 3=已重启 / 4=已接取；`statuses` 是 0..4 的整数数组，缺省不过滤状态）；
- 高风险语义写进 **action 描述**，而不是只放文档：`tasks.bulkUpdate` 的 `tags/tagIds` 是整体替换、`tasks.update` 的 `type` 是更新模式而不是任务类型、`tasks.list` 不传 `statuses` 且不传 `urgent` 时返回全部状态（含 3 已重启）；
- 返回结果必须回显生效条件（`filter`）与排序方向，agent 才能自查。

## 4.2 依赖降级（requires）

任务与站点都依赖标签插件提供 `tag` / `tag_mapping` 表，但**表归标签插件所有**：两个插件只读写 `tag_mapping` 里属于自己 `item_type` 的行，不建表、不迁移。为了在没装标签插件时也不骗人：

- 能力清单可以声明 `capability.requires: ["wb-addon-tags"]`；宿主 `capabilities.get/list` 计算 `missingRequires`，缺依赖时在 `warnings` 里追加「依赖未安装：wb-addon-tags；相关参数（如 tagIds/tags）会报错，其余功能正常」，`capabilities.get` 文本还会单列一行「依赖：wb-addon-tags（未安装）」。
- **站点**：传了标签参数（`tagIds`、`tags`、`addTags` 等）却缺标签域时必须抛可读错误「标签域未安装（未安装 dsh-workbench-tags 插件），无法…；去掉参数即可继续」，**不能**抛底层 SQL 错误、也不能静默丢弃或返回空列表。
- **任务**（2026-11-09 起）：标签是可选能力，缺域时不阻断写入——忽略标签参数、正文照常落库，回执带 `notices: [{code:"tag_domain_missing"}]`；读侧省略 `tags` 字段、按标签筛选返回空结果、`groupBy=tag` 返回空分组、`tasks.tags` 返回 `available:false`；客户端隐藏标签输入与筛选。契约测试同样在 `scripts/test-nodeps.mjs`。
- 不带标签参数时两个域的功能完全不受影响（增删改查、统计、数据页、表索引都正常）。
- `tag_mapping` 的同步声明只在标签域（整表行级同步，不区分 `item_type`）；站点域不再重复声明同一张表。站点备份仍导出 `item_type='site'` 的映射行，因为那是站点自己的数据（标签域没装时备份导入会跳过该表）。

契约测试在 `scripts/test-nodeps.mjs`（`pnpm test:nodeps`）：分别只装载「宿主 + 任务」「宿主 + 站点」，断言上面每一条。

契约测试在 `scripts/test-native.mjs` 的「4.3 自描述契约」段：断言字段字典存在且方向/范围正确、`tasks.list` 不传 `statuses` 时不做状态过滤、`sort=-priority` 真的把数值大的排前面、`bulkUpdate` 的 tags 整体替换与 `addTagIds` 增量的行为与描述一致。改实现或改描述时两边必须同时改，否则测试失败。

## 4.3 首页栏目分组（host 0.8.2 / sdk 0.2.2）

首页从「所有插件平铺一张网格」改成按栏目分段：栏目由宿主定义（顺序、中英文名、兜底项），
插件在注册阶段只声明自己属于哪个栏目。

- 契约：`DomainDef.category?: string` 声明栏目 id；`DomainPublicInfo.category: string` 回传
  宿主解析后的结果；`GET /workbench/api/domains` 额外返回 `categories: DomainCategoryInfo[]`
  （`{ id, title: { zh, en }, fallback }`），顺序即首页顺序。
- 栏目表：`packages/shell/src/infra/categories.ts` 的 `HOME_CATEGORIES`——`work` 工作与计划、
  `comm` 沟通与消息、`assets` 资产与资料、`finance` 财务、`auto` 自动化与集成、`other` 其他（兜底）。
  栏目 id 一旦发布只能新增，不能改名。
- 校验与兼容：未声明、空串、未知 id 一律落 `other`，宿主打一条日志（`业务域未声明首页栏目…` /
  `业务域声明了未知栏目 id…`），不阻断注册；客户端拿不到 `categories` 时回退旧的单网格渲染。
- 首页渲染：每个栏目一段标题（栏目名 + 插件数）+ `.wb-home-grid`；空栏目不渲染，栏目内保持注册顺序。
- 当前划分：任务/标签/日历 → `work`；邮件/消息/联系人/弹幕 → `comm`；储物/凭据保险箱/站点 → `assets`；
  工资 → `finance`；自动化/连接器 → `auto`。回归：`pnpm test:home-categories`。

## 5. 任务插件 `dsh-workbench-tasks`

| 项 | 内容 |
| --- | --- |
| 包名 | `dsh-workbench-tasks` |
| 域 id | `wb-addon-tasks` |
| 版本 | 5.2.25 |
| 表 | `task`、`task_node`、`task_timeline`、`task_timeline_link`、`task_workspace`、`task_workspace_link` |
| 视图 | `stats`、`tasks`、`timeline`、`workspace`（工作区管理）、`config`、`data`、`commands`（只读命令目录）、`actions`（Action 页：查看 schema 并开关 agent 可调用） |
| 数据页 | 表清单 + 逐列筛选（`dataQuery`）；侧栏「表索引」汇总本域每张表的行数/列数/主键/索引/最近写入（只读） |
| action 数 | 64（`tasks.*` 49 + `taskNodes.*` 11 + `taskTimelines.*` 7） |

**能力摘要**：记录可执行、可交付的工作项（任务），支持任务树、时间线、重启链、依赖与标签（多对多，标签定义归标签域）。

**记录类型 `task` → `tasks.create`**

- 何时记录：一个工作项已经完成或已有明确下一步；用户明确说“记一下 / 建个任务 / 加到工作台”；会话中发现需要后续处理、但当前不立即完成的动作。
- 不要记录：纯信息查询或一次性问答；没有明确标题或完成标准的模糊想法。
- 归属必填：`tableId` 与 `tablePath` 恰选一个；先用 `tasks.capabilities` 或 `tasks.resolveTable` 查看完整路径和职责，再明确选择。新路径仅在 `createMissing:true` 且每个新增段都有职责描述时创建。
- 常用参数：`title`、`description`、`tags`（标签名，缺失自动建）、`priority`、`targetDate`、`tagIds`、`dedupeKey`。
- 没有「类型」字段：工作/生活/学习/开发 已迁成同名标签，一个任务可挂多个。
- 去重：同 `dedupeKey` 的未删除任务会复用；自动记录建议稳定键，如 `dsh-session:<id>`。
- 关系：`taskNode` 通过 `tableId` 归组；`tag` 通过 `tagIds` / `tags.link` 关联。
- 约束：日期为 `YYYY-MM-DD`；`source=1` 需已有 `timelineId`（兼容 `timelineKey`），`source=2` 需 `restartKey` 且原任务已有有效归属；`status` 0 已开启 / 1 已关闭 / 2 已完成，不要直接创建 3（RESTARTED）。
- 标题不唯一：只做 trim + 非空校验，允许与其它任务重名，用 id 区分（与「标签名唯一」「任务节点名同级唯一」是不同规则）。
- 重启优先级：重启需优先级 >0。API `source=2` 未传 `priority` 时回落 1；显式 0 报错。UI 继承原任务有效优先级，原值为 0 时使用配置默认并限制在 1–10；空值/0 当场提示并禁止提交。通过 `capabilities.get` 查看概念说明，`tasks.capabilities` 发现有效任务表。
- 状态机：0 → 1 已关闭（`priority` 清零、补 `shutdownDate`）/ 2 已完成（`priority` 清零、补 `doneDate`）；1 或 2 可回到 0 继续办理；3 已重启只在重启老任务时由 `tasks.update` 写入，create 禁止。
- 分组键：`restart_key` = 重启链链首任务 id（普通任务为自身 id，`source=2` 继承原任务，`tasks.restart` 读取）；`timelineId` = 有效实体归属（普通任务为 null，`source=1` 只能加入已手动创建的线，重启必须继承）；`timelineKey` 是 deprecated 兼容别名。旧列保留用于双写与审阅，历史 key 不自动实体化。
- 分页：`pageSize` 上限 200（超出按 200 截断，`filter.pageSizeCapped=true`）；`total` 为真实总数、`returned` 为本次返回条数、`truncated` 表示是否还有未返回的行；未分页最多 500 条。

### 斜杠命令 `/wb-task-publisher`（5.2.6）

任务插件自带一个面向人的斜杠命令，插件安装或更新后**需要重启 DSH** 才会出现在命令面板。

- 用法：`/wb-task-publisher <需求描述>`，可附截图或文档附件；`/wb-task-publisher` 不带参数只显示用法，不产生模型轮次。
- 命令本身不建任务、不写业务数据：它把用户原话与发布 SOP 作为一条用户消息送入下一轮模型，由 agent 按流程执行。

### `/wb-task-publisher` 增加标签步骤（5.2.6）

发布流程原来只到「归属 → 时间线 → 发布」，标签全靠 agent 自觉，结果 2026-11-09～11-11 的存量任务大面积无标签。现在 SOP 插入独立的 **E 标签** 步（原发布、停问顺延为 F/G），要求自由联想标签、不被现有列表限制：业务域（tasks/tags/sites/storage/宿主/工作台）、功能面（UI/数据/统计/命令/发布）、动作（新增/优化/修复/重构/调研）、影响面（用户可见/内部/跨插件）只作启发；越多越好（通常 5–8 个，上不封顶），但每条语义准确，禁止为凑数堆同义词或空泛词。

写入方式统一为「按名字传」：`tasks.create` 的 `tags` 接受名称数组，未知名字受 `form.autoCreateTags` 控制（默认自动创建，关闭时报错并列出可用标签），因此不必先 `tags.create`、也不要用 `tagIds`。标签域未安装时不阻断发布：`tags` 照传，任务照常创建，回执 `notices` 说明标签缺失，agent 不得停问、重试或声称已打标。输出格式第 3 条与回执第 4 条都增加标签行（新建的单独标出，未打标须说明原因）。

改动集中在 `packages/addons/tasks/lib/publisher/brief.js`（SOP 与输出格式）与 `catalog.js`（命令摘要、送入回执与说明文案）；「命令」页只读模板由同一 `buildPublisherBrief` 现场渲染，无需另改。`scripts/test-task-publisher.mjs` 增加步骤顺序、`tags: ["标签名"]`、`form.autoCreateTags`、标签域缺失降级、回执与输出格式含标签、边界规则不重复标签口径等断言。brief 净增约 330 字，未稀释原有 A–D 步骤。

### 全屏页的返回按钮不再被窗口拖拽区吞掉（host 0.6.6）

覆盖在 drag 区之上、又没有声明 `no-drag` 的元素，点击会被当成「拖窗口」，事件到不了按钮 ——

- 覆盖层根节点声明 `-webkit-app-region: no-drag`，把宿主 chrome 的 drag 区从这块区域里减掉，
  点击落到插件页而不是窗框上；
- 工具栏空白段恢复 `drag`（仍可拖窗口），工具栏内的按钮/输入框统一 `no-drag`，与宿主 chrome 行的约定一致；
- 顶部仍用 `padding-top: var(--dsh-frame-top-clearance, 0px)` 让开红绿灯与控制区，其余三边不留白；
- 新增 `scripts/test-shell-immersive.mjs`（`pnpm test:shell-immersive`）锁定以上约束。

### 时间线视图（3.2.0）

顶层顺序为统计、记录、时间线、配置、数据。时间线为独立手动创建的实体，通过唯一 task_id 关联表形成 1:N。页面默认显示空线和单成员，支持创建、改名、编辑描述、删除（保留任务）、显式添加/移出任务、分页搜索和整线合并；合并先 dryRun 再确认。任务未关联时显示“没有关联时间线”；重启必须继承原有有效归属，无关联先手动建线并关联，失败零写。

列表每项返回 timelineKey/title/taskCount/openCount/doneCount/firstPublishDate/lastActivityDate；另含 timelineId/description/timelineUpdatedAt，标题由实体独立维护。API默认只显示多成员，includeSingletons=true显示全部（包括空线）。最近活动日取发布、完成、关闭、创建和更新日期的最大本地日，不含计划完成日。整线合并只迁移有效成员，返回 selectedCount 与 wouldUpdate（预览）或 updated（执行），不返回全量成员 id；旧 ids 模式保持兼容。

| Action | 行为 | 参数 |
| --- | --- | --- |
| `taskTimelines.create` | 手动创建空线 | `id?`, `title?`, `description?` |

| `taskTimelines.migrate` | 只读审阅默认；审批清单回填 | `dryRun?`（默认 true），实际执行需 `approvedKeys` 与 `snapshotHash` |

### 列表状态与时间范围（3.4.0）

`tasks.list` 与按条件导出的 `tasks.export` 支持 `publishFrom` / `publishTo`，分别可选，空字符串按未传处理。两端均含当天，以 `publish_date` 前十位比较，兼容历史时间部分；严格验证真实的 YYYY-MM-DD 日期。起始晚于终止时自动交换，回执 notices 提示「起始晚于终止，已交换」，筛选摘要显示归一后的发布日范围。与关键词、标签、页签及其他条件取 AND。

新增 `doneFrom` / `doneTo`、`shutdownFrom` / `shutdownTo`，与发布范围共用真实日期校验和归一逻辑；对应反序提示为 `done_range_swapped`、`shutdown_range_swapped`。三组范围取 AND；完成范围要求当前状态 2，关闭范围要求当前状态 1，同时提供两组非空范围时交集为空。

`targetFrom` / `targetTo` 是目标日期区间（含两端，可与任意状态组合），`statuses` 为 0/1/2/3/4 的整数数组（4=已接取），`urgent` 为布尔值；数组内状态与紧急谓词取 OR，再与其他条件 AND；空数组且 urgent=false 表示全部。`urgent` 仍兼容但客户端不再使用。4.0.0 起 `tab` 与 `filterRestarted` 已彻底移除：传了会直接报错，并给出对应的 `statuses` 写法（0→`statuses:[0]`+优先级 8..10、1..4→同名标签、5→`statuses:[1]`、6→`[0]`、7→`[2]`、8→`[]`（全部状态）、9→`[4]`）。单个 `status` 与活动筛选参数继续兼容。

左侧筛选区顶部是快捷筛选（4.1.0）：紧急任务 P8–10、高难度 D4–5、已逾期、今日到期、近 7 天完成、已接取六个按钮，点一下套用对应组合、再点一次回到全部；激活态由当前筛选值精确推导，手动改任何条件都会自动熄灭。下面依次是状态复选框、关键词、标签、优先级区间、难度区间、目标日期范围、四组事件日期（发布/完成/关闭/接取）和未填难度筛选；全部与其他状态互斥，清空选择显式回到全部。每组日期复用原时间范围按钮，点击展开起止日期选择，按钮显示已选范围并支持清除、Esc 关闭回焦，不常驻展开六个输入框。桌面吸顶并在超高时内部滚动，窄屏可折叠。热力图跳转换算为根节点下对应日期的单日范围和状态。动作按钮留在内容区。

节点名称和名称路径的每段上限统一为 40（JavaScript length，即 UTF-16 代码单元；部分 emoji 占两个单位）；最多 32 段、总输入最多 2048 个同口径长度单位。客户端 maxLength、后端错误和 schema 使用同一常量；不涉及数据库迁移。

### 今日指标（3.1.6）

`tasks.statsReport.today` 返回 `{ date, published, claimed, done, shutdown, avgDifficultyDone, avgSample }`；`tasks.stats.todayActivity` 返回相同对象，原有 `tasks.stats.today` 今日到期数字保持兼容。日期以服务端本地时间为准，使用日期字段前十位兼容历史时间部分；发布按发布日期，接取限当前状态 2/4 且取 `COALESCE(claimed_at 的本地日, publish_date)`（历史任务没有接取时间，按发布日期计），完成限当前状态 2 与完成日期，关闭限当前状态 1 与关闭日期，均排除软删除且独立于时间范围。平均难度只计今日完成且难度大于 0 的记录，保留一位小数，无样本返回 null，界面显示 `—`。

### 优先级/难度区间与时间线搜索（3.4.2）

`tasks.list` 与 `tasks.export` 新增 `difficultyMin` / `difficultyMax`（0..5，兼容 0.5 档，非数字或越界抛错、不静默截断），NULL 视作未设置（0）：仅给上限时包含 NULL，下界为 0 时同样把 NULL 算入，下界大于 0 时排除未填难度的任务。`priorityMin` / `priorityMax` 沿用原有 0..10 取整口径，本次为四个端点补充了带字段名的报错（`priorityMin 必须是 0..10 内的数字`）。`filter` 回显实际生效的四个值，列表摘要显示 `P>=6`、`难度2–4` 等。

左侧筛选面板在「标签 / 仅未填难度」之后、三组日期之前有优先级与难度两行：每行是「标签 + 一行单位说明」的标题行加两个数字输入与重置按钮；默认预填完整域（优先级 0–10、难度 0–5，端点等于完整域时不发送筛选参数，避免默认值变成隐性筛选），不再有分组标题与整段说明，`min>max` 自动交换并提示，非法值不写入状态。输入框保留草稿，失焦或回车才提交，避免输入「10」的首位就触发交换。难度区间与「仅未填难度」互斥：勾选后者清空难度区间，设置难度区间则取消勾选。四个值写入会话存储，切换视图再回来或刷新后仍保留；从热力图或排行显式跳转时按导航参数覆盖，不会串用上次的条件。

`urgent` 参数保留在 schema 中供旧链接与外部调用使用，但界面已不再发送它：「紧急任务」改为前端快捷组合，勾选即 `priorityMin=6`、`priorityMax=10`，手动把优先级改回 6–10 时复选框自动勾上，改成其它区间自动取消。口径变化因此明确为「优先级 6–10」，不再包含「优先级低但 2 天内到期」的任务，面板提示里写明了这一点。

`tasks.timelines` 的 `titleKey` 改为同时匹配时间线标题与描述（字面子串、ASCII 大小写不敏感，仍不搜索成员任务标题），与 `includeSingletons` 及其它条件 AND；列表行标题与描述首行摘要都会用 `<mark class="wbt-hit">` 高亮命中词，描述为空不占位。无结果时显示带搜索词的提示，与「暂无时间线」的空态文案区分。

### 最近发布清单（3.4.1）

统计页最近发布、最近完成、最近关闭三张卡各占 4 列，宽屏并列，窄屏堆叠（5.2.15 起合并为一张整行「最近任务」卡，四个维度按钮切换）。`lists.recentPublish` 包含全部状态的未删除任务，按 `publish_date DESC, updated_at DESC, id DESC` 排序，缺少发布日期的旧任务置末尾（`date: ""`、`daysAgo: null`，界面显示 `—`）；不受统计时间范围影响。行字段与另外两张最近清单一致。

新增可选参数 `recentPublishLimit`（默认 10，向下取整后夹到 1–50）；配置 `stats.recentPublishLimit` 位于统计分组，客户端透传，默认显示区块包含 `recentPublish`。

### 最近任务的难度与任务表跳转（3.1.3）

`tasks.statsReport` 的 `lists.recentDone` / `lists.recentShutdown` 均返回 `difficulty`（空值归为 0）、`tableId`、`groupId`、`tableTitle`、`tableDeleted`。已删除或不存在的表返回空导航 ID 和 `tableDeleted: true`。

统计页两张最近任务表共用列定义：难度展示星级和数值（兼容半星），0 显示 `—`；仅任务表名称是可键盘操作的链接式按钮，点击进入该表的全部记录列表并清空关键词和标签筛选。已删除表保持普通文本。返回统计页保留区间和滚动位置。

### 难度填写与巡检（3.1.2）

难度与优先级独立：优先级表示紧急程度，难度表示实现复杂度。创建、更新时建议填写 1–5，完成时应补齐；为兼容已有调用，不增加硬必填校验。0 和 null 表示未设置，不能当成最简单。已有半星值仍兼容。

| 难度 | 判定锚点 |
| --- | --- |
| 0 / null | 未设置 |
| 1 | 改文案、样式等单点小改 |
| 2 | 单模块内的局部功能 |
| 3 | 跨 2–3 个模块或带数据读取变更 |
| 4 | 涉及存储、迁移、同步、构建链路 |
| 5 | 跨进程架构重构或需多阶段验证 |

结合改动文件数、是否涉及数据迁移及测试面判断。创建带描述或标签的任务却未填难度时，回执提供 `notices: [{ code: "difficulty_missing", field: "difficulty", message: "建议填写 1–5 难度；0 会被统计为未设置" }]` 软提示；缺省不输出空 difficulty 字段。

巡检未填难度任务，再按实际复杂度分组补齐（不要把全部任务统一猜成同一档）：

```js
Workbench({ action: "tasks.list", args: { statuses: [], difficultyMissing: true, pageNumber: 1, pageSize: 100 } })
Workbench({ action: "tasks.bulkUpdate", args: { ids: ["已核对的任务id"], patch: { difficulty: 2 }, dryRun: true } })
// 核对预览后，使用同样 ids 和 patch，去掉 dryRun 执行。
```

筛选与表、状态、标签等条件取 AND；按 total/returned/truncated 翻页。统计页保留“未设置”桶，并提供未填数量及跳转；列表只在难度大于 0 时显示星级（卡片模式已于 5.2.9 移除）；5.2.14 起每张卡片最下方展示 `任务 ID · <完整 ULID>`。新建开放任务即可填写，编辑展示星级和数值。

工作区是独立实体（标题/简称/描述/可选本机目录），与任务是**多对多**：一个任务可挂 0..n 个工作区。关联行按 `workspace_id:task_id` 生成确定性 id，便于多设备同步幂等；表上唯一索引只约束**未删除**的同一对关联。删除任务会连带软删它的关联，删除工作区会软删工作区与关联但不动任务；任何一方软删后三向 live join 都查不到。

### 8.0 只读 Action 页与 agent 可调用开关（0.6.5 起；0.8.0 起可开关）

每个业务插件各有一个「Action」标签页，数据由**插件自己**提供：插件在注册 action 时本地记录定义，并注册自己的只读 action `<域>.actionSchema`（`tasks.actionSchema` / `mail.actionSchema` 等）；页面通过 `api.call("<域>.actionSchema")` 取数，插件未加载时页面自然降级，不需要宿主了解各插件的内部结构。

宿主仍保留统一接口 `GET /workbench/api/schema`（与 `actions.list(detail=true)` 同源，可带 `?domain=wb-addon-tasks`），服务于宿主自身的跨域场景；它不再是这些插件页面的数据源。宿主「工作台管理」里另有一张 Agent 权限页，直接复用共享 Action 页、数据源换成 `actions.list`，用来集中查看和调整所有域的开关。

设计说明见 `docs/specs/41-插件自证Action清单.md`。

该页按 action 渲染名称、所属域、必填参数、参数类型（含 `number | string` 这类联合类型）、枚举、默认值、范围/长度等约束与说明，支持搜索、按必填/类型过滤、复制示例、展开原始 JSON Schema；搜索命中的 action 名称、说明与参数文本会高亮，口径与过滤完全一致（示例与原始 JSON Schema 不高亮）。页面不提供 action 执行入口，唯一的写操作就是下面这个开关；打开页面读取 schema 不产生任何审计或写入。

#### agent 可调用开关（宿主 0.8.0 起）

每个 action 行右侧有一个「agent 可用」开关。它只决定 **agent** 能不能发现和调用这个 action，**界面操作永远不受影响**（`origin=ui` 不做这层校验）。三种状态：

| 状态 | schema 字段 | 界面表现 | 当前 action |
| --- | --- | --- | --- |
| 允许（默认） | 不写 `agentEnabled`（视作 `true`） | 开关打开，可关闭 | 大多数读类 action |
| 默认关闭（可打开） | `agentEnabled: false` | 开关关闭，可打开 | 33 个写 / 发信 / 同步 / 数据页类 action |
| 永远关闭（安全锁定） | `agentEnabled: false` + `agentLocked: true` | 开关禁用，标「仅界面 · 安全约束」 | 宿主 `actions.setAgentAccess`；保险箱 21 个、邮件 5 个 |

**两类锁定要分清**：

- `agentLocked: true` 是**固有安全限制**，由 action 定义声明、宿主统一执行：agent 永远调不到，`actions.setAgentAccess` 也拒绝把它打开，界面显示灰态并提示「该 action 只能在界面执行（安全约束），agent 开关不可放开」。当前一共 27 个：邮件的 `mail.attachmentDownload`、`mail.draftList`、`mail.draftGet`、`mail.draftSave`、`mail.draftDelete`，宿主内置 `actions.setAgentAccess`（打开它等于打开一切，永久锁死），加保险箱 21 个——`vault.setup`、`vault.unlock`、`vault.lock`、`vault.setUnlockMode`、`vault.changePassphrase`、`vault.secretCreate`、`vault.secretUpdate`、`vault.secretDelete`、`vault.secretReveal`、`vault.lease`、`vault.rotateDeviceKey`、`vault.groupCreate`、`vault.groupUpdate`、`vault.groupDelete`、`vault.subjectRegister`、`vault.bind`、`vault.unbind`、`vault.subjectSecrets`、`vault.bindingPurge`、`vault.dataTables`、`vault.dataQuery`。它只限制 agent，界面照常可调。
- `agentEnabled: false` 是**可改的默认值**：新装默认不给 agent，用户在界面上随时能打开；它是策略，不是安全边界。

默认关闭的 33 个 action（都可在界面打开）：邮件 12 个 `mail.accountCreate`、`mail.accountUpdate`、`mail.accountDelete`、`mail.accountTest`、`mail.accountProbe`、`mail.mailboxSync`、`mail.messageSend`、`mail.messageMarkRead`、`mail.messageMove`、`mail.messageDelete`、`mail.sync`、`mail.dataQuery`；联系人 6 个 `contacts.create`、`contacts.update`、`contacts.delete`、`contacts.groupCreate`、`contacts.groupDelete`、`contacts.importVcf`；自动化 6 个 `automation.ruleCreate`、`automation.ruleUpdate`、`automation.ruleDelete`、`automation.ruleRun`、`automation.configSet`、`automation.dataQuery`；日历 8 个 `calendar.calendarCreate`、`calendar.calendarUpdate`、`calendar.calendarDelete`、`calendar.eventCreate`、`calendar.eventUpdate`、`calendar.eventDelete`、`calendar.eventRemind`、`calendar.dataQuery`；工资 1 个 `salary.dataQuery`。

**生效方式**：`actions.list`、`actions.help`、`capabilities.list|get`、`<域>.actionSchema` 的条目都带 `agentEnabled`（界面拿到的 schema 另带 `agentLocked`，agent 视图按开关过滤）。关闭后 agent 下一次发现就看不到它，硬调得到结构化错误 `code=ACTION_AGENT_DISABLED`（消息「该 action 已被本机设置禁止 agent 调用（界面仍可执行）」），并写一条 force 审计。开关存宿主库 `meta` 的 `config.wb-shell.actionAgent.<action>`（值 `1` / `0`），与声明默认值相同时删除该行；不写同步日志、不进业务备份、换机回到默认值；数据库读故障或覆盖值非法时按关闭处理（agent 侧 fail closed），界面不受影响。

**新 action 的声明约定**：agent 不该调用时，写 `agentEnabled: false`（默认关闭、界面可开）或 `agentLocked: true`（永远不可开，只用于安全边界）。不要把插件内 `if (origin !== "ui") throw ...` 当作唯一闸门——插件里的 `only()` 只再拦 `sync` / `plugin` 这类非界面、非 agent 的 origin，属于纵深防御。

## 8.2 消息（message 0.1.1）

消息中心给 agent、子插件与界面提供**一个**发送入口：`message.send`。插件之间不互相 import、不直读对方数据表——子插件在自己的 `apply(ctx)` 里存下 `ctx.workbench`，之后 `host.invoke("message.send", {...}, "ui")` 即可；消息域未安装时按 `host.hasDomain("wb-addon-message")` 降级，不阻断自己的主流程。同理，消息插件不依赖任何业务插件。

数据只落本机（`sync: {tables: []}`，不参与云端同步，也不进业务备份导出）。已读消息默认保留 30 天（`retention.readDays`），未读消息永久保留；总量上限 5000 条，超出时从最旧的已读开始清理，单次最多 200 条。去重靠 `dedupeKey`：同一键在未删除期间只保留一条，重复发送返回 `deduped: true` 与已有消息。

新消息通过宿主 SSE 的 `domain-event` 广播 `message.created`（随后 `message.read`），客户端提示音**只**监听本域事件：默认开启、可配置音量，`audience=agent` 的消息不发声，页面隐藏时默认不响，22:00–08:00 默认不启用免打扰且只放行 warning/error。提示音由 WebAudio 合成，首次点击页面后解锁；界面另有「试听」按钮。

## 8.3 凭据保险箱（vault 0.3.11）

0.3.7 起 Action 页接入共享组件：保险箱全部 21 个敏感与数据类 action（解锁、口令、密文增删改、明文查看、租用、设备密钥、分组、关联与数据页查询）声明 `agentLocked: true`，界面上显示为「仅界面 · 安全约束」、开关不可打开，agent 永远调不到；界面操作照旧。完整清单见 8.0 节。

独立域 `wb-addon-vault`，只保存密文与 KDF 参数。0.3.0 起十张表：`vault_header`（单行，salt/kdf/wrapped_dek/schema_version）、`vault_secret`（密文，不再带 group_id）、`vault_group`、`vault_set`（凭据集合）、`vault_group_set`（分组 ↔ 集合 N:N，`uk(group_id,set_id)`）、`vault_set_secret`（集合 ↔ 凭据 N:N，`uk(set_id,secret_id)`）、`vault_binding`（业务对象 ↔ 组 N:N）、`vault_subject_type`（模块注册的关联类型）随云同步；`vault_device`（解锁模式、device key 包裹）与 `vault_secret_usage`（最近使用时间）只留本机。备份仍不导出密文与 KDF 参数。

凭据类型 7 种通用类型：`password`（密码）、`phone`（手机号）、`id_card`（身份证号）、`token`、`app_password`、`api_key`、`other`。0.3.0 移除了业务专属的 `site-account`：旧的 `site.<siteId>.<accountId>.<field>` 行在首次解锁时按 field 收口为 password/phone/id_card，并把同一 accountId 的凭据收进同名集合。`kind` 参与 AAD，改类型会触发重加密。

归属模型改为「分组 ⊃（多对多）集合 ⊃（多对多）凭据」：一条凭据可进多个集合，一个集合可挂多个分组；删除任一层只断关联、不删实体。旧分组的直属凭据在迁移时自动生成「<组名> · 默认」集合，`schema_version` 由 2 升到 3，整批一个事务，失败回滚并保持 2，下次解锁重试。

口令经 scrypt（N=65536, r=8, p=1，≥12 字符）派生 KEK，AES-256-GCM 包裹 DEK；单条凭据再用 DEK 加密，AAD = `vault:<id>:<name>:<kind>`。DEK 只在宿主进程内存，空闲 15 分钟或手动 lock 后清除。云端只能看到 KDF 参数、包裹后的 DEK 与密文，没有口令解不开。

三种解锁模式：A 全锁（默认，每次启动要解锁）、B 自动解锁但查看凭据需再输口令、C 自动解锁且查看免口令。B/C 用 `$WB_HOME/vault-device.key`（32B，0600）包裹 DEK；切回 A 会删除该文件。

同步按 LWW 合并：`vault_secret`/`vault_group` 以 id 与 name 去重，重名时较旧的行被软删并留冲突记录；`vault_binding` 以 (subject_type,subject_id,group_id) 去重。并发改口令按 LWW，后写生效；另一台设备用旧口令解锁会收到“口令已在其他设备修改”的提示，用新口令可解锁。宿主同步协议没有运行时开关，声明即同步，setup 返回值会带同步说明。

## 8.4 连接器（connector 0.1.3）

独立域 `wb-addon-connector`，把 RSS/Atom 与 Webhook 内容接进工作台。四张表：`connector_source`（来源定义，参与云同步）、`connector_source_state`（secret_id/cursor/next_run_at/失败计数，本机）、`connector_item`（内容，本机）、`connector_run`（运行记录，本机）。备份只导出来源定义，不含凭据、cursor、条目。

driver 内置 `rss` 与 `webhook`；抓取不引入 XML 依赖，按 `<item|entry>` 边界解析。调度器在插件内每 15 秒检查一次，单次最多 3 个到期来源；失败按 60/120/240…秒指数退避，上限 6 小时。投递统一走 `host.call("message.send", …, "plugin")`，不直写消息表。

| action | 参数 | 必填 | 说明 |
| --- | --- | --- | --- |
| `connector.status` | 无 | 无 | 就绪状态、driver、统计与到期数 |
| `connector.driverList` | 无 | 无 | 可用 driver 与配置字段 |
| `connector.sourceList` | q | 无 | 来源定义与最近运行状态；不返回 cursor/secret |
| `connector.sourceGet` | id | id | 单个来源定义与状态 |
| `connector.sourceCreate` | name, driver, config, scheduleSec, sink, sinkConfig, enabled, secretId | name/driver | 新建；同事务写 source+state；仅 ui |
| `connector.sourceUpdate` | id, name, driver, config, scheduleSec, sink, sinkConfig, enabled, secretId | id | config 整体替换；仅 ui |
| `connector.sourceDelete` | id | id | 软删除并停止调度；仅 ui |
| `connector.sourceBind` | id, secretId | id | 绑定 vault 凭据，只写本机 state；仅 ui |
| `connector.sourceDelivery` | id, enabled | id/enabled | 开关新内容投递；仅 ui |
| `connector.sourceRun` | id, force | id | 立即运行；ui/plugin |

| `connector.runList` | sourceId, limit | 无 | 运行记录，上限 100 |

| `connector.dataTables` | 无 | 无 | 四张表列清单；仅 ui |
| `connector.dataQuery` | table, limit, offset | table | 白名单只读查询；仅 ui |
| `connector.actionSchema` | 无 | 无 | 本域 action 清单；仅 ui |

Webhook 入口为 `POST /workbench/hooks/connector/inbound?source=<id>`。鉴权支持：

- `authMode=token`：token 放在 `header`（默认 `x-webhook-token`），常量时间比较；
- `authMode=hmac`：`x-webhook-timestamp` 毫秒时间戳 + `x-webhook-signature: sha256=<hex>`，签名内容为 `timestamp + "." + rawBody`，窗口默认 300 秒；同一签名只接受一次（进程内重放缓存）。

可配 `windowSec`、`ipAllowlist`（支持 IPv4 与 CIDR，逗号分隔）、`ratePerMin`（默认 60，0 关闭）、`trustProxy`（仅在反代可信时读取 `x-forwarded-for`）、`allowPublic`。宿主 hooks 路由只接受回环地址；公网必须用反向代理转发到本机，不能直接暴露端口。拒绝时返回 401/403/409/413/429，429 带 `retry-after: 60`。

`sourceBind` 只写 `secret_id`，明文由 `vault.lease` 在运行时租用，列表与数据页都不回显。

0.1.2：随共享 `packages/addons/lib/client-common.cjs` 的 `unwrap` 修复，服务端拒绝（`{ok:false}` + `error`，如锁定/权限/重名）不再被当成成功吞掉，界面会直接显示错误原文。

## 8.5 自动化（automation 0.2.2）

独立域 `wb-addon-automation`，把「定时 / 域事件 / 手动」接到白名单 action。三张表：`automation_rule`（规则）、`automation_run`（运行记录）、`automation_meta`（本机配置）。规则参与备份导入导出，运行记录只在本机，`sync:{tables:[]}` 不参与云同步。

0.2.2 起 6 个写/执行/配置/数据类 action（`automation.ruleCreate`、`ruleUpdate`、`ruleDelete`、`ruleRun`、`configSet`、`dataQuery`）声明 `agentEnabled: false`：新装默认不给 agent，界面可逐个打开；插件内的 `only(ui)` 放宽为放行 `ui`+`agent`，只再拦 `sync`/`plugin`。

触发方式：`interval`（1–10080 分钟）、`dailyAt`（HH:MM + IANA 时区 + 星期，默认 Asia/Shanghai）、`event`（`domainId` + `event`）、`manual`。事件来自宿主 `domain-event`，payload 为 `{domainId,event,data}`；connector 的 `item.created` 带 `sourceId` 与 item 摘要（不含正文原文）。

参数支持模板 `{{event.field}}` / `{{item.field}}` / `{{rule.name}}`，路径最多 3 段并禁用原型链键；条件为 `{field,op,value}`，`op=eq/neq/contains/gt/lt`，不满足记 `skipped`。执行走 `host.call(action,args)`（固定 plugin origin），失败写 `automation_run` 的 `error`。

白名单固定为 `message.send`、`tasks.create`、`tags.create`、`sites.create`、`connector.sourceRun`；拒绝 `vault.*`、`automation.*`、`audit.*` 与任何 `delete` / `backup` action。每规则每小时默认 60 次、全局并发 2、规则上限 50（可在设置页调整），超限记 `skipped`。

界面（0.2.0 重做）：四块视图的文案统一走 `client/ui/copy.cjs`（zh/en），布局只引用主题 token（`--wb-*` / `--dsw-alias-*`）；新增版式层 `client/ui/layout-styles.cjs`（面板、表格容器、KPI 卡、键值列表、chip 组、代码块、模态、骨架屏、空态卡、`:focus-visible` 焦点环），基础样式仍来自 `packages/addons/lib/client-base-styles.cjs`。

- 概览：5 张 KPI 卡（规则总数、已启用、今日成功/失败/跳过，各带口径说明与图标）、允许与不允许调用两组 chip、四类触发说明，页头提供「新建规则」入口。
- 规则：页头说明触发/白名单/限频；过滤条搜索名称与 action、按状态与触发方式筛选；无数据时只渲染一张虚线空态卡，不渲染表头与表格；表格六列（名称含弱化 id、触发方式、执行 Action、状态、上次运行、操作），操作为运行/编辑/启停/删除四个图标按钮，删除二次确认带规则名。

## 9. 记录边界与已知缺口

- **能力清单是声明，不是强制校验**：宿主会校验 `kind` 非空/不重复、`primaryAction` 已注册，但不会阻止 agent 绕过清单直接调 action。
- **没有跨插件事务**：一次“任务 + 标签 + 站点”需要多次 action；失败时由调用方自行补偿和去重。
- **站点没有 `dedupeKey`**：自动记录前必须用 `sites.list` 查重；标签允许重名，创建前建议先复用同名标签。
- **任务有 `dedupeKey`**：自动记录建议使用稳定键，避免重复建任务。
- **`capabilities.list` 是紧凑视图**：只返回 kind / title / description / primaryAction；完整的 `when`、`notFor`、`dedupe`、`relations`、`examples` 需要 `capabilities.get`。
- **未声明能力的插件**：`source:"fallback"`，仍可用 `actions.list` 查看 action；不会凭空编造记录类型。

## 10. 会话记录模式（/record）

记录模式是宿主提供的会话级行为开关，不新增 tool，也不改变工具集。开启后，当前会话的 agent 会在完成主任务后，按各业务插件声明的能力清单，把本轮可复用的交付物记成任务、站点或标签。

### 10.1 开关与状态

- 斜杠命令：`/record on`、`/record off`、`/record status`；不带参数显示帮助。
- 对话输入区左侧的记录胶囊：点击开启/关闭，状态与斜杠命令通过 `record-mode` SSE 双向同步。
- 状态按 `sessionId` 存在本机 `workbench.db` 的 `session_mode` 表；不参与同步和备份，也不自动作用于子 agent。
- 仅影响当前会话；关闭后，用户明确说“记一下”时 agent 仍可直接调用 `Workbench`。

### 10.2 注入给 agent 的规则

开启后，宿主通过 `systemPrompt.section` 注入 `workbench:record-mode`（order 为 `PLAN_POLICY` + 10），要求：

1. 先查 `capabilities.list`，需要字段细节时用 `capabilities.get`，再按需 `actions.help`；
2. 只记录同时满足 `when` 且不满足 `notFor` 的内容，没有命中就不写；
3. 用 `records[].primaryAction` 写入，不猜 action 名；
4. 写入前查重：任务用 `tasks.list`（`titleKey`），站点用 `sites.list`，标签用 `tags.list` / `tags.search`；
5. 只新增，不修改、不删除已有数据；
6. 多条记录合并成一行回执，失败只提示一次，不阻塞主任务；
7. plan mode 下不写入。

### 10.3 记录边界

- **任务**：完成的可交付项或明确的下一步；不记纯问答、一次性查询、模糊想法。
- **站点**：以后还会访问的外部站点；排除 `localhost`、`127.0.0.1`、内网地址、临时页和搜索结果页。
- **标签**：可复用的主题分类；不记一次性描述、状态词、日期。
- **一律不记**：聊天内容、日志、临时笔记、token/密钥/密码，以及用户明确拒绝记录的内容。

### 10.4 已知限制

- 这是提示层行为模式，不是 100% 自动入库；agent 仍需判断 `when` / `notFor` 并调用 action。
- 没有跨插件原子写入；一次“任务 + 标签 + 站点”需要多次 action，失败时由调用方补偿。
- 站点没有 `dedupeKey`，必须先用 `sites.list` 查重；标签允许重名，创建前建议先复用同名标签。
- 关闭后不会删除已记录的数据；改删需要用户到工作台 UI 操作。

原理、状态表、prompt 注入时序、设计取舍与故障排查见 [会话记录模式.md](./会话记录模式.md)。

### 标签来源注册与重复来源校验（tags 1.7.1）

`tag_mapping.item_type` 原来是自由文本，任何插件都能写任意来源标识，来源重复时标签统计与筛选语义会含混。1.7.1 引入来源注册表 `tag_source`，并把「来源必须恰好注册一次」做成写入门禁：

- 新表 `tag_source(id, source, owner, title, created_at, updated_at, deleted_at, rev)`，唯一索引 `uk_tag_source(source, owner)` 只覆盖未删除行；启动时 seed 三个内置来源（`task→wb-addon-tasks`、`storage→wb-addon-storage`、`site→wb-addon-sites`，`INSERT OR IGNORE` 不覆盖人工行）。
- 老库兼容：既有 `tag_mapping` 里出现过、但没有活跃注册的 `item_type` 自动补一行 `owner='legacy'`，升级后旧数据照常读写。
- 门禁：`tag_mapping` 上的 `BEFORE INSERT/UPDATE` 触发器在「该来源活跃注册数 ≠ 1」时 `RAISE(ABORT, '标签来源未注册或重复，无法操作：<来源>')`；`tags.link` / `tags.unlink` 先做同样检查，抛带 `code` 的结构化错误（`TAG_SOURCE_UNREGISTERED` / `TAG_SOURCE_DUPLICATED`）。
- 新 action：`tags.registerSource`（幂等；重复来源不抛错，回执带 `conflict:true` / `conflicts` / `message`）、`tags.unregisterSource`（软删；仍有未删除映射时抛 `TAG_SOURCE_IN_USE`）、`tags.sources`（只读盘点，标出重复与「有映射但未注册」）。
- 备份导入：导入 `tag_mapping` 前对未知 `item_type` 先补 `legacy` 注册，旧备份不会整批失败；`tag_source` 不参与同步与备份（本机注册状态，不跨设备携带）。
- 回归：`pnpm test:tag-source-registry`；契约细节见 [specs/25](./specs/25-标签域解耦审计与改造.md)。

### 任务 / 储物 / 站点接入标签来源注册并统一重复来源错误（tasks 5.2.16、storage 1.5.3、sites 1.11.1）

标签域 1.7.1 的门禁上线后，三个业务域都要自己完成「登记 + 先判后写 + 错误翻译」，否则用户在标签来源重复时只会看到一行触发器原文：

- 启动登记：三域 `setup()` 在 `ensureSchema` 之后各调一次 `ensureTaskTagSource` / `ensureStorageTagSource` / `ensureSiteTagSource`，幂等写入自己的来源行；标签域未安装或仍是 1.7.0（无 `tag_source` 表）时整块跳过，保持既有降级行为。
- 先判后写：各域新增 `lib/tagging/source.js`（导出 `tagSourceReady` / `tagSourceError` / `withTagSource` 等），把所有 `tag_mapping` 写入（任务的 `replaceTaskTags` / `addTaskTagByName`，储物的 `replaceTags`，站点的 `replaceTagMappings`）包进 `withTagSource`。它只判定不补登记——若在写入时静默补注册，人工注销就会失效，门禁形同虚设。
- 统一文案：未注册抛 `TAG_SOURCE_UNREGISTERED`「标签来源未注册，无法操作（来源：task）；先调用 tags.registerSource 注册该来源」；重复注册抛 `TAG_SOURCE_DUPLICATED`「标签来源标识重复，无法操作（来源：task；归属：wb-addon-tasks、wb-addon-intruder）；请先清理 tag_source 中的重复注册」。触发器原始报错（含「标签来源」）在 catch 里翻成同一套文案，其它错误原样上抛。
- 备份导入：储物与站点的导入在写 `tag_mapping` 前先补登记自己的来源，不就绪时整批失败并给出可读原因，而不是逐行报触发器错误。
- 回归：`pnpm test:tag-source-adopt`（4 个场景：启动登记 / 抢注重复 / 注销未注册 / 无 `tag_source` 表降级）。

### 任务检索支持多关键词分组返回（5.2.31）

之前一次 `tasks.list` 只能带一个 `titleKey`，agent 想比对两个词就得连发两次工具调用。现在 `titleKey` 也接受字符串数组：

- 数组最多 10 项，去首尾空白后不能为空、不能重复；空数组、空白项、超限、重复都在查询前报错，并指出是第几项，不会跑出一半才失败。
- 每个关键词独立跑一遍完整筛选（状态、标签、表/组、日期区间、排序、分页各自生效），结果按输入顺序分组：`{ keywords, groups:[{ keyword, records, total, filter, notices }], total, returned, filter:{ multiKeyword, keywords, pageNumber, pageSize }, notices }`。`total`/`returned` 是各分组之和，方便一次看清规模。
- 同一任务命中多个词时，会分别出现在各组；零命中的组给空 `records` 而不是报错；某个词查询失败时该组带 `failed:true` 与 `error`，其余分组照常返回，`notices` 追加 `{ code:"keyword_failed", keyword }`，能直接看出是哪个词坏了。
- 字符串写法完全不变（仍返回 `records/total/filter`，无 `groups`），`tasks.export` 只接受字符串，传数组会明确报错——分组结果拼不成一份完整导出。
- 底层是同步 SQLite，多关键词是「一次调用里逐词执行」，不是线程并行；收益在于省掉多次工具往返，不在于缩短单次 SQL 耗时。
- 回归：`pnpm test:task-multi-keyword`（字符串口径不变、分组顺序、跨词重复命中、零命中、每组独立分页、四类参数校验、导出拒绝数组、单词失败隔离与 `keyword_failed` 定位）。

优先级与难度不再有分组标题和整段说明：每行标题行是「标签 + 单位说明」，下一行只有两个输入框与重置按钮。默认预填完整域（优先级 0–10、难度 0–5，中英文一致），端点等于完整域时不发送 `priorityMin/Max`、`difficultyMin/Max`，因此默认值不会变成隐性筛选；重置把该行恢复为完整域。校验域同步为 0 起（优先级整数、难度 0.5 档），错误提示改为「0–10」「0–5」。窄栏下标题行与输入行都按容器宽度换行，不横向溢出。

### 发布命令不得写出裸会话引用（5.1.1）

`/wb-task-publisher` 生成的 brief 正文曾把 `dsh-session:` 前缀和裸 sessionId 直接连写。DSH 会把用户消息里的 `dsh-session:<base64url>` 当会话引用 URI 解析，裸 id 不是合法 payload，于是下一轮在模型调用前就抛 `invalid session reference URI`。修复方式：brief 只写 `sessionId: <id>`，dedupeKey 改为文字描述「用 `dsh-session:` 前缀拼接上面的 sessionId」，不出现可直接匹配的裸串；`scripts/test-task-publisher.mjs` 增加 `/dsh-session:[A-Za-z0-9_-]+/` 不得命中的回归断言。

### 工作区实体与任务关联（5.1.0）

新增 `task_workspace`（工作区：标题、简称、描述、可选本机目录）与 `task_workspace_link`（任务↔工作区关联，id 规则 `workspace_id:task_id`，唯一索引只约束存活行）。任务侧接入：`tasks.create` / `tasks.update` 的 `workspaceIds` 整体替换（同事务，任一非法整体回滚）、`tasks.get` 回执加「工作区：…」行、`tasks.list` 支持 `workspaceIds`（OR）与 `noWorkspace` 互斥过滤并批量附带 workspaces、`tasks.export` 增加工作区列。删除任务会连带软删关联；删除工作区只软删工作区与关联，不动任务；三向 live join 过滤任何已删行。备份 schemaVersion 升到 5，旧备份缺两张表的键时按空数组恢复；同步表顺序为 workspace 先于 link，link 的 id 与 `workspace_id + ":" + task_id` 不一致时整批拒绝。客户端在任务创建/编辑弹窗内提供工作区多选与内联新建，卡片与详情展示 chips，筛选面板支持按工作区与「未关联工作区」过滤。设计见 `docs/specs/42-工作区实体与任务关联.md`。

### 任务依赖整体移除（5.0.0）

任务插件不再提供依赖关系：`tasks.depends`、`tasks.link`、`tasks.unlink` 三个 action 已删除，`task_dep` 表连同索引一并移除（`task_schema_version` 升到 5，旧库升级时直接 `DROP TABLE`，不再保留墓碑行），同步声明、数据页表清单、备份导出与 `tasks.changelog` 默认表也都去掉了它。备份导入空出兼容位：旧备份里的 `taskDeps` 数组会被忽略，并在导入回执 `message` 里注明忽略条数。
