# 13 · 插件体系重构方案（DSH 原生插件）

> 状态：已实施（2026-11-07）。本文保留为重构决策记录；实际包结构、
> 域注册与安装链路以 [04](04-子插件体系.md) 为准。
> 目标：去掉自建插件市场与运行时下载器，让个人工作台、任务、标签、站点都成为 DSH 可直接安装的插件；安装业务插件时自动带上个人工作台。

## 1. 结论

采用 **monorepo + 4 个独立 DSH 包**，不拆 Git 仓库：

| 包 | 作用 | DSH bundle |
|---|---|---|
| `dsh-workbench` | 个人工作台宿主：数据库、账号/同步、首页、API、工具、插件注册中心 | 是 |
| `dsh-workbench-tasks` | 任务：任务表、任务树、9 个视图 | 是 |
| `dsh-workbench-tags` | 标签：标签与映射 | 是 |
| `dsh-workbench-sites` | 站点：目录树、链接、标签关联 | 是 |

三个业务包都声明 `dependencies: { "dsh-workbench": "^x.y.z" }`，所以装任意业务包时 pnpm 会把工作台一起装上文件；业务包的 bundle patch 再把工作台这一行插入组合树，保证它被加载。

不再需要：
- 自建 GitHub catalog / Releases 市场；
- `AddonManager` 运行时下载、解包、原子发布；
- `tar.ts`、`catalog-cache.json`、`.staging`；
- 客户端“子插件”安装/卸载页；
- `WB_ADDON_MARKET` 与市场相关文档。

## 2. DSH 机制验证

以下结论来自本机 DSH 安装包的只读验证，不是猜测。

### 2.1 装业务插件会装工作台文件，但不会自动激活传递依赖

在临时 DSH profile 中安装一个包：

```json
{
  "name": "poc-domain",
  "dependencies": { "poc-host": "file:/tmp/.../poc-host" },
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

安装后：

- `poc-host` 确实出现在 profile 的 `node_modules`；
- profile 的 `dsh.profile.bundles` 只有 `poc-domain`，没有 `poc-host`。

原因：插件管理器的 `reconcile()` 只对 **本次新增的 profile 直接依赖** 检查 `dsh.bundle` 并加入 bundles；传递依赖只安装文件，不自动激活。

### 2.2 业务 bundle patch 插入工作台行，是可行的自动激活方式

让每个业务包的 `cordis.patch.yml` 同时插入两行：

```yaml
- insert:
    - id: workbench
      name: dsh-workbench
      config:
        enabled: true
    - id: workbench-tasks
      name: dsh-workbench-tasks
```

装任务时，任务 bundle 层自己把工作台行带进组合树；工作台不需要出现在 `dsh.profile.bundles`。

### 2.3 多个业务包重复插入工作台行是安全的

临时 profile 同时安装两个 bundle，二者 patch 都插入同一个 `id: workbench`：

- `--dump-config` 能看到两行；
- Cordis loader 的 `EntryGroup.update()` 用 `Object.fromEntries(config.map((options) => [options.id, options]))` 建表，同 id 折叠为一条；
- loader 的 `ensureId()` / `store[id] ??= new Entry()` 也按 id 复用。

因此多个业务插件重复插入同 id、同 name、同 config 的 workbench 行，最终只加载一个工作台实例。**前提：所有包里的这一行必须完全一致**。

### 2.4 客户端顺序可以用 `dsh.client.inject`

业务包 manifest：

```json
"dsh": {
  "client": {
    "platform": "web",
    "inject": ["dsh-workbench"]
  }
}
```

客户端模块加载器 `arriveGraphRow()` 会先加载 `row.inject` 里的包，再加载当前包。因此业务客户端可以安全地读取工作台客户端挂到 `window.__WB_HOST__` 的桥。

### 2.5 服务端用 Cordis service 注册

宿主：

```ts
ctx.provide("workbench", service);
```

业务插件：

```ts
export const inject = ["workbench"];

export function apply(ctx: any): void {
  const host = ctx.workbench;
  host.registerDomain({ ... });
}
```

这与 DSH 现有插件（theme / locale / connection 等）的 `ctx.provide` 模式一致。

## 3. 包结构

```text
packages/
  core/                 # 平台核心：SQLite、同步、行级 LWW（不直接暴露给业务）
  sdk/                  # 业务插件与宿主共用的类型
  shell/                # dsh-workbench 宿主
  addons/
    tasks/              # dsh-workbench-tasks
    tags/               # dsh-workbench-tags
    sites/              # dsh-workbench-sites
```

保留现有 `packages/shell` 作为宿主，不再有 `shell-dist` 这一层“手工拼装产物”；发布前由构建脚本把 `core` 打进宿主 `lib/core`，或把 `@wb/core` 作为普通依赖一起发布。

### 3.1 宿主 `dsh-workbench`

`package.json` 关键字段：

```json
{
  "name": "dsh-workbench",
  "version": "0.2.0",
  "main": "lib/index.js",
  "exports": {
    ".": "./lib/index.js",
    "./client": "./client/client.js",
    "./shared": "./lib/shared.js",
    "./package.json": "./package.json"
  },
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },
    "client": {
      "platform": "web",
      "inject": [
        "@deepseek-ai/dsh-client-locale",
        "@deepseek-ai/dsh-client-ui-settings",
        "@deepseek-ai/dsh-client-ui-theme"
      ]
    }
  }
}
```

`cordis.patch.yml`：

```yaml
- insert:
    - id: workbench
      name: dsh-workbench
      config:
        enabled: true
```

服务端职责：

- 打开 `~/.dsh/workbench/workbench.db`；
- 继续使用 core 的 schema/meta/sync_change_log/conflict_shadow/sync_state；
- 账号、设备、同步循环、`/workbench/api/*`；
- 提供 `workbench` 服务；
- 维护业务域注册表；
- 注册唯一的 `Workbench` 工具，action 动态分发；
- SSE 广播域事件。

### 3.2 业务包（以任务为例）

`packages/addons/tasks/package.json`：

```json
{
  "name": "dsh-workbench-tasks",
  "version": "2.0.5",
  "type": "module",
  "main": "lib/index.js",
  "exports": {
    ".": "./lib/index.js",
    "./client": "./lib/client.js",
    "./package.json": "./package.json"
  },
  "dependencies": {
    "dsh-workbench": "^0.2.0"
  },
  "dsh": {
    "bundle": { "patch": "./cordis.patch.yml" },
    "client": {
      "platform": "web",
      "inject": ["dsh-workbench"]
    }
  }
}
```

`cordis.patch.yml`：

```yaml
- insert:
    - id: workbench
      name: dsh-workbench
      config:
        enabled: true
    - id: workbench-tasks
      name: dsh-workbench-tasks
```

`lib/index.js`：

```js
import { tasks } from "./tasks.js";
import { tree } from "./tree.js";
import { ensureSchema } from "./db.js";

export const inject = ["workbench"];

export function apply(ctx) {
  const host = ctx.workbench;
  ensureSchema(host.db);
  const dispose = host.registerDomain({
    id: "wb-addon-tasks",
    title: "任务记录",
    version: "2.0.5",
    tables: ["task", "task_node"],
    actions: { ...tasks, ...tree },
    views: [{ id: "tasks", title: { zh: "任务记录", en: "Tasks" } }],
  });
  ctx.effect(() => dispose, "tasks domain");
}
```

> 实际 `tables` 只写任务相关表；这里只是结构示意。

`lib/client.js` 仍是 IIFE，但模块 id 改为包名 `dsh-workbench-tasks`，在 factory 内调用 `window.__WB_HOST__.registerAddon({...})`。因为 `dsh.client.inject` 已保证宿主客户端先加载，无需轮询。

标签、站点同理；站点的 `capabilities.tags` 改为通过 `host.hasDomain("wb-addon-tags")` 判断，不再通过 `api.hasAddon`。

## 4. 宿主服务契约

建议先在 `packages/sdk` 定义：

```ts
export interface DomainActionDef {
  description?: string;
  input?: unknown;
  execute(args: any, ctx: { origin: "ui" | "agent" | "sync"; emit(event: string, data?: unknown): void }): any;
  render?(result: any): string;
}

export interface DomainViewDecl {
  id: string;
  title: { zh: string; en?: string };
}

export interface DomainDef {
  id: string;
  title: string;
  description?: string;
  version: string;
  tables?: string[];
  actions?: Record<string, DomainActionDef>;
  views?: DomainViewDecl[];
}

export interface WorkbenchHost {
  db: DatabaseSync;
  shellVersion: string;
  registerDomain(def: DomainDef): () => void;
  hasDomain(id: string): boolean;
  emit(event: string, data?: unknown): void;
  log(...args: unknown[]): void;
}
```

宿主只做注册、路由与广播；业务规则仍在各业务包里。

## 5. 客户端结构

宿主客户端保留现在的：

- `sidebar.panellist` 图标：个人工作台；
- root `main` 页；
- `settings.plugins.tab`；
- `window.__WB_HOST__ = { react, jsx, h, registerAddon, addons, error }`。

首页卡片不再来自服务端动态安装列表，而是来自 `registerAddon` 的已加载业务域：

- 任务卡 / 标签卡 / 站点卡；
- 账号与同步卡；
- 去掉“子插件”管理卡（安装/卸载交给 DSH 设置里的插件列表）。

全屏页、返回首页、SSE 刷新逻辑不变。

## 6. 安装、升级、卸载

### 安装任务

1. `dsh plugin --profile web add dsh-workbench-tasks`（或 DSH 插件页安装）；
2. pnpm 安装任务包，并把 `dsh-workbench` 作为依赖一起安装；
3. 插件管理器把任务包加入 `dsh.profile.bundles`；
4. 任务 bundle patch 插入 `workbench` 行 + `workbench-tasks` 行；
5. 重启 DSH 后，宿主加载，任务插件 `inject: ["workbench"]` 注册域；
6. 首页出现任务卡。

### 安装第二个业务包

- 标签 bundle patch 再次插入 `workbench` 行；
- loader 按 id 折叠，仍只有一个宿主实例；
- 首页多一张标签卡。

### 卸载

- 从 `dsh.profile.bundles` 移除业务包；
- `pnpm remove` 删除业务包；
- 若没有其他包依赖宿主，宿主也可能被一起删除（pnpm 的传递依赖清理）；
- 数据表保留在 `workbench.db`；
- 重装后数据仍在。

> 这是“装业务包自动装宿主”的自然结果：最后一个业务包卸载后，宿主可能一起消失。若希望宿主常驻，需要用户显式安装 `dsh-workbench`，或在未来给 DSH 增加“直接依赖展开”能力。

## 7. 数据迁移

- 数据库路径不变：`~/.dsh/workbench/workbench.db`。
- 表名不变：`task`、`task_node`、`tag`、`tag_mapping`、`site`、`site_node`、`site_node_mapping`。
- 现有 `~/.dsh/workbench/addons/` 目录与 `addons.json` 不再读取；可以保留一个版本用于回滚，之后手动清理。
- 旧 `tasks` 表已在 2.0.x 迁到 `task`/`task_node`，新插件沿用 `ensureSchema`，不会重复迁移。
- 行级同步表由宿主汇总业务域声明；`task_node`/`site_node` 的“整树快照”仍未实现，继续沿用当前策略（先保证本地，快照作为后续项）。

## 9. 实施顺序

1. **类型与宿主服务**：sdk 增加 DomainDef/WorkbenchHost；shell 提供 `workbench` 服务，保留旧数据库与账号/同步。
2. **宿主页面改造**：首页卡片改为域注册；删除子插件管理页与安装 API。
3. **任务插件化**：新增 `cordis.patch.yml`、DSH Node 入口、客户端入口；复用现有 `db.js/tasks.js/tree.js/client.js`。
4. **标签、站点插件化**：同上；站点通过 `host.hasDomain` 检测标签。
5. **移除运行时下载器**：删除 AddonManager/tar/市场分支；清理文档。
6. **安装验证**：临时 profile + 本地 tarball/本地 registry 验证“装任务自动装并激活工作台”。
7. **真实 GUI 验收**：现有工作台数据、任务/标签/站点功能回归；卸载保留数据。
8. **文档与提交**：docs/02、04、05、08、09、10、11、README 全面改写；提交。

## 10. 已决定

1. **包名**：无 scope，`dsh-workbench-tasks` / `-tags` / `-sites`，宿主 `dsh-workbench`。
2. **分发**：先用本地 `file:` 验证；最终可由 npm 或发布渠道提供，DSH 负责安装。
3. **最后卸载业务包**：允许工作台随最后一个业务包一起消失；需要常驻时把
   `dsh-workbench` 也作为 profile 直接依赖安装。
4. **“子插件”页**：删除；安装/卸载交给 DSH 设置里的插件管理。
