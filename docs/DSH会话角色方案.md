# DSH 会话角色方案

建议用输入框旁的一个角色选择器，统一今天的记录胶囊和任务发布入口。用户选择「任务发布者」，可以连续描述需求、补充截图、回答归属问题，再切到「任务执行者」继续处理刚创建的任务。业务插件负责定义这些角色，宿主负责让选择在正确的会话和轮次生效。

## 一、两个旧入口分别如何替代

| 现有行为 | 新入口与语义 | 需要保留的能力 |
| --- | --- | --- |
| 通用会话中打开记录，继续做原来的事 | 角色菜单里的「收尾时记录交付物」，默认关闭，可随主角色组合 | 显式选择、按会话持久化、先完成主任务，再按插件能力清单查重并只新增可复用成果 |
| 每次用 `/wb-task-publisher` 提交需求 | 任务插件贡献「任务发布者」，用户选一次即可连续发布 | 原话和附件、现状证据、任务表和工作区归属、时间线、标签、查重与发布回执 |
| 从已发布任务开始执行 | 同一插件贡献「任务执行者」，接收明确的任务引用 | 读取目标与验收标准，推进工作，将进展、阻塞或完成依据写回原任务 |

保留记录作为可选收尾行为，是因为「替我把这个问题解决，顺手记下结果」同时表达了两项意图。如果把记录做成互斥的主角色，用户就得在执行和记录之间二选一。界面只保留一个入口。菜单首段选择当前角色，末项控制记录，收起时可显示「任务执行者 · 记录中」。

## 二、用户如何开始和切换

1. 新会话默认「不使用工作台角色」。未选角色时，宿主返回空角色提示，DSH 使用原预设和工具权限。Agent 无须查询角色。选择后，由宿主在每次模型请求前注入当前角色，实际送入的文字占用输入 token。在首条消息前选好角色，首条原始消息和附件直接作为业务输入。当前版 DSH 的欢迎页先选择工作区，首次可发送消息的输入框已带真实会话 ID。选择器直接绑定这个 ID，保存成功后显示角色。绑定失败保留草稿，用户可重试。
2. 建议允许**在原会话切换，下一轮生效**。这样发布者给出任务编号后，用户可直接切到执行者说「按刚才的验收标准推进」。若上文涉及多个任务，先让用户选定目标。切换处留一条轻量标记，历史消息保留原角色语义。
3. 一轮开始时固定角色和记录选项。工具运行中选择新角色，界面显示「下轮使用」，当前工具调用继续按本轮约束处理。若希望隔离上下文，用户仍可另开会话。子会话默认通用、记录关闭。
4. 切到发布者本身只改变待发送消息的处理方式。用户说「先聊方案」就只讨论，说「发布这条需求」再进入发布流程。执行者在只有提议、尚无结果证据时，回报进度并保持任务未完成。

## 三、注册与运行契约（拟议）

| 负责方 | 职责 |
| --- | --- |
| 子插件 | 在现有业务域注册契约增设可选 `roles[]`。每项声明本域角色 ID、显示名、一句职责、版本、工作规则和所需 Workbench action。宿主从注册来源派生完整 ID，如 `wb-addon-tasks/publisher`。任务归属和发布规则由任务插件维护一份。 |
| 宿主 | 聚合角色目录，拒绝同域重复 ID，随插件卸载撤销注册。以本机数据库的会话 ID 为键保存所选角色、版本和记录选项，延续记录模式的本机状态范围。命令和界面共用状态读写，更新后通知已打开的窗口。 |
| DSH 对话接入 | 复用记录胶囊所在的 `conversation.input.left` 插槽。每轮按可信会话身份解析配置，每步组装系统提示时只加入本轮角色规则。模型能持续看到职责，聊天正文仍是用户原话。 |
| 调用路径 | 业务角色能调用的工作台动作取角色声明与现有 agent 授权的交集。列表与实际执行两处使用同一判定，计划模式禁止业务写入。角色不授予文件、浏览器或其他 DSH 工具权限。 |

自动记录沿用各域的 `capabilities.list/get` 和记录声明。为了同时允许执行者更新任务、限制自动记录只新增，收尾记录走单独可识别的调用上下文，只开放查重、声明的新增及必要关联动作。上下文来源由宿主确定。主流程已经创建或更新了目标任务，则在收尾回执中引用已有编号，避免为了「记一笔」再建一条任务。排除聊天原文、日志、密钥和内网地址。记录失败单独反馈，主任务结果照常交付。

**开发起点。** 已有输入区插槽、按会话持久化和按步装配提示三条接入路径。先验证欢迎页首轮绑定时序、是否能在 Workbench 调用端取得可信的会话与轮次标识，以及如何区分收尾调用。若缺少上下文，先补相应适配，再启用对应写操作。不能仅凭模型传入的角色或收尾标记放行。[工作台架构指南](ARCHITECTURE.md) · [记录模式原理](会话记录模式.md) · [输入区接入](../packages/shell/client/client.js#L6781)

## 四、任务插件首版的行为

**任务发布者。** 将现有发布 SOP 从一次性的用户消息移到角色规则。沿用现行判断：明确要求发布、信息齐全且归属唯一时直接发布。任务表职责相当、信息冲突或查重命中时先提问。沿用自建节点、时间线、工作区和标签的条件，回执列出任务编号、归属和本次自建内容。每个独立需求使用独立且可重试的去重键，解决同一发布会话连续创建多项任务时仅用会话 ID 会发生的碰撞。[现有发布规则](../packages/addons/tasks/lib/publisher/brief.js)

**任务执行者。** 明确目标任务后读取当前状态、工作区、验收标准，再按用户要求执行。用户只问进度就只读。回写时限于当前目标，记录完成项及证据或具体阻塞。切换角色不等于自动开工、重开任务或标记完成。

## 五、过渡和退出旧实现

1. 先交付宿主角色目录、选择器和两种任务角色。在独立 profile 验证首轮绑定和调用约束，再迁移现有会话。
2. 一次性迁移旧记录状态：开启行映射为「不使用工作台角色＋记录开启」，关闭或无记录映射为默认值，已存在新配置的行优先。升级保留业务数据，不回扫历史聊天。旧命令的使用历史不作为持续角色授权。
3. 保留一个兼容版本。`/record on|off|status` 和旧记录接口读写新配置的同一字段。`/wb-task-publisher <需求>` 以**单次发布角色**处理该请求，保留正文和附件，结束后回到用户原先所选角色。旧入口与新入口共用规则，每轮只注入一次。提示用户今后可从角色菜单进入。
4. 兼容用例、旧客户端切换和真实 profile 验证通过后，再退役旧胶囊、专用提示和命令入口，更新使用文档。兼容期保留旧表及迁移前快照以供回退，回退前从新配置导出当前记录选项，避免恢复过期偏好。角色插件卸载后，历史可读，输入框提示重新选择，再恢复业务调用。

### 兼容期回退

退回旧宿主前，先退出 DSH 并备份本机工作台数据库。旧版本只读取 `session_mode`。如需保留升级期间改变的记录偏好，在备份后对实际工作台数据库执行下列事务，再用原安装源恢复宿主和任务插件。角色与业务表保留。

```sql
BEGIN IMMEDIATE;
INSERT OR REPLACE INTO session_mode(session_id, enabled, updated_at)
SELECT session_id, enabled, updated_at FROM session_role;
COMMIT;
```

## 六、评审与验收

| 场景 | 应看到的结果 |
| --- | --- |
| 装入贡献新角色的插件，再卸载 | 无需修改宿主菜单即可出现角色，卸载后不可再发起该角色调用 |
| 选发布者，带截图连续发两条不同需求，再重试第一条 | 首轮即按发布流程处理，两个需求有各自编号，重试复用原任务 |
| 在原会话从发布者切到执行者 | 正在进行的轮次维持原角色，下轮读到正确任务，写回进度有据可查 |
| 通用会话开启记录，另开会话，重启并恢复 | 仅原会话启用收尾，纯问答不落库，任务已发布时没有重复任务 |
| 禁用某个动作、进入计划模式、尝试从记录阶段修改任务 | 直接调用也按实际授权拒绝，普通页面仍按原有权限工作 |
| 迁移开启与关闭的旧会话，混用命令和界面 | 两个入口状态一致，旧发布命令单次生效，主任务只执行一次 |

**已确认的产品取舍**：① 同一会话可切换角色，从下一轮生效；② 收尾记录可与任一角色组合，默认关闭；③ 明确要求发布且信息齐全时沿用直接发布，旧命令保留一个兼容版本。
