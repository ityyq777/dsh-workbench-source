# 跨插件界面插槽设计

> 状态：设计定稿（阶段 0）。任务：`01a1fcba-76bb-7c62-8efa-bf7e36e74e2d`。
> 一句话：宿主提供**命名插槽**，插件把组件贡献进别人的界面；落点由属主插件声明，贡献方只声明"挂到哪个槽、排第几"，两侧都不需要编译期依赖。

## 1. 为什么要有它

现状（依据仓库源码）：

- 服务端已经能跨域调用：`ctx.workbench.invoke` / `DomainSetupApi.call`（`packages/sdk/src/index.ts:179`、`:312`）。
- 客户端也能跨域调用：`apiFor(id).call` 会按 action 前缀路由到目标域（`packages/shell/client/client.src.cjs:46-61`）。
- 但界面只能整块注册：`registerAddon(mod)` 只接受 `{id,title,version,views[]}`（`packages/shell/client/client.src.cjs:76-83`），宿主 `ViewOutlet` 只在自己那块区域渲染属主插件的视图（`packages/shell/client/view-outlet.cjs:22-30`）。
- 结果是跨插件协作只剩一种形态：**编译期硬依赖 + 整页拦截**。唯一实例是邮件依赖保险箱（`packages/addons/mail/package.json:65`、`packages/addons/mail/lib/index.js:54`），代价是邮件里多了一个整页门禁 `packages/addons/mail/client/ui/vault-gate.cjs`。

所以今天"在邮件里看到一封要跟进的信 → 建一个任务"做不到，除非让邮件依赖任务（方向反了：任务才是通用能力，邮件是具体场景）。

## 2. 目标与非目标

目标：

1. 插件 A 能把组件贡献到插件 B 的界面，**A 不依赖 B，B 不依赖 A**。
2. 顺序只由贡献自身的 `(order, id)` 决定，**与安装顺序、加载顺序无关**。
3. 任何一方缺失或抛错，页面照常可用，且缺口**可见**（能力清单/控制台），不静默消失。
4. 首个真实用例：邮件动作条 +「从邮件创建任务」，并能从任务回到原信。

非目标：

- 不做贡献的手工拖拽排序、不做运行期热插拔权限模型。
- 不做 Cypht 式的 `before/after` 相邻锚点。理由见 §3.4。
- 不改邮件/任务的存储结构（回链写进任务描述，见 §6.3）。

## 3. 契约

### 3.1 插槽目录由宿主定义（白名单）

宿主在 `packages/shell/client/slot-catalog.cjs` 里声明全部插槽，随桥暴露给插件：

| 插槽 id | 落点（属主） | 渲染形态 | props 契约 |
| --- | --- | --- | --- |
| `item.actions` | 任何列表/详情的条目属主 | 一行按钮 | `item: WbItemRef` |
| `view.toolbar` | 插件视图工具条 | 一行按钮 | `view: { addonId, viewId }` |
| `settings.sections` | 配置页 | 分段块 | `owner: string` |
| `home.card.footer` | 首页卡片底部 | 一行文字/按钮 | `card: { addonId, title }` |

未知插槽 id：宿主**拒绝注册**并 `console.error`，不进入渲染队列，不影响其它贡献。

### 3.2 贡献声明

```js
host.registerAddon({
  id: "wb-addon-tasks",
  views: [/* ... */],
  slots: [
    { slot: "item.actions", id: "create-from-mail", order: 50,
      title: { zh: "建任务", en: "New task" }, component: CreateFromMail },
  ],
});
```

也可单独注册（动态贡献）：

```js
const off = host.registerSlot({ slot: "item.actions", id: "x", order: 10, component: X });
```

字段：

- `slot`：插槽 id，必须在宿主目录内。
- `id`：同一插槽内唯一；**重复注册后到者被拒**（不覆盖前者），并 `console.error`。
- `order`：升序，缺省 `100`。相同 order 按 `id` 字典序比较，保证结果与安装顺序无关。
- `title`：`string | {zh,en}`，宿主用于按钮/分段标题与诊断显示。
- `icon`：可选函数组件（size=14）。
- `component`：函数组件，按 §3.3 的 props 调用。

### 3.3 贡献组件的 props

```js
{ slot, item?, ownerId, contributorId, lang: "zh" | "en", t(key), api, onNavigate(viewId?, params?) }
```

- `api` 是**贡献方自己域**的 api（`apiFor(contributorId)`），不是属主的；跨域写入由贡献方自己发起，权限与审计仍归它自己的 action。
- `onNavigate` 跳到贡献方自己的视图（`host.navigateAddon(contributorId, viewId, params)`）。
- `lang` / `t` 沿用属主当前语言，保证同一块区域语言一致。

`item`（`item.actions` 专用，宿主定义，属主只填值）：

```ts
interface WbItemRef {
  kind: string;   // "mail.message" / "task" / "site" …
  id: string;
  title?: string;
  subtitle?: string;
  url?: string;
  /** 属主自定义字段；贡献方不得依赖，仅可透传回属主 */
  [key: string]: unknown;
}
```

把 `item` 定义在宿主而不是属主，是为了**贡献方可移植**：同一个「建任务」按钮既能挂在邮件上，也能挂在连接器条目上，不用为每个属主写一份。

### 3.4 为什么不用 before/after 相邻锚点

Cypht 的 `add_output(page, name, enabled, module, anchor, before|after)` 靠"插在某个模块名前后"排序（`_archive/cypht-master/lib/modules.php:245-260` 的 `insert_at_marker`）。它成立的前提是：所有模块在同一份配置里一次性装配、构建期固化（`lib/config_builder.php:404`），顺序在部署时确定。

我们的插件是用户用 npm 逐个安装的，安装顺序不可控。若采用相邻锚点，"UI 顺序"会退化成"谁先装谁先上"，比 Cypht 更不确定，而且锚点缺失时只能降级（Cypht 的做法是排队重试两次后只写一条 `Hm_Debug`，见 `lib/modules_exec.php` 的 `$queue_limit = 2`；真实后果：禁用 imap 会让 tags 的设置整段静默消失，因为 `modules/tags/setup.php:23` 的锚点 `sent_source_max_setting` 属于 imap 模块集）。

结论：只保留 `(order, id)` 全局排序——顺序可解释、与安装顺序无关、缺谁都不影响谁。

## 4. 渲染与隔离

宿主导出 `Slot` 组件（`window.__WB_HOST__.Slot`），属主这样用：

```js
h(host.Slot, { slot: "item.actions", item: { kind: "mail.message", id: m.id, title: m.subject }, lang: props.lang, t: props.t })
```

渲染规则：

1. 取该插槽的贡献列表，按 `(order, id)` 升序。
2. 空列表 → 渲染 `null`（不占位、不报错）。
3. 每个贡献单独包一层 `SlotBoundary`（class 组件，`componentDidCatch`）：某个贡献渲染抛错只让这一个消失，`console.error` 记录插槽 id、贡献 id、错误，不影响相邻贡献与属主页面。
4. 贡献是异步注册的（客户端模块可能后加载）→ `Slot` 订阅注册表变化，注册后自动补渲染。
5. 属主卸载或插件被卸载 → `setAddons` 清理时按 `addonId` 撤销该插件的全部贡献（`client.src.cjs:84-91` 的既有清理路径）。

## 5. 失效可见

三层：

1. **运行期**：未知插槽、重复 id、非函数组件一律 `console.error`（沿用 `registerAddon` 现有的报错风格与中文文案）。
2. **诊断接口**：`host.slotContributions(slotId)` 返回 `[{ id, addonId, order, title, ok }]`，`ok: false` 表示该贡献曾抛错；`host.slots` 返回宿主目录。测试与将来的诊断面板都读它。
3. **能力清单**：`DomainDef.slots?: string[]` 声明"我这个插件往哪些槽贡献"，`DomainDef.slotHosts?: string[]` 声明"我渲染哪些槽（提供落点）"。`capabilities.*` 输出 `slots: { contributes: [{slot, hosts, missingHost}], renders }`；`missingHost` 为真时给 warning：**"插槽 X 暂无落点：没有已启用的插件提供该界面，这个贡献不会显示"**。

   为什么是两个字段：只看"谁贡献"回答不了"对方没装会怎样"。加上"谁提供落点"，服务端才能在不看客户端状态的情况下算出一个诚实的结论——声明了贡献、但当前没有任何已启用插件渲染该槽。这条不追求与客户端注册表强一致（客户端装了哪些插件、注册成功没有，服务端看不到），只回答"声明往哪挂、当前有没有地方挂"。

## 6. 首个消费者：邮件 → 任务

### 6.1 邮件侧（属主）

`packages/addons/mail/client/views/messages.cjs` 的详情工具条 `wbml-tools`（`:526` 起）末尾追加：

```js
h(host.Slot, { slot: "item.actions", item: { kind: "mail.message", id: current.id, title: current.subject, subtitle: sender(current) }, lang: props.lang, t: props.t })
```

`item` 只放**非敏感摘要**（id / 主题 / 发件人）。正文与附件不进 `item`；贡献方需要时用自己的 action 读，权限走贡献方自己的域。

### 6.2 任务侧（贡献方）

新增 `packages/addons/tasks/client/slots/create-from-mail.cjs`：一个按钮「建任务」。点击后：

1. 用 `api.call("tasks.create", {...})` 创建任务，`title = "跟进：" + item.title`，`description` 写来源行（§6.3）。
2. 成功后按钮就地变成「已在任务中」，并提供「打开任务」用 `onNavigate("tasks", { taskId })`。

不新开弹窗：第一版只需要"一键把信变成待办"，复杂编辑留给任务插件自己的创建弹窗。

### 6.3 回链

任务描述里写一行规范文本：

```
来源邮件：wb-mail:<messageId>
```

格式固定（前缀 `来源邮件：wb-mail:`），任务侧可以正则提取。邮件侧不存反查表，避免新增表与同步负担。

**回到原信**：宿主导航加参数（`navigateAddon(addonId, viewId, params)` → `addonNav.navigate` → `go(route, params)`），邮件主视图读 `viewParams.messageId` 后在列表就绪时选中该封。这样"任务 → 原信"是一次普通路由跳转，不需要插件互相依赖。

## 6.4 第二个消费者：站点 → 保险箱（对象管理界面由贡献方提供）

「从邮件建任务」是贡献方加一个动作；站点与保险箱的关系更进一步——**管理界面本身**由贡献方提供，
属主只放落点：

| 角色 | 谁 | 做什么 |
| --- | --- | --- |
| 落点属主 | 站点 | 记录页每行 `h(host.Slot, { slot: "item.actions", ownerId: "wb-addon-sites", item: { kind: "site", id: s.id, title: s.siteName } })` |
| 贡献方 | 保险箱 | `slots: [{ slot: "item.actions", id: "vault.bind-site-groups", order: 90, component }]`；组件只认 `kind === "site"`，其余返回 `null` |

为什么这么分工：

1. **写入方唯一**。`vault_binding` 只由保险箱写（`vault.bind` / `vault.unbind`）。站点以前有一份
   只读弹窗 + 「请去保险箱绑定」的文案，两边都不完整；现在站点连读取都不做了，`sites.vaultGroups`
   只留给 agent 查询。
2. **属主不认识来源**。站点不知道分组有哪些、组里几条凭据、关联状态怎么判——这些都在贡献方
   自己的域里。站点只提供对象引用（`kind/id/title`），符合 §7.5 的同一条不变量。
3. **装没装都能用**。未装保险箱时插槽没有贡献，站点行里就是不出现按钮，不留空按钮、不报错；
   `capabilities.list` 用 `slotHosts`（站点）与 `slots`（保险箱）两边声明互相配对，缺一半会写「暂无落点」。

配套的一件小事：站点 setup 调 `vault.subjectRegister({ type: "site", title: "站点" })` 登记对象类型，
保险箱分组页的「关联对象」才显示中文名（`subjectsOf` 的 title 来自 `vault_subject_type`）。
删站点时仍由站点调 `vault.bindingPurge` 清映射，长期改成订阅 `site.deleted` 事件。

### 7.4 与初版设计的差异

1. **审计改成加载构建产物**：初版写"扫源码里的 `slot:` 声明"，正则扫描容易误判（`slot:` 也出现在别处）。改成在 vm 里加载 `lib/client.js`、拦截 `registerAddon` 拿到真实声明，结论更硬。
2. **贡献组件路径**：初版写 `tasks/client/slots/create-from-mail.cjs`，实际放在 `tasks/client/views/slot-task-from-message.cjs`——和已有视图同目录，构建脚本的入口规则不用改。
3. **新增 `slotHosts`（提供落点）**：只有"谁贡献"无法回答"对方没装会怎样"。加上"谁渲染"才能让 `capabilities` 说出"当前没有插件提供该界面，这个贡献不会显示"。
4. **未 bump 插件版本**：本轮只做功能与测试，不做发布；发版时按 `05-发布与插件市场.md` 统一 +0.0.1。
5. **不写旧宿主兼容分支**（按用户要求"一切以最新的为主"）：插槽链路直接依赖 `host.Slot`、
   `host.navigateAddon` 与 `react.Component`，缺了就是宿主版本不对，不做 `host.Slot ? … : null`
   这类静默降级——静默降级会让"插槽没生效"看起来像"没装贡献方"，排查成本远高于直接报错。
   插件声明 `minShell` 表达这个下限。

## 7.5 回链由来源贡献：属主不解析来源

「从邮件建任务」只解决了一半——任务详情要能跳回原信。第一版把这件事写在任务里：
`task-item.cjs` 用 `MAIL_REF = /wb-mail:(...)/ ` 匹配描述、自己渲染「原邮件」、自己判邮件插件是否安装。
这等于每加一个来源（站点、日历、消息）都要在任务客户端再长一段 `SITE_REF`、`CAL_REF`。

现在改成插槽，方向与「建任务」相反：

| 角色 | 谁 | 做什么 |
| --- | --- | --- |
| 落点属主 | 任务 | `h(Slot, { slot: "item.actions", ownerId: "wb-addon-tasks", item: { kind: "task", id, title, description } })` |
| 贡献方 | 邮件 | 匹配 `item.description` 里的 `wb-mail:<id>`，渲染「原邮件」，点击 `props.onNavigate("messages", { messageId })` |

三条不变量：

1. **属主不认识任何来源前缀**。任务只把描述原文当纯文本透传（本地渲染，不过网），
   连 `wb-` 都不出现；`scripts/test-addon-slots.mjs` 的 D2 用例直接断言任务源码里没有 `wb-mail`。
2. **贡献方自己匹配、自己跳转**。`onNavigate` 由宿主按贡献方的域绑定，只传视图 id 与参数，
   贡献组件不用拼 `addonId`，也不碰 `window.__WB_HOST__`。
3. **加来源零改属主**。D3 用例注册第三个贡献（`calendar.back-to-event`）证明同槽可容纳任意来源，
   卸载时按 `addonId` 只撤销它自己那条。

同一个槽因此有了双向用途：任务 → 邮件的「建任务」，邮件 → 任务的「原邮件」。
落点组件按 `item.kind` 各自返回 `null`，互不干扰；没有贡献方时 `item.actions` 渲染 `null`，
任务用 `.wbt-metazone:empty{display:none}` 保证元信息区不会留空盒子。

## 8. 风险与权衡

| 风险 | 处理 |
| --- | --- |
| 贡献方在别人的界面里做重活，属主页面被拖慢 | 契约要求贡献组件轻量；重逻辑走异步 action，渲染期不阻塞；`Slot` 不做 Suspense 包装，贡献方自己控制 loading |
| 属主升级后 `item` 契约变化 | `item` 定义在宿主，属主只填值；给 `kind` 加命名空间前缀（`mail.message`），贡献方按 `kind` 分支而不是按属主 |
| 贡献方悄悄全量拉邮件正文 | 契约禁止（§6.1），落点上只给摘要；需要正文时贡献方自己调自己的 action，留审计 |
| 顺序仍可能被误用成"依赖" | 文档明确：order 只表达视觉优先级，不表达依赖；跨插件依赖一律走 action |
| 卸载后残留贡献 | `setAddons` 按 addonId 撤销；测试覆盖 |

## 9. 验收对照

| 任务验收标准 | 本设计的落点 |
| --- | --- |
| 卸掉任务插件后邮件视图照常、能力清单有说明 | §4 空列表渲染 null（`setAddons` 按 addonId 撤销）；§5.3 `contributes[].missingHost` + warning |
| 单个贡献抛错只影响该按钮 | §4 `SlotBoundary`；`scripts/test-addon-slots.mjs` 的 B3 用例 |
| 不同安装顺序最终顺序一致 | §3.2 `(order, id)`；`scripts/test-addon-slots.mjs` 的 A3 用例（两种注册顺序比对） |
| 任务可回溯原信 | §7.5 回链由邮件自己的贡献渲染；描述里的 `wb-mail:<id>` 只当文本透传 |
| 加新来源不用改任务 | §7.5 三条不变量；`scripts/test-addon-slots.mjs` 的 D2/D3 用例（任务源码不含 `wb-mail`、第三个贡献零改属主） |
| 单测覆盖排序/隔离/缺失 | `pnpm test:slots` = `scripts/test-addon-slots.mjs` + `scripts/audit-slots.mjs` |
