# 13 会话角色

> 本章回答：会话角色是什么、谁声明、什么时候生效、注入什么、存在哪里、插件怎么接、
> 被拒了怎么查。
> 角色只决定“这一轮模型收到哪份业务规则”；它**不限制能调哪些动作**，也不是 DSH 的 agent
> preset，不是操作系统用户，也不是插件本身。动作本身的定义与分发见
> [05 Action 机制](05-Action机制.md)，来源权限与审计见
> [09 权限、审计与安全](09-权限审计与安全.md)。

## 1. 角色是什么，不是什么

角色是**会话级**的选择：用户在输入框左侧选一个角色，宿主在每一轮组装模型请求时注入
这个角色的正文规则。切换角色不丢已有消息、附件和任务引用，它只影响之后的轮次。

先划清三个容易混的东西：

| 容易混淆的概念 | 与本角色的关系 |
| --- | --- |
| DSH 的 agent preset | 无关。preset 决定工具集与系统提示骨架，角色是工作台在系统提示里追加的一段业务规则 |
| 操作系统用户 / 账号 | 无关。角色不携带身份与凭据，只带规则文本与可选的动作提示清单（不产生拦截） |
| 插件本身 | 相关但不同。角色由插件在 `DomainDef.roles` 声明，随插件上下线；选中之后，插件卸载会让角色失效（第 6 节） |

角色只做一件事：**注入规则**（模型看到的业务约束）。`instructions` 里可以写“本角色涉及
哪些 action、按什么顺序调”，那是 SOP 描述，由模型自己遵守；`actions` 字段保留下来，只用于
界面展示与按动作名检索，**不产生任何拦截**——选了角色照样能调任意动作，宿主不再当警察。

## 2. 三个概念：插件角色、用户角色、会话绑定

| 概念 | 来源 | 存放 | 生命周期 |
| --- | --- | --- | --- |
| 插件角色 | 业务域在 `registerDomain(def)` 里声明 `roles[]` | 只在内存里，随域注册 | 插件加载即在、卸载即撤 |
| 用户角色 | 用户在角色管理页“复制为新角色”或新建 | `user_role` 表（`definition` 存正文与动作） | 用户自己维护，域名记为 `user` |
| 会话绑定 | 用户在选择器里选中的那一个 | `session_role` 表（`role_id` + `role_version`） | 每个会话一行，切角色即覆盖 |

完整角色 id 由宿主拼出来：插件角色是 `<域 id>/<角色 id>`，例如
`wb-addon-tasks/publisher`；用户角色是 `user:<uuid>`，冒号不属于合法业务域标识，
因此两者永不重名。声明校验在 [`packages/sdk/src/roles.ts`](../../packages/sdk/src/roles.ts)：
`id` 必须是以字母开头的小写标识、域内唯一；`actions` 可不写（缺省按空数组处理），写了就必须
是 `tasks.list` 这种完整动作名（不接受 `*`），重复项会被去重——校验只为拦住脏数据，不代表权限。

## 3. 生效时机：每轮一次快照

宿主在 `agent/inbox/claimed` 时调用 `claim({agent, message, turn})`，按
`session_role`（以及第 7 节的单次绑定）为这一轮生成快照，模型请求期间读的是快照而不是表。
因此：

- **轮中切换角色，下一轮才生效**：快照在轮次开始时定下，本轮已发出的请求不受影响。
- **同一轮不会重算**：`claim` 只在轮次号变化时重新 `capture`，避免中途把规则换掉。
- **子会话不继承**：没有绑定记录的会话 `prompt()` 返回空串，不会拿到父会话的角色。

切角色不丢消息、附件与任务引用：绑定只写 `session_role` 一行，动的是“下一轮注入什么”。

## 4. 注入什么：只有 instructions

宿主用 `systemPrompt.section({name:"workbench:session-role"})` 注册一个系统提示分段
（order 取 `PLAN_POLICY` 之后 10，老版本退回 510），正文就是角色的 `instructions`，另附
会话 id 与来源消息 id。参见
[`packages/shell/src/index.ts:540`](../../packages/shell/src/index.ts)。

三条边界：

- **不占工具调用**：agent 不需要“查我的角色”，规则直接进上下文。
- **不注入动作清单**：`actions` 只用于校验，不写进提示词，避免模型把它当能力目录。
- **未选角色时返回空串**：宿主不注入任何“你没有角色”的说明，普通对话不受影响。

## 5. 动作权限：角色不再参与拦截

[`packages/shell/src/session/tool-policy.ts`](../../packages/shell/src/session/tool-policy.ts)
的 `allows(name)` 只剩两条与角色相关的判定，都跟“角色能调什么”无关：

- **角色失效**：选了角色但 `available(snapshot)` 为假（插件卸载、版本变了、用户角色被删），
  拒绝并抛 `ACTION_ROLE_STALE`，提示“当前工作台角色已变更，请重新选择后再调用该动作”。
- **计划模式只读**：选了角色且处在计划模式时，只放行 `tool-policy.ts` 顶部 `reads` 里的只读
  动作，其余抛 `ACTION_PLAN_READ_ONLY`。

`actions.includes(...)` 的判断已经删除：`actions.list` / `actions.help` 也不再按角色收窄，
agent 能看到并查到任意业务动作。动作准入剩下的两层是 **agent 来源开关 → 动作自身 `origins`**
（见 [09 权限、审计与安全](09-权限审计与安全.md)），跟角色无关。

越权风险改由角色指令自律：想约束“发布者不要改别人任务状态”，就把这条写进 `instructions`
（例如“`tasks.update` 只用于回修本轮自己刚发布的任务”），而不是指望动作清单兜底。

## 6. 存储与版本：`role_version` 跟着会话走

三张表都在 `packages/core/src/schema.ts`，都不参与备份与云同步：

| 表 | 列 | 作用 |
| --- | --- | --- |
| `session_role` | `session_id`、`role_id`、`role_version`、`updated_at` | 会话当前选中的角色与**选中时的版本** |
| `user_role` | `id`、`version`、`definition` | 用户角色的正文与动作；每次编辑换一个新版本 |
| `session_message_role` | `session_id`、`message_id`、`role_id`、`role_version` | 单次命令的角色绑定，消费后即删（第 7 节） |

`role_version` 是最容易记错的一点：会话存的是**选中时的版本**，不是“这个角色现在是什么
版本”。`available(snapshot)` 的判定是
`snapshot.version === live.version && (是用户角色 || 快照对象仍是当前对象)`
（`packages/shell/src/session/roles.ts:75` 附近）。所以：

- 插件改了角色声明（`version` 变了）→ 已绑定旧版本的会话**不再生效**，`prompt()`
  返回“原选工作台角色已变更，请用户重新选择后再进行业务操作。”，而不是静默沿用旧规则。
- 插件卸载 → 目录里 `resolve` 不到该角色 → 同样失效；重新装回来且版本一致时恢复。
- 用户角色被编辑 → 版本换新 → 绑定失效，需要重选；删除用户角色同理。

这也是“角色声明改了要升 `version`”的硬理由：不升版本，旧会话会继续用旧规则文本，
表现为“改了不生效”。

## 7. 单次角色：命令只绑自己派发的消息

`bindMessageRole(sessionId, messageId, roleId)` 把角色绑到**一条消息**上，返回撤销函数。
下一轮 `claim` 命中这条消息时，快照带上 `once: true`，注入时会多一句“用户通过业务命令
明确要求在本轮执行该角色流程。此授权仅适用于命令关联的消息。”；读完即从
`session_message_role` 删除，下一轮自动回到会话原来的角色（可能为空）。

典型用法是任务插件的 `/wb-task-publisher`：命令本身不建任务，只登记这条消息的发布者角色，
派发失败时调用撤销函数。宿主侧还会在 `agent/inbox/discarded` 时清掉残留绑定。命令与
选择器共用同一份角色定义，所以规则正文不会有两份。

## 8. 插件接入

在 `registerDomain(def)` 里加 `roles[]`，用 `instructions` 写清“只做什么、不做什么、涉及哪些
动作”；`actions` 可写可不写，写只为了让管理页与选择器能按动作名检索：

```js
// 最小可运行声明：只读角色
roles: [{
  id: "reviewer",
  name: "文稿审阅者",
  description: "审阅用户提供的文稿并标出待核实的结论",
  version: "1",           // 改规则文本时必须升，否则旧会话继续用旧规则
  instructions: "领到文稿先用 tasks.get 取正文，再按 tasks.list 找同批稿件；先引用待核实的原句，\n再说明需要什么证据；不要直接改写正文。",
  actions: ["tasks.get", "tasks.list"],   // 仅展示/检索用，不构成权限
}]
```

接入步骤：

1. 声明 `roles[]`，`id` 用域内小写标识；`actions` 可选，只作参考清单，权限不在这里。
2. `instructions` 写成边界式规则（“只做什么 / 不做什么 / 输出什么”），它会被原样注入系统提示。
3. 加一个验证用例：选中该角色后首条消息按职责处理，且没写进 `actions` 的动作照样能调（第 12 节）。
4. 角色改版时升 `version`，并在功能清单里说明旧会话需要重选。

## 9. 真实样例：同一领域的两种职责

任务插件声明了一对角色，用同一份动作清单的子集划出两条边界
（[`packages/addons/tasks/lib/publisher/roles.js`](../../packages/addons/tasks/lib/publisher/roles.js)）：

| 角色 | 版本 | 动作 | 用途 |
| --- | --- | --- | --- |
| 任务发布者 `publisher` | 1.1.0 | 只读 + `tasks.create`、`tasks.update`、节点/时间线/工作区相关写动作 | 整理需求、发布任务；`tasks.update` 只用于回修本轮自己发布的任务 |
| 任务执行者 `executor` | 1.0.0 | 只读 + `tasks.update` + `tasks.complete` | 推进已有任务、回写进展与验收证据；不能发布新任务 |

发布规则正文在 `packages/addons/tasks/lib/publisher/brief.js`，`/wb-task-publisher` 命令
与角色注入共用它。上面表里的“动作”只是这两个角色**常用**的动作清单，不是权限：执行者调
`tasks.create` 也不会被宿主拦。真正把两者区分开的是 `instructions` 里的边界（“只能改自己刚
建的任务”“不能发布新任务”），属于提示层，靠模型遵守。

- 声明契约（`DomainRoleDef` 的字段与校验）写在
  [03 SDK 与插件契约](03-SDK与插件契约.md)，本章只讲运行时行为。
- 来源权限、开关、审计写在 [09 权限、审计与安全](09-权限审计与安全.md)；角色已不在权限链路里，

- 角色选择器的检索只读界面数据：`/workbench/api/session-role` 的 `roles[]` 带 `actions` 供「按动作名倒查角色」，
  这份列表不影响任何准入判定；
  过滤与高亮是纯函数（`packages/shell/client/conversation/session-role.cjs` 的 `filterRoles`/`splitHits`），可单测。
- 角色选择器与角色管理页属于界面，见 [07 视图与跨插件界面](07-视图与跨插件界面.md)；
  选择器贡献在 `conversation.input.left` 插槽（`packages/shell/client/client.src.cjs`，
  order 40），管理页在宿主 `roles` 路由：`packages/shell/client/conversation/catalog.cjs`（页面与列表/详情）、`catalog-editor.cjs`（编辑、预览与动作名校验）、`catalog-groups.cjs`（过滤、动作分组与校验的纯函数，单独可测）。
- 方案记录见 [`docs/DSH会话角色方案.md`](../DSH会话角色方案.md)：那份是当时的论证，
  现行契约以本章为准；两者冲突时以实现与本章为准。

## 11. 排障对照

| 现象 | 先查什么 | 常见原因 |
| --- | --- | --- |
| 选择器里没有这个角色 | 插件是否加载成功（域 `error`）、`DomainDef.roles` 是否声明 | 声明校验失败会让整域注册失败；`id` 重复或含大写也会被拒 |
| 选了但模型没按规则来 | `session_role` 是否有行、`role_version` 与目录是否一致 | 版本不一致时提示词被替换成“已变更，请重选” |
| 动作被拒（`ACTION_PLAN_READ_ONLY`） | 是否处在计划模式 | 计划模式下只放行只读动作，与角色无关 |
| 动作被拒（`ACTION_ROLE_STALE`） | 角色是否被卸载、改版或删除 | 版本对不上要先让用户重选，不是动作清单问题 |
| 改完角色声明不生效 | 角色的 `version` 是否升过 | 会话快照存的是选中时的版本 |
| 命令用了一次之后还在生效 | `session_message_role` 里是否有残留行 | 正常应立即删除；残留说明派发路径没走撤销或 `discarded` |
| 升级插件后旧会话失效 | 这是预期行为 | 版本变了要用户重选，不是 bug |

取证位置：`session_role` / `session_message_role` 两张表、宿主的 role 目录接口
（`/workbench/api/role-catalog`）与会话角色接口（`/workbench/api/session-role`）、
系统提示分段 `workbench:session-role` 的实际文本。

## 12. 验证

两条可复现的验证步骤（都在仓库内，不需要手动点界面）：

1. **选角色 → 首条消息生效，动作不受角色限制**：
   `node scripts/test-session-role-host.mjs`。它通过宿主公开入口注册一个带 `roles` 的示例域，
   选中后断言系统提示分段含角色规则、没写进 `actions` 的动作（`example.update`）能直接调通、
   `actions.list` / `actions.help` 也能看到它；随后切换自定义角色并编辑正文，断言旧绑定失效
   （`unavailable: true`）与重选后重新生效。
2. **命令单次生效，下一轮恢复**：同一脚本的后半段用 `bindMessageRole` 绑一条消息，断言只在
   该条消息的轮次注入“命令明确要求”，且绑定行读完即删、下一轮回到空角色。

脚本还断言「角色没声明的动作照样能调」与「计划模式只读另有错误码」，退出时打印
「通过：旧入口退役、目录、轮次隔离、动作不再按角色名单拦截、计划模式只读、命令单次角色与卸载失效」。
声明面校验另有 [`packages/sdk/test/roles.test.mjs`](../../packages/sdk/test/roles.test.mjs)。
