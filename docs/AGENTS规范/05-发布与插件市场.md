# 发布与插件市场

> 从根 `AGENTS.md` 拆出的发布链路、npm 发布、GitHub 镜像与市场维护规范。

## 插件市场发布与维护

个人工作台由一个宿主和多个 DSH 原生业务插件组成，发布链路与市场维护都按本节执行。
插件清单以 `packages/addons/` 下的目录为准，发布脚本按目录枚举，不维护第二份硬编码列表。

### 包与命名

| 用途 | npm 包名                  | 源码目录                    |
| ---- | ------------------------- | --------------------------- |
| 宿主 | `dsh-workbench-host`    | `packages/shell-dist`     |
| 任务 | `dsh-workbench-tasks`   | `packages/addons/tasks`   |
| 标签 | `dsh-workbench-tags`    | `packages/addons/tags`    |
| 站点 | `dsh-workbench-sites`   | `packages/addons/sites`   |
| 储物 | `dsh-workbench-storage` | `packages/addons/storage` |
| 消息 | `dsh-workbench-message` | `packages/addons/message` |
| 保险箱 | `dsh-workbench-vault` | `packages/addons/vault`   |
| 连接器 | `dsh-workbench-connector` | `packages/addons/connector` |
| 联系人 | `dsh-workbench-contacts` | `packages/addons/contacts` |
| 日历 | `dsh-workbench-calendar` | `packages/addons/calendar` |
| 邮件 | `dsh-workbench-mail`    | `packages/addons/mail`    |
| 弹幕 | `dsh-workbench-danmaku` | `packages/addons/danmaku` |

- npm 名由插件自身 `package.json` 的 `name` 决定，`scripts/stage-release.mjs` 原样沿用；
  只有宿主需要从内部名 `dsh-workbench` 改写成 `dsh-workbench-host`。

- 源码内宿主仍叫 `dsh-workbench`；npm 上该名字已被无关项目占用，对外发布名必须是
  `dsh-workbench-host`。不要在源码里直接改名，统一由 `scripts/stage-release.mjs` 改写。
- 业务包通过 `dependencies` 依赖 `dsh-workbench-host`，安装任意业务插件会自动带宿主。
- 源码仓库：`https://github.com/ityyq777/dsh-workbench-source`（origin，唯一开发入口）。
- 对外发布仓库：`https://github.com/ityyq777/dsh-workbench`（发布镜像，不是源码仓库）。
- 市场列表仓库：`https://github.com/awesome-dsh-plugin/awesome-dsh-plugin`；
  市场页面是 dshmarket.com。

### 版本升级

发布前同步修改：

1. 对应 `packages/addons/<name>/package.json` 的 `version` 与 `wb.addon.version`；
2. 对应 `packages/addons/<name>/client/client.src.cjs` 里 `registerAddon` 的 `version`
   （`lib/client.js` 是 `pnpm build:clients` 的产物，不要直接改）；
3. 宿主版本改 `packages/shell/package.json`，业务包依赖范围按需调整；
4. 文档中的版本引用（docs/04、docs/09、docs/10、docs/11 等）。

### 本地校验

```sh
pnpm build
node scripts/dist-shell.mjs
pnpm test:native
pnpm test:clients
pnpm test:tags
pnpm test:sites
pnpm test:e2e
```

涉及界面或安装链路的改动，还要重启一个临时 profile 实例做真实加载验证，不要重启
正在使用的 3080 主实例。

### 生成发布树

```sh
pnpm stage:release
```

输出在 `dist/release/`：

- `packages/host` 与 `packages/<插件>`：按 `packages/addons/` 目录逐个生成；
- `marketplace/*.yml` 草稿：宿主 + 每个插件一份，目录每次整目录重建；
- `release.json`：发布清单（宿主在前的包顺序），`publish-npm` 与 `publish-github` 读它，
  不再各自维护硬编码顺序；
- 根 README、LICENSE。

新增插件必须在 `scripts/stage-release.mjs` 的 `ADDON_META` 里登记
`description`/`keywords`/`marketCategory`/`marketEn`/`marketZh`：漏登记时脚本直接报错，
不会悄悄漏发；`ADDON_META` 里登记了但目录已删除同样报错。

检查 `package.json` 的 name/dependencies/files/dsh.client.inject，确认宿主 id、patch name、
业务包依赖都已改写为 `dsh-workbench-host`。子插件 patch 里的宿主行必须还在（独立安装靠它），
且必须是流式写法（块式会被插件市场判成「和已安装的插件冲突」），见
[`03-安装与交付.md`](03-安装与交付.md#子插件的宿主行必须保留且写成流式插件市场冲突的由来)；
改完跑 `node scripts/test-market-conflict.mjs --release` 与 `node scripts/verify-install-order.mjs`。

### npm 发布

- 必须用官方 registry：`https://registry.npmjs.org`；本机默认 npmmirror，不要用默认值发布。
- 首次需要：`npm login --registry=https://registry.npmjs.org`。
- 发布顺序固定：host 在前，其余按 `ADDON_META` 声明顺序；业务包依赖宿主。
- 发布前重进一次发布树：`pnpm build && pnpm dist:shell && pnpm stage:release`。
  `dist/release` 是 stage 时刻的快照，之后只要有一个提交改了版本号，发出去的就是旧包
  （2026-11-19 踩坑：源码已到 tasks 5.2.26 / host 0.8.0，发布树仍停在 5.2.20 / 0.7.0，
  npm 上因此「不是最新」）。
- 先 dry-run：

```sh
pnpm publish:npm
```

- 正式发布：

```sh
pnpm publish:npm -- --publish
# 有 2FA 时
pnpm publish:npm -- --publish --otp=123456
```

- 脚本发布前会逐包比对发布树与源码版本，不一致直接退出码 3 并列出差异，提示重建发布树；
  确认要用这份旧快照时才加 `--allow-drift`。
- 已存在的同名版本会被脚本跳过，不要为了重发而改版本号以外的元数据。
- 账号处于安全管控时不得尝试绕过；等限制解除后再发布。

### 更新 GitHub 发布镜像

发布镜像只放 `dist/release` 的产物，不直接编辑：

1. `pnpm stage:release`；
2. `pnpm publish:github`（dry-run，列出差异），确认后 `pnpm publish:github -- --publish`；
   脚本在 `~/.dsh/workbench/release-mirror` 里同步、提交（默认
   `release: workbench plugins <host 版本>`）并推送；
3. 源码仓库与镜像历史无关，**不要在源码目录里 `git push` 到镜像**（源码仓库只配置
   自己的 origin，不配置镜像 remote）；
4. 确认市场要求的 topic 存在：`dsh-plugin`（以及 `deepseek-harness` 等）；
5. 确认 `packages/<name>/package.json` 可通过 raw.githubusercontent.com 读取。

GitHub token 放在 `~/.dsh/workbench/github-token`（0600），只在推送时读取；
不得写入仓库、日志或对话。git 推送时不要把 token 持久化进 remote URL 或 git config。

### 插件市场收录与维护

- 一插件一个文件：`data/plugins/<owner>__<repo>.yml`；README 由脚本生成，不要手改 README。
- 本仓库是 monorepo：`url` 指向 `/tree/main/packages/<sub>`，`name` 用
  `ityyq777/dsh-workbench#<sub>`，文件名用
  `ityyq777__dsh-workbench--packages-<sub>.yml`。
- 必填字段：`url`、`name`、`category`、`description.en`；中文描述可选。
- 每个 PR 最多 3 个 entry，按每批 ≤3 个分批提交。历史情况：host/tasks/tags、
  sites/storage、message/vault/connector、contacts/calendar、mail 已分批合并；
  之后每个新插件单独补一条（工资 salary 即单独一批）。新增条目数超过 3 时不要塞进同一个 PR。
- 市场分支要基于分叉的 `origin/main` 建，不要基于 `upstream/main`：分叉里
  `.github/workflows/build-site.yml` 与上游不一致，令牌没有 `workflow` scope 时推送会被拒
  （`refusing to allow a Personal Access Token to create or update workflow ...`）。
  基于 origin/main 建分支后 PR 差异仍只含新增条目。
- 收录硬条件：
  - 仓库 `package.json` 声明 `dsh.bundle`；
  - 仓库创建满 1 天（CI 会自动重跑放行）；
  - 仓库带 `dsh-plugin` topic；
  - 真实可用代码，不是纯聚合包。
- 版本升级不需要改市场 YAML；市场读取仓库中的 package.json 与 npm 版本。
- 新增插件时才需要新增 YAML 并提 PR；发布前先跑市场仓库的
  `scripts/check-submission.mjs`。

### 发布完成检查

- npm 各包版本可查询：`npm view <pkg> version --registry=https://registry.npmjs.org`；
- 全新临时 profile 用 npm 包名安装 tasks，确认宿主被自动解析；
- 首页出现对应卡片，视图可打开；
- 市场页面能搜到插件；
- 记录发布版本与日期到 `docs/14-发布与插件市场.md`。

### 安全

- GitHub token、npm token 只存本机私有文件，权限 0600；
- 不打印、不提交、不写进文档；
