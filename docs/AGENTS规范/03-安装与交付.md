# 安装与交付

> 从根 `AGENTS.md` 拆出的 profile 核对、重装、桌面 CLI 与整目录同步规范。

## 交付前必须核对「profile 已安装版本 == 源码版本」（每个 agent 都走）

只改源码、只重启，用户看到的仍然是旧版本：profile 里是**拷贝安装**的产物，重启只是重载
那次拷贝。2026-11-10 踩坑：源码已经到 tasks 5.2.0 / tags 1.7.0 / sites 1.10.0 /
storage 1.5.0，desktop profile 里还是 5.1.3 / 1.6.13 / 1.9.4 / 1.4.3，用户重启后界面
毫无变化，还以为是代码没生效。

改完插件代码，交付前按顺序做完，并在回复里给出各步结果：

1. `pnpm build && pnpm dist:shell`：把源码构建成 `packages/shell-dist` 与各插件 `lib/client.js`；
2. 准备**带版本标识的完整安装源**：`~/.dsh/workbench/local-packages/<标识>/packages/`
   下放 `shell-dist` 与 `addons/*`（当前 11 个业务插件），用
   `rsync -a --exclude node_modules` 整目录复制，保持 `file:../../shell-dist` 的相对结构；
3. 用桌面端 CLI 装进 `$DSH_PROFILE`（见下一节），加 `--force`；
4. 跑 `pnpm audit:profile`：脚本会读源码 `packages/{shell-dist,addons/*}/package.json`，回读
   `$DSH_PROFILE_DIR/node_modules/<包>/package.json` 逐包比对版本，对全部包入口各做一次
   `import()` 冒烟，并打印 profile 的 `file:` 安装源；退出码 0 一致、1 版本差异或冒烟失败、
   2 参数/缺包/环境错误。`--skip-import` 跳过冒烟，`--json` 给 agent/CI 读，
   `--profile` / `--profile-dir` 显式指定实例（默认读 `DSH_PROFILE` / `DSH_PROFILE_DIR`）；
5. 重启后 `capabilities.list` 报的版本号与源码一致，才算「当前实例已安装」。

脚本化核对：`pnpm audit:profile`（实现 `scripts/check-profile-sync.mjs`，自测
`pnpm test:profile-sync`）。它只核对磁盘与入口 import，**不自动安装/构建/重启**，也读不到
进程内运行版本——第 5 步仍需重启后看 `capabilities.list`。

不允许的结论：「源码好了，重启就行」「安装命令成功，所以已经生效」。安装命令退出成功
不代表内容更新，必须回读 profile 里的 `package.json` 与产物文件；磁盘已更新但进程未重载时，
明确写「仍需重启」，不能声称运行中已可见。

## 本地安装要重装，不是只重启

`~/.dsh/profiles/<profile>/node_modules/` 里是**拷贝安装**的产物，源码改完不重装就
还是旧的。典型症状：`capabilities.list` 报的版本比源码低、新 action 在 `actions.list`
里看不到、`actions.help` 返回的是旧描述。

本次踩坑：`dsh-workbench-tags` 的 `package.json` 已是 1.4.2，但 `lib/tags.js` 还是旧构建，
`tags.update` 根本没注册进去——重启 DSH 也没用，必须重新打包安装该插件。
改完插件的正确姿势：`pnpm build` → 重新安装到 profile → 重启 DSH → 用
`capabilities.list` 核对版本号与 `actionCount`。

## 桌面实例必须使用桌面端 CLI 安装

先读取 `DSH_PROFILE`、`DSH_PROFILE_DIR` 确认用户当前实例；不要把临时 profile 的安装验证当作已安装到用户实例。新增插件仅提交源码、重启应用不会自动安装。交付时明确区分「源码完成」「临时实例验证」「当前实例已安装」，用户要求当前实例可用时要完成对应 profile 的安装。

macOS 桌面版使用应用附带的 CLI，不要直接调用 PATH 中 npm 安装的 `dsh`：

```sh
DESKTOP_DSH="/Applications/DeepSeek Harness.app/Contents/Resources/runtime/cli/bin/dsh"
"$DESKTOP_DSH" --help
"$DESKTOP_DSH" plugin --profile desktop add \
  "file:$PWD/packages/shell-dist" \
  "file:$PWD/packages/addons/tags" \
  "file:$PWD/packages/addons/storage" --force
```

以上为 storage 的安装示例；按实际目标调整 profile、安装位置及包列表，先完成构建。普通 `dsh plugin --profile desktop ...` 会报 `profile "desktop" is managed exclusively by the Electron application`；这表示选错 CLI，不是需要绕过限制或手改 profile。不要仅凭两个 CLI 帮助文字相似就认为它们相同。

安装后核对目标 profile 的包版本、bundle 清单和入口 import；重启/重新加载后再用 `capabilities.list` 核对运行中版本与 actionCount。磁盘安装成功但进程尚未重载时，明确说明仍需重启，不能声称运行中插件已可见。

本地 `file:` 依赖可能复用旧内容：本次 `add --force` 和 `update --force` 均退出成功，但已安装宿主仍为 0.5.5、标签仍为 1.6.5。必须读目标 `node_modules/<包>/package.json` 核实；版本未更新时，准备新的、带版本标识的完整安装源，再通过桌面 CLI 安装。保留包间相对依赖目录结构；不要直接挑文件覆盖 profile。本次使用 `~/.dsh/workbench/local-packages/storage-1.0.0/packages/` 下的完整 `shell-dist` 与 `addons/tags`，最终核实为 0.5.6 / 1.6.6。

## 不要手工「拷一半」插件目录（高频事故）

拷贝安装是按 `package.json` 的 `files` 把整个目录复制过去的。开发期如果只手工
`cp`/`rsync` 了一部分文件（比如改了 `lib/tasks.js` 只拷这一个文件），profile 里就会
出现**半套源码**：主文件已经 `import "./task-options.js"`，但目标目录没有这个文件。

后果不是「某个 action 报错」，而是**整个插件加载失败、从工作台彻底消失**：
`ERR_MODULE_NOT_FOUND` 发生在模块求值阶段，宿主会跳过该 addon，
`capabilities.list` 里只剩别的插件，用户看到的就是「插件不见了」。

本次踩坑（2026-11-09）：tasks 插件在 profile 里只有 11 个文件，缺
`db-core.js` / `db-legacy.js` / `tag-options.js`，重启后任务域整体消失；补全文件后
不重启仍然不出现，因为失败的加载结果在进程内是缓存住的。

规矩：

1. 拆文件/新增 `lib/*.js`、`client/*.cjs` 之后，**重新安装该插件**，不要手工挑文件拷；
2. 真要手工同步，必须整目录 `rsync -a --delete <pkg>/lib/ <profile>/…/<pkg>/lib/`，
   并顺带同步 `package.json`；
3. 同步后在 profile 目录做一次导入冒烟：
   `node --input-type=module -e 'await import("./node_modules/dsh-workbench-tasks/lib/index.js")'`，
   四个包入口都能 import 才算装好；
4. 改完必须重启 DSH 再验证，进程内不会因为文件补齐而自动重载失败的插件。


## 子插件的宿主行必须保留，且写成流式（插件市场「冲突」的由来）

宿主 `dsh-workbench` 是各子包的 `dependencies`（传递依赖）。DSH 启动时**只把 profile 的直接依赖**
选进 `dsh.profile.bundles`（`@deepseek-ai/dsh-app-boot` 的 `reconcileProfilePlugins()` 读的是
`manifest.dependencies`），所以「只装一个子插件」时宿主不会被自动选入，只能靠子包
`cordis.patch.yml` 里那行 `id: workbench` 把宿主加载起来。删掉这行，子插件要的 `workbench`
服务永远不会出现——插件静默不动，比报错更难查。

但插件市场（dsh-market，`~/.dsh/profiles/<profile>/node_modules/dshmarket`）装完包后的门禁
`lib/profile.js` 的 `conflictingEntryIds()` 会把「新包 patch 里 insert 的 id」与「已装 bundle 的
insert id」求交集，命中就整次回滚，文案是「和已安装的插件冲突，只能留一个」。它用的
`parsePatchRows()` 是**逐行正则**（只认 `- id: x` / `insert:` / `name:` 这类块式行），不看 name，
也不管两行是否指向同一个包。于是「每个子包都块式插一行宿主」= 任何第二个 workbench 系插件
安装必然被判冲突（2026-11-22 用户报的 bug：先装宿主再装子插件、子插件之间互装，全都失败）。

真正该修的是市场：同一 id + 同一 name 的重复行由 loader 折叠即可。宿主自带的
`@deepseek-ai/cordis-plugin-loader` 1.1.0 会把重复 id 折叠成 Map、后者胜出；市场自己的
`lib/check.js` 的 `duplicateEntryIdsAreFatal()` 也只在 loader < 1.0.4 时才判致命。市场不在本仓库，
所以本仓库按下面两条约定避开误判：

1. **共享行写成流式**：宿主行 `- { id: workbench, name: 'dsh-workbench' }`，邮件顺带带进来的
   保险箱行同理 `- { id: workbench-vault, name: 'dsh-workbench-vault' }`。js-yaml 与 DSH 的
   `applyPatches()` 解析结果和块式完全一致（照常插入这一行），市场的逐行正则却认不出流式行，
   安装不再被误判。**不要改回块式**，改回去冲突立刻复现。
2. **不要删掉宿主行**：独立安装会坏。各子插件自己的行仍用块式，市场照常能停用/启用它们。

发布侧 `scripts/stage-release.mjs` 的 `rewritePatch()` 同时改写块式与流式里的宿主名
（`dsh-workbench` → `dsh-workbench-host`），漏改会直接抛错，不会悄悄发出去。

回归与实测：

```sh
node scripts/test-market-conflict.mjs             # 共享行仍是流式、各包市场视角 id 两两不相交
node scripts/test-market-conflict.mjs --release   # 连 dist/release 发布树一起校验
node scripts/verify-install-order.mjs             # 临时 profile 真装一遍：宿主 → tasks → sites
```

## 版本号只有一个来源：package.json

首页插件卡片上的 `v5.2.46` 不是读安装包，而是读**服务端注册时传的 `version`**
（`registerDomain({ version })`，走 `/workbench/api/domains` 返回）。这个数字以前是手写字面量，
`tasks` 写到 5.2.40 之后就一直没再改，于是出现「实际装的 5.2.45、卡片显示 5.2.40」的假象——
排查安装流程会完全走偏。

规则：

- **服务端** `packages/addons/<插件>/lib/index.js` 不许写 `version: "x.y.z"`，一律

  ```js
  import { createRequire } from "node:module";
  const ADDON_VERSION = createRequire(import.meta.url)("../package.json").version;
  ```

- **客户端** `packages/addons/<插件>/client/client.src.cjs` 不许写 `version: "x.y.z"`，
  一律用 `version: __ADDON_VERSION__`；`scripts/build-addon-clients.mjs` 用 esbuild 的
  `define` 把当前 `package.json` 版本注入进去。
- **新增/改版插件**：只改 `package.json`（顶层 `version` 与 `wb.addon.version` 一起改），
  再 `pnpm build`，两个注册点的版本自动跟上。
- 护栏：`pnpm audit:version`（`scripts/audit-addon-version.mjs`）检查三件事——服务端没有
  字面量、客户端没有字面量、已构建的 `lib/client.js` 里注册的版本等于 `package.json`。
  提交前跑一次，别等用户截图来问「怎么还是旧版本」。

## 插件自己声明 npm 更新来源（host 0.17.6 起）

插件的升级地址不再靠用户记、也不靠宿主维护包名表：**在 `registerDomain` 里声明一次**，
宿主的 `host.addons.*` 与首页「插件」页都按它工作。

```ts
registerDomain({
  id: "wb-addon-tasks",
  version: ADDON_VERSION,
  update: { source: "npm", package: "dsh-workbench-tasks" }, // registry 只允许官方源
  // …
});
```

规则：

- `source` 只认 `"npm"`；`registry` 只能省略或写 `https://registry.npmjs.org`，写别的源
  一律判为「声明有问题」，该插件不会出现在可升级列表里（宁可不动，也不把用户带去未声明的源）。
- `package` 必须是真实的 npm 包名，且与发布的包一致；`distTag`（如 `beta`）可选。
- 安装动作不要自己实现：宿主把 `pluginManager`（DSH 的插件管理器，与插件市场同一条路径）
  接起来执行 `updateBundle`，占用检查、兼容检查、失败回滚、是否需要重启都由 DSH 给出结论。
- 拿不到 `pluginManager` 时必须降级为可复制的命令
  `dsh plugin --profile <profile> add <包>@<版本>` 并写明「执行后需要重启 DSH」——
  不要静默失败，也不要自己改 profile / node_modules。
- 改完在首页「插件」页实机核对三件事：自报版本与已装版本都显示、`检查全部更新`能查到版本、
  升级结果文案与 `application` 一致（`restart-required` 必须写重启）。

回归：`pnpm test:host-addons`（声明校验、官方源白名单、版本比较、列表合并、检查更新的逐条容错、
安装三种结果文案、无管理器时的命令降级）。
