# 01 · 总体架构

## 两层插件结构

系统由「一个共享运行时宿主 + 三个业务插件」组成，全部是 DSH 可直接安装的插件；
云端只负责账号与数据备份，不参与插件分发。

1. **宿主（dsh-workbench）**：唯一的共享运行时。提供本地 SQLite、域注册中心、
   同源 HTTP/SSE（`/workbench/api/*`）、`Workbench` agent 工具、账号与同步循环，
   以及浏览器端的首页卡片和沉浸式全页框架。
2. **业务插件（dsh-workbench-tasks / tags / sites）**：各自是一个独立 DSH 包，
   在自己的 `apply(ctx)` 里调用 `ctx.workbench.registerDomain(...)` 注册数据域、
   action 与客户端视图。业务包在 `dependencies` 声明宿主，安装时由 DSH 一并准备；
   删除业务包后宿主仍可单独存在。
3. **云端（wb-cloud，可选）**：账号、设备、`push`/`pull` 行级同步。
   未登录时业务完全本地运行，不访问云端；它不再是插件市场。

```
DSH profile
├── dsh-workbench        ← 宿主：db / HTTP / tools / sync / client frame
├── dsh-workbench-tasks  ← 任务 + 任务树
├── dsh-workbench-tags   ← 标签
└── dsh-workbench-sites  ← 站点 + 目录树（依赖标签域时显示标签）
        │
        └── 登录后可选 ── wb-cloud（账号 / 设备 / 数据同步）
```

## Monorepo 布局（~/code/dsh-workbench）

```
dsh-workbench/
├── docs/                        # 本文档集
├── packages/
│   ├── shell/                   # dsh-workbench：宿主 (host + client)
│   │   ├── src/index.ts         # cordis apply(ctx)，inject webServer/tools/connection
│   │   ├── src/sync.ts          # 30s 同步循环与 LWW 应用
│   │   ├── client/client.js     # 首页卡片 + 沉浸式全页 + 共享 __WB_HOST__
│   │   └── cordis.patch.yml
│   ├── core/                    # @wb/core：SQLite/schema/repo/sync 基础能力
│   ├── sdk/                     # @wb/sdk：DomainDef / WorkbenchHost / 客户端类型
│   ├── addons/
│   │   ├── tasks/               # dsh-workbench-tasks@2.2.0
│   │   ├── tags/                # dsh-workbench-tags@1.1.1
│   │   └── sites/               # dsh-workbench-sites@1.2.1
│   ├── cloud/                   # wb-cloud：node:http + node:sqlite 同步服务
│   └── shell-dist/              # 宿主的可安装产物（dist:shell 生成）
├── scripts/                     # 构建、分测、e2e、发布辅助
└── pnpm-workspace.yaml
```

要点：**core 不 import 任何 `@deepseek-ai/*`**。宿主只是把 core 接到 cordis ctx
和 UI slot 上，业务插件只依赖 `@wb/sdk` 的契约。

## 关键运行时流

- **读路径**：业务客户端视图 → `api.call(action)` → `/workbench/api/domains/:id/actions/:action`
  → 域 action → SQLite。全程本机、毫秒级、离线可用。
- **写路径**：同上，写入时追加一行到 `sync_change_log`（无论登录与否）。
- **同步路径**：登录后宿主每 30s pull/push change log；行级 LWW，冲突写 conflict_shadow。
- **Agent 路径**：模型调用 `Workbench` 工具 → 宿主按 action 名找到所属域 → 同一套 action，
  与 UI 共享同一权威数据库。

## 为什么拆成四个原生插件

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 全部塞进一个大 DSH 插件 | 最简单，无跨包注册 | 每个小功能都要走宿主发版；用户无法单独安装/卸载 | ✗ |
| B. 宿主 + 三个业务插件（本方案） | 业务可独立安装/升级/卸载；装业务插件自动带宿主；复用 DSH 安装链路 | 需要一层域注册契约与客户端加载顺序约定 | ✓ |
| C. 自建插件市场 + 运行时下载器 | 完全自主 | 与 DSH 安装体系重复，安全面和维护成本高 | ✗ |

同步协议选 **变更日志 + 行级 LWW** 而非全量快照或 CRDT：
任务/站点这类数据行小、字段独立、编辑并发概率低，LWW 实现成本最低且语义够用；
change log 表天然给出增量推送能力和审计能力。树表（task_node/site_node）的整树快照
尚未实现，当前仍只做行级同步；富文本类数据将来再考虑 CRDT。
