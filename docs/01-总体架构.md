# 01 · 总体架构

## 三层结构

系统分三层，边界清晰、各自可独立演进：

1. **DSH 壳层（wb-shell）**：唯一直接依赖宿主的包。npm 包 `dsh-workbench`，
   cordis 插件（host 半边）+ React client bundle。负责：
   - 注册 UI 入口（设置页 tab / 右侧栏面板 / overlay）；
   - 挂载子插件运行环境与本地 SQLite；
   - 暴露同源 HTTP API（`/workbench/api/*`）与 agent 工具（`Workbench`）。
2. **工作台子插件层（wb-addons）**：面向"工作台平台"而非 DSH 的包。
   每个 addon 是一个 npm/git 包（如 `wb-addon-tasks` 任务记录），
   由壳的安装器从**工作台自己的安装源**拉取，装入 `~/.dsh/workbench/addons/`。
3. **云端层（wb-cloud）**：自研服务。账号、设备、数据同步、addon 目录（市场）。
   客户端未登录时完全不依赖它。

## Monorepo 布局（~/code/dsh-workbench）

```
dsh-workbench/
├── docs/                      # 本文档集
├── packages/
│   ├── shell/                 # dsh-workbench：DSH 插件壳 (host + client)
│   │   ├── src/index.ts       # cordis apply(ctx)，inject: storage/webServer/tools/sessions/connection
│   │   ├── src/client/        # React UI（jsx-runtime, CSS Modules）
│   │   └── cordis.patch.yml   # profile 注入声明
│   ├── core/                  # @wb/core：无宿主依赖的领域逻辑（数据模型、同步引擎、事件总线）
│   ├── sdk/                   # @wb/addon-sdk：addon 开发者契约（类型 + defineAddon()）
│   ├── addons/
│   │   └── tasks/             # wb-addon-tasks「任务记录」官方首个 addon
│   └── cloud/                 # wb-cloud 服务端（Fastify + Postgres + Drizzle）
├── proto/                     # 同步协议 schema（客户端/云端共享 codegen）
└── pnpm-workspace.yaml
```

要点：**core 不 import 任何 `@deepseek-ai/*`**。壳只是把 core 接到宿主的
DI（cordis ctx）与 UI slot 上——将来若出现 Desktop/Electron 宿主或独立 Web 版，core 原样复用。

## 关键运行时流

- **读路径**：addon UI → `useTasks()`（sdk hook）→ core repository → SQLite。全程本机、毫秒级、离线可用。
- **写路径**：同上，写入同时追加一行到 `sync_change_log`（无论登录与否）。
- **同步路径**：登录后同步引擎后台循环 pull/push change log；冲突按 LWW per field 解决；对 UI 透明。
- **Agent 路径**：模型调用 `Workbench` 工具 → 壳 handler → core repository（与 UI 同一权威，绝不双库）。

## 备选方案对比（为什么这样拆）

| 方案                         | 优点                                                                      | 缺点                                                                                   | 结论 |
| ---------------------------- | ------------------------------------------------------------------------- | -------------------------------------------------------------------------------------- | ---- |
| A. 全部塞进一个大 DSH 插件   | 最简单，无第二套插件体系                                                  | 每个小功能都要走 DSH 发版；用户升级颗粒度粗；违背"工作台是平台"的定位                  | ✗    |
| B. 壳 + 子插件（本方案）     | 子插件独立安装源/更新节奏；对齐 dshmarket 先例；agent 工具可按 addon 组合 | 要自建 addon 加载器与安装器（有先例可循，成本可控）                                    | ✓    |
| C. 每个功能各做一个 DSH 插件 | 零自研加载器                                                              | "个人工作台"名存实亡：没有统一数据层、统一 UI、统一同步；登录态与同步逻辑被迫复制 N 份 | ✗    |

同步协议选 **变更日志 + LWW** 而非全量快照或 CRDT：
任务记录类数据行小、字段独立、编辑并发概率低，LWW 实现成本最低且语义够用；
change log 表天然给出增量推送能力和审计能力。CRDT（Yjs automerge）留给将来的富文本笔记类 addon 按需引入。
